# 摘要事实错误：框架调研与改进建议

日期：2026-09-11。范围：核对公开源码、官方文档与本项目现有实现；没有修改运行时，
没有新增付费模型测试。源码版本及 SHA-256 留档于
[来源清单](data/compaction-factuality-sources.json)。对用户的完整说明直接在 CLI 给出，本文用于留档。

建议优先级：明确区分原始观察、历史推断和未解决冲突；为关键结论保存可验证的来源；
再通过离线对比决定是否增加一次模型审查。更多摘要输出额度或独立摘要角色不能直接保证事实正确。

## 已有错误与当前缺口

此前冻结 A32 断点重放中，四份独立路径摘要有三份继承了 `0x485adc=0.0f` 的历史错误解释。
原文消息 38 的 `485ad0 ... 0000803f` 已提供反证：该地址的四字节按小端 float32 解码为 1.0。
两份前缀直接摘要则混有同一球体半径为 1 与 2 的说法。后者能证明摘要内部不一致，
不能单凭这两种历史解释确定真实半径。样本来自同一个断点，不能当作总体事实错误率，
也没有证据证明这些具体错误导致了另一条完整运行轨迹的图像验收失败。

另一个问题是把消息 56–57 的 gzip 1444 bytes 写入只覆盖 1–40 的摘要。
这是覆盖范围与尾部重复问题，内容本身有原文支持，应与事实错误分开统计。

目前 `src/bot/compaction/handoff.py` 的共享提示词已经要求保留假设与事实的区别、
精确保留数值、不编造完成状态；同时明确不要求逐条消息编号。`a_fallback` 的独立角色
还说明推理文本未经核实，前缀后缀也要求未确认信息标为待核实。
因此问题不是完全没有准确性提示，而是没有足够的结构和验证来落实它。

`src/bot/compaction/service.py` 已有可选 `compaction_source_refs="item"` 校验，
检查列表项是否有引用，以及消息编号是否处于覆盖范围；默认是 `range`。
这不能证明被引用的内容支持结论，也不检查原始观察与助手解释之间的语义矛盾。
直接打开该开关还需同步修改 A / a_fallback 的共享提示与输入映射，避免与“不需要编号”冲突。

## 其他框架已经做了什么

| 框架 / 核对路径 | 已实现措施 | 对事实错误的边界 |
|---|---|---|
| Gemini CLI | 先生成结构化快照，再用同一个摘要模型配置，携带待摘要历史和候选摘要进行第二次自查；重点核对技术细节、路径、工具结果与用户约束 | 是额外模型请求，但不是外部事实裁判；主要防遗漏，没有逐项证据证明或专门的矛盾拒绝判定 |
| OpenCode | 更新提示明确要求新对话与旧摘要冲突时采用新对话；另区分完成、进行中、阻塞，保留精确标识和近期历史 | 能处理旧摘要过时，但较新的助手推断仍可能错误；所核对路径未见通用语义校验器 |
| pi | 专用摘要角色、结构化进展、保留近期对话；代码从工具调用参数提取文件路径并追加文件列表 | 避免文件信息完全依赖模型记忆；提取的是调用记录，不保证操作成功，更不验证任意数值和推断 |
| VS Code Copilot | 所核对的摘要提示要求按时间审视进展、检查上下文完整性、保留任务要求和近期上下文的原文引述 | 此处的 Context Validation 是同次生成中的提示词步骤，不能据名称称为独立验证器 |
| Claude Code | 官方文档确认压缩后重新读取并注入项目根 CLAUDE.md；嵌套指令按相关文件访问恢复 | 能帮助稳定约束跨越压缩；公开文档不足以证明存在通用摘要事实审查器 |

## 适合本项目的最小改法

### 1. 关键条目明确标注证据性质

保留现有八章节，在关键事实与决策条目中使用“观察 / 推断 / 冲突”标注，不新增复杂的全局知识图谱。
规则覆盖助手普通正文和 reasoning，避免只把 reasoning 视作可能出错。

- 原始观察：实际工具返回的字节、退出码、结构化测试结果，注明来源与文件/运行版本。
- 推断：模型对观察的解释，不因写入摘要、重复多次或出现更晚而自动升级为已验证事实。
- 冲突：同一对象、属性和版本出现互斥说法，有明确纠正证据才替换；否则同时标出待核实。
- 完成状态需要实际执行结果支持，不能从工具调用意图或助手自述直接推出成功。

针对已有样本，期望摘要保留以下含义，而非注入一道题的固定答案：

```text
观察 [m:38]：0x485adc 对应字节 00 00 80 3f。
冲突 [m:38-39]：历史助手把该地址解释为 0.0f，与原始字节不一致；勿直接沿用该解释。
```

若摘要覆盖范围包含消息 51，可进一步记录消息 39 与 51 的半径解释冲突；若只覆盖 1–40，
不应把尾部 51 的新结论混入归并摘要。尾部本身仍可在续跑时提供这些信息。
无需要求压缩器运行 Python 或继续逆向；不能可靠判断时，保留原文和不确定性即可。

### 2. 为关键结论绑定来源，并维护少量确定性状态

复用已有位置映射、原文存储和引用校验；关键数值、测试结论、完成状态携带 `[m:N]`
与必要短引文。程序校验编号、覆盖范围及引文是否出现在对应原文中。
后续增量摘要需继承原始来源或父摘要中的条目来源，不能将没有本轮原文可查的旧结论重新标为已验证。

退出码、工具调用是否完成、已有结构化测试计数等可由运行器保存；普通 shell 文本不能一律
解析成确定事实。引用存在只能证明可追溯，不代表论断得到支持；从原始字节推导浮点值
也不能靠字符串匹配验证。需要领域解析器或模型语义检查，二者必须分别标记证据等级。

### 3. 将针对性自查作为待评测增强项

借鉴 Gemini 的第二次请求，给审查器候选摘要与原始证据，要求找出：
无证据支持的确定结论、观察与推断冲突、同一属性互斥值、把尝试写成成功、尾部越界内容。
审查输出问题条目及来源，允许将未解决项降级为待核实；无需继续原任务。

先离线比较全量原文审查的收益；若上线局部审查，可只传关键数值/状态的证据及相邻工具往返，
但需明确局部输入可能漏掉远处反证，不能把“未发现问题”写成全量事实通过。
不能只在摘要自报有冲突时检查，因为当前错误恰好可能没有被模型标注。
模型审查仍可能重复原错误，也可能制造新错误；要测修正率与误改率，不能只看自评分数。

现有两路径各一次的尝试上限保持为基线。引用校验失败可进入已有独立兜底；
额外语义审查若启用，应作为明确、至多一次的新增阶段计入费用和总时限，不能隐藏在修复循环中。
已发现的严重问题不得被静默发布为确定事实；标记不确定性后可在预算校验通过时继续交接。

## 缓存与验证建议

第一阶段的规则和映射只修改末尾摘要指令，不重写已经缓存的 system、工具列表和历史消息；
可保留原有前缀匹配条件，真实命中仍需 usage 验证。独立兜底继续采用其专用角色。
第二次审查的开销单独计量：完整历史仍可能很长，前缀是否命中取决于实际请求组装。

建议以冻结断点比较三组：当前 a_fallback；标注与来源校验；标注与来源校验加一次审查。
先每组五次作筛查，固定模型、主请求 32K 与各路径原有输出额度、摘要预算及抽样顺序。
提前固定事实标签，保留关键错误项和必须保留的信息，至少报告：

1. 错误确定结论数、未消解且未标注的矛盾数、关键约束遗漏数、越界引用/尾部重复数。
2. 原错误被修正或正确降级的比例，以及正确结论被误改的数量；不能通过删除所有细节取得好成绩。
3. 可发布摘要率、发布后完整上下文占用、已知费用/缺失 usage、延迟与缓存命中率。
4. 同环境快照的短续跑是否采用错误结论、重新取证成本，以及任务验收；五次筛查不足以宣称总体收益。

这些是后续测试设计，没有在本次执行，也没有证据可宣称某项建议已降低事实错误率。
