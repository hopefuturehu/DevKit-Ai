# Web 实时任务工作台设计

状态：设计提案，尚未接入生产 Web UI。日期：2026-09-08。

配套交互原型：[bot-execution-workbench.html](designs/bot-execution-workbench.html)。它是供会话预览的 HTML 片段，使用虚构示例；任务切换、工具详情、补充要求和停止操作仅演示界面行为，不执行真实任务。

## 用户体验

Web 工作台延续 CLI 的任务交互，让用户在执行中看到更多细节，同时保留清晰的阅读顺序：任务要求 → 当前计划 → 进行中的动作 → 工具结果 → 交付物和最终回答。面向普通使用者，不包含评测队列、评分或人工标注。

推荐三栏布局：左侧会话与历史任务，中间对话和执行过程，右侧按需打开所选动作的详情。中间区域始终是主要阅读路径；右侧承载参数、长日志和诊断信息，工具调用默认只占一张简洁卡片。浅色和深色主题沿用当前 Web 的深蓝与红色强调。

| 区域 | 用户看到什么 | 可做什么 |
|---|---|---|
| 左侧会话 | 会话标题、当前运行/等待/完成状态、最近时间 | 新建、切换、恢复历史会话 |
| 顶部状态 | 模型、连接状态、任务已用时间、累计输入/输出 Token、已知费用 | 查看任务信息；连接状态与任务状态分开 |
| 任务计划 | 待做/进行中/完成的步骤、Bot 当前动作 | 展开完整计划，快速定位当前步骤 |
| 主对话流 | 用户消息、Bot 流式正文、工具调用卡、阶段完成说明和最终回答 | 展开调用、查看输出、跳转交付物 |
| 工具详情 | 名称、参数、stdout/stderr、结果、退出码、调用/等待耗时 | 切换输入/输出，按需读取长输出；原始事件放到高级详情 |
| 输入区 | 运行中显示“补充要求”，空闲时显示“描述任务” | 发送补充要求、明确停止当前任务 |
| 交付物 | 新增/修改文件、可验证的 diff、报告与下载入口 | 打开文件、查看变更、下载已存在的产物 |

右侧打开时不挤掉主对话。在较窄屏幕改为上下排列；生产版本的手机端可用详情抽屉。原型用上下排列保证所有内容可读。

## 执行中的呈现方式

- 工具调用卡：以“读取配置”“运行测试”等简短描述为主，保留 `read_file/run_command` 名称；显示运行中、等待审批、已返回、失败等明确状态，以及一两行结果摘要。点开后才显示完整参数和长日志。
- 流式输出：主界面展示最新动作，选中的详情显示持续追加的 stdout/stderr。用户滚动查看旧内容时暂停自动跟随，提供“有新输出 · 回到最新”；暂停跟随不停止任务。
- 长命令：区分工具调用已经返回与进程仍在运行。用 `process_id` 将后续 `poll_process` 结果串起来，避免启动成功后显示“测试通过”。
- 文件操作：`read_file` 展示文件与行范围；`apply_patch` 展示修改内容和工具结果。参数中的替换片段不能充当最终文件 diff；最终产物需要真实文件或快照证据。
- 当前计划：直接复用 `plan.updated`。没有计划时不虚构百分比，用当前动作和已执行步骤说明进度；无法预计剩余时间时不展示倒计时。
- 子 Agent：主对话显示子任务标题、职责和状态，可展开子任务轨迹；需要实际父子关联。后续可加入并行泳道，主界面不要求用户理解 Agent 调度。
- 压缩和重试：主对话以简短系统消息说明“正在整理上下文”“请求重试中”。压缩详情、Token 分布、记忆读取和原始事件放入高级视图。
- 审批：展示具体动作、影响范围和原因，允许/拒绝关联到准确的请求 ID。评审普通工具日志不会触发审批。
- 补充要求：消息进入对话后先标记“已发送，等待 Bot 接收”，收到 `run.steered` 等确认后再改为“已接收”；发送失败可重试。
- 停止：点击后进入“正在停止”，收到取消终态再显示“已停止”，保留已有输出。明确运行停止是否包含已启动进程，不能只停止流式显示就宣称执行已取消。
- 最终结果：Bot 正文与真实执行结果并列。工具报错不必意味着整次任务失败；任务结束也不自动表示外部测试通过。

## 数据与状态规则

1. 调用使用 `(session_id, run_id, tool_call_id)` 归并。`tool.requested` 提供参数，`tool.started` 提供开始状态，`tool.output` 提供流式数据，`tool.completed` 提供摘要与 `context_ref`，`tool.result` 提供统一结果和退出码；它们只计作一次调用。
2. 内部工具或拒绝执行的调用不一定有 started/completed；通过 requested/result 仍需正确结束卡片。没有结果时显示“状态未知”或“等待结果”，不能擅自判成功。
3. `success=true/status=running` 显示“调用已返回，进程运行中”。工具耗时、审批等待、进程总耗时分开；缺时间戳显示“未记录”。
4. 模型正文按 Run、step、phase 合并，终态消息与 delta 去重。高级视图只展示实际记录的模型 reasoning，没有记录时不补写推理。工具请求暂缺统一 step 字段，初版按事件顺序呈现，不虚构精确的模型轮次关联。
5. `model.usage` 当前值是累计值，不能逐条相加；费用未记录时显示“未记录”。Run 汇总、压缩和子任务用量须明确范围，避免重复计算。
6. 输出默认读摘要；按需读 `context_ref` 的已留存结果。工具源输出被截断时，即使有 Blob 也不一定可恢复原始全文，界面须区分“显示摘要”“源输出已截断”“全文不可用”。流式日志与终态摘要不重复拼接。
7. 连接断开与 Run 终态分开。重连后先恢复历史再合并实时事件，以 `event.id` 去重；用户切换会话不应丢失后台执行状态。
8. 历史和实时使用同一事件归并器。`sequence` 属于 EventBus 实例，重启和子 Agent 实例可能重置，不可单独作为全局恢复游标。API 使用稳定持久化次序的 opaque cursor；数据库重建/导入后更换 epoch 并重新同步。
9. 输出按文本渲染，Markdown 使用安全渲染；文件、Blob 和事件读取均检查归属。未知事件可折叠显示，缺失字段有占位，避免格式差异使整页失效。

## 分阶段实现

### 第一版：实时执行界面

继续使用 FastAPI、WebSocket、SQLite；将当前单文件前端拆分为状态归并、主对话、计划、调用卡与详情视图。先完成工具输入/流式输出/结果、运行状态、补充要求和停止，保留现有会话与 Skill 能力。

前端接入当前 `/ws` 的执行事件，补充 `steer` 界面。会话列表使用现有 API。当前审批后端按队列取下一个请求，若加入可交互审批卡，必须同时改成通过请求 ID 与所属 Run 精确解析，不能仅修改按钮外观。

### 第二版：历史恢复与文件产物

拟新增接口（均未实现）：

| 接口/协议 | 用途 |
|---|---|
| `GET /api/sessions/{session_id}/runs` | 查询会话的任务运行与汇总 |
| `GET /api/runs/{run_id}/events?cursor=...&limit=...` | 分页恢复历史轨迹，返回游标与快照边界 |
| `GET /api/runs/{run_id}/tools/{tool_call_id}` | 调用聚合信息及输出引用 |
| `GET /api/runs/{run_id}/blobs/{blob_id}` | 校验归属后按需读取留存输出 |
| Run 订阅、恢复和审批响应协议 | 指定会话/Run 和请求 ID，恢复断线事件 |
| 产物清单与受限文件读取 | 显示真实修改文件、diff 和下载内容 |

先订阅并缓冲实时事件，读取历史到快照边界后合并缓冲事件，按 ID 去重。长日志分页/虚拟列表，用户浏览旧内容时保持位置。原始事件和只读诊断可在这一阶段加入。

### 第三版：复杂任务可视化

加入子任务层级与并行泳道、产物预览、上下文/记忆高级诊断和跨设备恢复。默认主界面仍以用户消息、计划、动作和结果为主。

## 实现后需要验证

- 所有类型的工具调用可正确结束，进程运行中不会误报完成；失败、拒绝、取消和断线有不同状态。
- 多个会话、多个 Run 重用 Call ID 时不串线；刷新与重连不丢事件、不重复显示消息。
- 流式正文与工具输出同时到达时分别更新；用户查看旧内容时不被抢滚动位置。
- 补充要求可确认是否被接收；停止先显示处理中，依据真实终态更新。
- 长输出、源截断、Blob 缺失和 HTML 形似输出能安全、明确呈现。
- Token 累计不重复计数；计划不存在时不虚构进度；没有 reasoning 或最终文件快照时不补造内容。
- 桌面、窄屏、键盘交互和浅/深色主题均可阅读。示例原型的交互检查不能替代真实 WebSocket 和后端验收。
