# 重复工具调用：四项针对性调整与开源方案比较

日期：2026-09-13。状态：**实施提案，尚未接入生产代码**。
bot 源码基线为 `1f9053cc48eba26471ab2882aea5e4bdfa1dbc91`；历史任务运行包为
`99d70d8`。当前行为见 [自动终止与长任务控制](termination.md)，历史实验见
[V4 Flash 三轮复测](context-strategy-flash-repeats.md)。

建议依次实施：稳定结果身份、按新证据计算进展、独立重复检测、执行前限制。
前三项使运行器能够识别循环，第四项让识别结果真正影响执行。调整不需要增加逐工具 LLM
判断，也不以重新设计摘要作为前置条件。

## 1. 问题与可验证的目标

历史 repeat-2 的 A 轨迹中，同一命令调用 230 次，均返回成功、退出码 0、空输出；
每次创建不同的 `process_id`。CURRENT 同轮另一条命令重复 186 次，也存在相同输出和不同
进程 ID。两者是已经发生的轨迹事实，不是未来修复的效果预测。

原始证据位于 `artifacts/context-strategy-flash-repeats-20260913/repeat-2/jobs/` 下的
`a/035880d7ef5554b217e53a75ce5e87e4__QQdgthU/agent/events.jsonl` 与
`current/035880d7ef5554b217e53a75ce5e87e4__HV74SVN/agent/events.jsonl`。
计数按工具名与参数聚合请求，并通过 tool call ID 对应结果，排除调用 ID 本身的变化。

当前 `_process_progress()` 把进程 ID 放进完成结果的 `evidence_key`；控制器将显式
`WEAK` 直接接受为弱进展，弱进展还能抵扣停滞计数。`run_command` 又不是幂等工具，
不进入幂等重复计数。因此，同样的动作和输出不断被当作不同证据，周期匹配也无法命中。

此前对现有控制器的内存复现得到：保留进程 ID，20 次相同输出调用均继续；只替换成稳定
结果 key，六次观察出现警告、恢复、最终停止；再逐次改变 `wait_seconds`，又可连续
20 次不触发。这是控制器输入层的复现，尚不是修复后完整任务的回测。

验收分为两个目标：一是对已确认的重复模式限制实际执行次数；二是保留必要重试、正常
轮询和上下文恢复。提前停止失败任务不等于提高任务成功率，费用变化须与验收结果一起报告。

## 2. 调整一：拆开执行身份与结果证据

### 实现位置与数据契约

- 在 `src/bot/core/termination/identity.py` 增加纯函数，统一产生调用身份和观察身份。
- 修改 `src/bot/tools/builtins.py` 的 `_process_progress()`、`_process_tool_result()`，
  对齐受管与非受管命令路径。
- 扩展 `src/bot/core/progress.py` 的信号契约：保留 `evidence_key`，增加可选资源身份
  `subject_key` 和证据完整性 `evidence_complete`。未知工具默认不保证完整性。

建议三个身份各司其职：

| 身份 | 内容 | 用途 |
|---|---|---|
| 执行身份 | `process_id`、tool call ID、运行 ID | 查询进程、审计、关联请求与结果 |
| 调用身份 | 工具执行语义、目标环境、有效 cwd、有效参数 | 判断是否再次请求同一操作 |
| 观察身份 | 终态、退出码、分别计算的 stdout/stderr 哈希、完整性 | 判断是否获得相同结果证据 |

完成结果的观察身份去掉进程 UUID、耗时和交付用的 `context_ref`。失败结果也采用稳定的
状态与错误证据，避免每次失败的新进程 ID 破坏相同失败检测。stdout、stderr 分别哈希后
结构化编码，避免直接拼接产生边界歧义。

`WAITING` 仍用进程 ID 标识等待对象，保留最后输出时间与存活状态；相同进程仍在运行不是
“命令又执行了一遍”。进程 ID 因此不能从所有信号中一概删除。

输出被截断时，仅有已保留文本的哈希不能证明完整输出相同。首版标记证据不完整，只用于
提示，不单凭它执行重复阻断；完整流摘要可作为后续执行层增强。

### 收益与代价

直接修复本次新进程 ID 掩盖重复的问题，两个执行后端行为一致。计算量主要是已有输出的
线性哈希，无新增模型请求。局限是输出相同只能证明观察相同，不能证明命令没有副作用。

验收：新建六个真实进程执行同一小输出命令，执行 ID 各异但调用/观察身份相同；退出码、
stderr、目标环境发生变化时必须区分；截断结果不得被标为完整。

## 3. 调整二：只有新证据才计入弱进展

### 实现位置与判定顺序

修改 `ProgressController._classify_progress()`、`observe_tool()` 和 `finish_step()`。
工具给出的 `WEAK` 表示“可能提供观察”，由控制器结合既有证据判断是否为新观察。

| 情况 | 建议处理 |
|---|---|
| 首次读取某文件区间、首次得到某命令结果 | 新证据，计 `WEAK` |
| 相同调用再次得到已记录结果，资源版本没有变化 | 重复证据，计 `NONE` |
| 相同调用得到变化后的结果 | 新证据，计 `WEAK` |
| 已验证相关文件内容变化、明确状态转换 | 计 `STRONG`，推进相关资源版本 |
| 同一存活进程等待，无新输出 | `WAITING`，沿用独立静默时长策略 |
| 未知工具缺少稳定完整的证据 | 保守标记，不以相同文本直接硬阻断 |

首版保留“新 `WEAK` 小幅抵扣停滞”的现有规则，缩小行为变化；重复 `WEAK` 不再抵扣。
`STRONG` 必须来自工具可验证的状态变化，模型自述完成、重复计划或新的调用 ID 均不够。

任务级进展计数与特定调用的重复记录分开。一个批次里既有 `WAITING` 又有重复命令时，
等待不得让重复检查提前返回；无关文件发生变化，也不能清除另一条调用的重复记录。
相关资源确实变化才使其观察失效。资源依赖未知的 shell 命令不能声称已完成这种关联验证。

### 收益与代价

修正“执行成功等于取得进展”的偏差，使停滞指标有实际含义。代价是维护有限的证据历史，
以及处理必要回读：此前读过的内容可能已经被压缩移出模型可见上下文。

为必要回读设置独立的交付凭据：运行器确认原始交付被压缩覆盖时，允许恢复对应证据一次；
凭据绑定原始结果引用及覆盖位置，消费后持久化。优先重新交付已有结果，避免重新执行命令。
不得通过模型自行声明“我忘了”解禁，也不因任意压缩事件清空循环记录。

验收：稳定读取不能无限维持 `no_progress_steps=0`；不同文件内容相同不能误合并；
修改后再读能继续；压缩后能恢复所需原文，但相同恢复凭据不能重复解禁。

## 4. 调整三：增加独立于幂等声明的重复检测

### 调用规范化

首版只实现已知内置工具的确定性规则，不尝试推断任意 shell 程序是否等价：

- JSON 对象键排序，保留数组顺序；补齐与工具实际执行一致的默认参数。
- `run_command` 保留 argv、有效 cwd、目标环境、交互模式、硬超时及影响执行的环境配置；
  排除只影响本次返回等待时长的 `wait_seconds`。
- `run_shell` 保留完整 script；仅对与 `run_command` 实际使用同一 argv 的路径合并身份。
  不删脚本文本中的空白、注释或重定向。
- 读取保留路径与区间，搜索保留查询、范围、过滤和分页。路径按执行目标解释，不能用宿主机
  `Path.resolve()` 替容器解析路径。
- 未知插件仅采用规范 JSON 参数匹配，首版不自动推断其参数哪些无关。

在现有控制器内增加独立记录，记录调用/观察哈希、次数、最近位置、资源版本、恢复/阻断状态。
所有完成调用均可提供重复线索，不再以 `idempotent=True` 为入口条件；幂等声明仍服务其他
工具语义。相同调用结果变化时开始新计数，不因中间插入另一工具就自动重置。

保留现有 16 条周期窗口、最长周期 4，用规范化身份检测 A→B→A→B 等循环。
首版硬限制只针对已经达到重复证据门槛的具体调用，避免看到两个不同调用就直接判定整个
任务无效。窗口内观察记录与持久化的限制记录分开，窗口滚动不得解禁已限制调用。

### 状态和兼容

恢复提示、无关强进展、上下文压缩和普通 resume 不清空独立重复记录。记录绑定 session、
任务及执行目标身份；正常完成后清理。明确的新任务可以创建新作用域。

为记录设置容量上限，建议首版 256 项，优先淘汰非活跃记录；活跃限制不得被 LRU 静默淘汰。
容量用尽时产生明确事件并进入受控收尾，避免无限增长或靠制造新参数绕过限制。

`STATE_VERSION` 升到 2，继续使用现有 JSON checkpoint。v1 无法恢复稳定身份时保留可迁移
的通用计数，丢弃不兼容指纹并记录一次迁移事件。新增字段、阈值和模式变化分别处理，
不能沿用“配置指纹改变就把所有状态忘掉”的隐式行为。

### 收益与代价

覆盖本次命令工具，也解决单改等待参数就躲过检测的问题。相较只比较原始 JSON，多了内置
工具适配和迁移维护；仍无法可靠识别 `cat x`、`sed -n '1,$p' x` 等任意语义等价程序。

验收：参数键序与 `wait_seconds` 变化不绕过；cwd、环境、分页、区间变化不误合并；
无关强进展、混合等待、压缩和 resume 不擦除已有模式；跨目标不得继承旧限制。

## 5. 调整四：把恢复提示接到执行前限制

### 建议初始阈值

以下次数从首次实际执行起算，是待验证的工程起点，不是已经证明的最优参数：

| 时点 | 执行策略 | 对模型的反馈 |
|---|---|---|
| 第一次 | 正常执行并记录证据 | 正常结果 |
| 第二次得到相同完整观察 | 执行后警告 | 指出同一调用未提供新证据 |
| 第三次仍相同 | 本次结果交付后限制该调用 | 提供一次结构化恢复提示 |
| 第四次再请求该调用 | 执行前拒绝，不再创建进程 | 返回明确未执行的结果及已有证据引用 |
| 连续两个模型响应只碰撞限制，且没有其他有效工作 | 统一收尾，状态 `blocked` | 总结已有结果、重复模式与恢复条件 |

“两个响应”不是两个工具调用。同一响应批量请求十个重复工具，不能消耗十次纠偏机会；
至少给下一次模型响应改变路线的机会。仍有其他有效工作的运行可以继续，只限制相关模式。

重复拒绝属于运行器控制结果：建议 `success=false`，metadata 包含
`executed=false`、`reason_code=repeated_observation`、次数和授权范围内的证据引用。
不要虚构退出码，不把拒绝作为一次真实工具失败叠加旧的失败计数，也不伪造执行开始/完成事件。

### 接入与协议不变量

在 `src/bot/core/agent.py` 的工具派发路径加入统一检查入口。注册工具先完成参数验证和
静态权限判定，再在审批交互及 `tool.execute()` 前检查限制；内置特殊分支使用同一入口的
适配器，并保留各自授权校验。重复检查不能授予新权限或因命中缓存泄露原本无权访问的结果。

每个已经记录的 tool call 都必须收到对应 tool result。同批次前面调用触发限制后，后续
调用仍逐个产生实际结果或“未执行”结果；最终决定在批次闭合后提交，避免半途中断造成
悬空调用。统一 finalizer 保证不执行工具，核验其请求中的 `tool_choice` 与工具声明兼容性。

恢复提示保持短小，包含：受限调用、重复次数、已有证据、允许继续的方向，例如缩小查询范围、
读取其他证据或检查明确前置条件。提示本身不清零历史，模型输出“已换思路”不能解禁。

### 误拦边界与推广策略

完整的相同输出仍不证明没有副作用：连续运行静默迁移脚本、消费队列或等待外部服务，可能
每次都在推进。因此，这是一条有界重试策略，不能包装成通用的语义正确性证明。

建议新增 `repeat_guard_mode = observe | enforce`。先以 `observe` 记录“本会阻断”的事件，
通过验收后在测试配置启用 `enforce`。命令工具在 `enforce` 下对三次相同完整观察应用上表，
包括空输出；部署前必须验证静默副作用反例。未知工具和不完整输出保持提示模式。

正常进程轮询继续走 `WAITING`。确需反复启动命令的任务，通过宿主配置或可信运行控制设置
明确的重复额度/轮询策略，不能由模型的普通工具参数自行增加额度。已有预算仍然适用。
相关资源已验证变化时允许新探测；未知资源依赖不使用“任何一次写入都全部解禁”的捷径。

收益是限制实际副作用和模型反复消耗，不再依赖模型听取提示。代价是误拦会更直接影响任务，
需要观测模式、受控例外和可恢复结果；因此第四项最后开启强制模式。

## 6. 与其他开源方案比较

比较依据是下列源码与官方说明，不是同一数据集上的性能横评。优缺点是由实现推导出的工程
取舍，不能据此声称 bot 的任务成功率高于其他框架。

| 项目 | 已核对的机制 | 优点 | 局限 | bot 应借鉴的部分 |
|---|---|---|---|---|
| OpenCode | 相同工具与输入重复三次触发 `doom_loop` 权限；默认 `ask` | 实现直接，交互场景可由人判断是否继续 | `allow` 或自动批准会削弱阻止效果；固定快照检查当前 assistant message 的工具 parts，不能假定跨响应循环都被覆盖 | 将重复判断放到实际执行许可之前；无人值守场景另设明确限制 |
| DeepSeek Harness | 规范 JSON 比较连续工具和参数，默认在 3、5、8 次后注入提醒 | 不依赖输出内容，不增加模型请求，改动小 | 提醒本身不阻断；变化非语义参数仍能绕过；连续计数不等于周期检测 | 借鉴规范化与分级提醒，继续增加稳定观察和执行限制 |
| Hermes | 文件读取去重与搜索重复限制；未变化读取返回简短提示，持续重复可 `BLOCKED`；压缩后清除读取去重缓存 | 同时减少重复 I/O、结果 token，并防止引用已不可见的原文 | 主要覆盖特定文件工具；mtime 判定与其他工具重置计数都有适用边界 | 借鉴工具侧去重、必要回读；把可见性失效与循环历史分开 |
| OpenHands SDK | 观察动作/结果重复、连续错误、交替模式和独白；部分情形先 nudge，判为 stuck 后运行状态转 `STUCK` | 多模式检测，外层状态机能实际停止循环 | 全局停机会影响其他可继续工作；动作相等比较包含 thought 等字段，表面变化可影响识别 | 借鉴独立检测与外层停止，先限制具体调用再决定整段收尾 |
| bot 本提案 | 稳定调用/观察身份、新证据进展、跨压缩重复记录、执行前分级限制 | 对准已复现故障，覆盖命令与混合批次，保留异步等待和恢复能力 | 适配器、资源版本、checkpoint 迁移复杂度较高；任意 shell 语义仍无法完全判断 | 优先交付确定性规则，先观测再强制 |

OpenCode 官方说明给出三次重复触发、默认询问及自动模式行为；具体检查范围依据固定源码，
两者不可混同。[权限说明](https://opencode.ai/docs/permissions/)、
[processor 源码](https://github.com/anomalyco/opencode/blob/da4730e4a41dcbb2cb2d907dd2b06ac481b8f962/packages/opencode/src/session/processor.ts)。

DeepSeek Harness 的上述计数、JSON 规范化和提醒方式见
[repeat-tool-reminder](https://github.com/deepseek-ai/deepseek-harness/blob/47f943859bef60e4160492346772ded9b24f765a/packages/guard/repeat-tool-reminder/src/index.ts)。

Hermes 读取的连续计数路径在第三次提示、第四次阻断；未变化文件去重路径可能更早阻断，
不能统一概括为“第四次才阻断”。其压缩后缓存处理见固定本地 checkout 的
[file_tools.py](https://github.com/NousResearch/hermes-agent/blob/eac1e25127a75c61116a0bbb8ce7681a2f8b61b4/tools/file_tools.py) 与
[conversation_compression.py](https://github.com/NousResearch/hermes-agent/blob/eac1e25127a75c61116a0bbb8ce7681a2f8b61b4/agent/conversation_compression.py)。
此版本依据本地源码核对，远程固定 SHA 页面本次未成功获取，不用在线 main 的后续重构替代。

OpenHands SDK 依据 2026-09-13 在线 main：
[stuck_detector.py](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/conversation/stuck_detector.py)、
[阈值定义](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/conversation/types.py)、
[运行循环](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/conversation/impl/local_conversation.py)。
这些 main 链接会变化；后续正式复现实验应再固定其提交。

## 7. 分批实施与验收

| 批次 | 交付内容 | 必过检查 |
|---|---|---|
| A | 稳定身份、受管/非受管一致性 | 新 PID 相同结果可识别；失败与截断语义正确 |
| B | 新证据判定、独立重复记录、规范化、v2 checkpoint | 参数轻微变化、混合等待、强进展、周期、恢复与迁移用例 |
| C | 执行前限制、结构化恢复、必要回读凭据、观测开关 | 真实执行次数有界；拒绝不产生进程；批次调用/结果配对完整 |
| D | 历史轨迹回放、反例矩阵、同状态续跑评测 | 明确误拦和漏检范围后，再决定生产默认是否强制 |

最小测试集放在现有 `tests/unit/test_progress_termination.py`、
`tests/unit/test_execution_tools_policy.py`、`tests/integration/test_agent_loop.py`，
必要时新建 identity 单元文件。覆盖重点如下：

1. **正例**：相同命令新 PID；不同 `wait_seconds`；相同失败；A/B 交替；插入无关强进展；
   一个批次混合等待与重复调用；压缩和 resume 后再次碰撞限制。
2. **反例**：同内容不同文件；目标或环境变化；修改后回读；分页搜索；截断输出；长进程静默
   等待；显式允许的静默副作用重复；上下文压缩后的必要原文恢复。
3. **协议**：模拟模型一次请求多个重复工具，实际启动次数受限，所有 tool call 均有 result；
   被拒绝调用不污染真实失败计数；最终收尾不重新执行工具。
4. **真实进程**：使用本地小命令验证执行层，而不只伪造 `ProgressSignal`；无须付费模型即可
   验证识别、计数、拒绝和配对。强制重复的模拟模型用于验证受控 `blocked`，不证明能恢复解题。

历史轨迹回放只回答“新检测器会在何处触发”。触发后模型将改走不同轨迹，不能把原轨迹余下
成本直接当作已实现节省，也不能推断最终成功。后续同一检查点成对续跑，覆盖重复读取、失败
重试、异步等待三类任务，固定模型/工具/预算并重复观察，再做整题验收。

报告指标：冗余实际执行次数、首次提醒/限制位置、恢复后是否出现有效新证据、误拦用例数、
官方任务通过数、每次成功成本、总模型请求数、检测耗时与状态大小。收益数字待实施验证后填写。

本方案不覆盖单个模型响应内部的超长参数重复，也不保证所有语义等价命令都可检测。
输出长度与异常生成终止应作为独立问题处理，避免把工具执行循环修复误报为所有重复问题已解决。
