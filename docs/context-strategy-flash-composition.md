# V4 Flash 压缩前后的上下文组成

日期：2026-09-13。依据已有 `path-tracing-reverse` 测试做离线复核，没有发起新模型请求。

## “释放四十多个点”的分母

最新三轮有效结果中，A、B、双路径的净释放率中位数约为 57%；这是
`(压缩前输入预算 − 压缩后输入预算) / 压缩前输入预算`。
约 43% 是剩余比例。如果把释放空间除以整份可用输入额度，则约为 46%–47%。

| 方案 | 成功发布样本数 | 净释放预算 tokens 中位数 | 占压缩前输入的比例中位数 | 占 94,208 可用输入额度的比例中位数 |
|---|---:|---:|---:|---:|
| A | 10 | 44,301.5 | 57.00% | 47.03% |
| B | 7 | 43,302 | 56.94% | 45.96% |
| 双路径 | 13 | 44,081 | 57.55% | 46.79% |

这里使用发布时记录的完整输入预算，包含本地输入估算的 5% 余量。
131,072 总窗口减去 32,768 输出预留、2,048 协议预留、2,048 安全余量，得到
94,208 可用输入；压力触发点为其 80%，即 75,366。
32K 是允许生成和预留的空间，不是已经占用输入的正文，也不是摘要必然生成的长度。
CURRENT 未记录同状态预算对，保持三轮报告中的“未记录”，不补造同口径中位数。

统一取首轮测试中每组第一次成功发布，避免混合不同事件各部分的中位数。
这些例子展示组成，不是四组平均值，也不是同一输入上的控制实验。

消息序列化器离线计数。下表不含输入估算的 5% 余量、32K 输出预留；每格为
**K tokens（占当时输入的比例）**，K=1,000。百分比可能因四舍五入略有误差。

| A 前 | 74.18 | 3.91（5.3%） | 5.08（6.8%） | 65.19（87.9%） | 0 |
| A 后 | 27.52 | 3.91（14.2%） | 2.96（10.7%） | 17.94（65.2%） | 2.71（9.8%） |
| B 前 | 72.84 | 3.91（5.4%） | 9.85（13.5%） | 59.08（81.1%） | 0 |

| 双路径后 | 30.35 | 3.91（12.9%） | 0.59（1.9%） | 23.23（76.5%） | 2.62（8.6%） |

固定部分由系统规则、环境、工具定义、运行提示与序列化余项合计而来，约 3,783 tokens；
用户原文及其消息标记约 131 tokens，始终保留。没有逐层原始请求快照，因此不把这个
余项进一步伪拆成“系统提示精确多少、工具 schema 精确多少”。四个例子前后余项均为
3,783，是复原能够对齐总输入的交叉检查。

压缩发生在 CURRENT 第 26 步、A 第 29 步、B 第 52 步、双路径第 12 步之后。
CURRENT 前值由前一主请求本地计数加该轮完成的 Assistant/工具消息重建，假设运行前缀
不变；不是历史实测预算对。其例子释放约 42.47%。A/B/双路径前值来自记录预算扣除
5% 余量；后值取发布后首个请求的本地计数。投影中的占位摘要 ID 与实际 ID 会造成
少量 token 差异，不能把例子直接作为新的精确净释放统计。

四组压缩后供应商实际输入分别为 42,086 / 27,439 / 30,624 / 30,312 tokens，
与离线计数的差异分别为 85 / 85 / 127 / 37；各分项不是供应商逐层计费数据。

双路径在首次压缩前刚完成一次 `load_context_reference`，新读取正文约 11.39K tokens，
还未被主模型消费。复原时使用事件引用的完整投递 blob，不能用数据库中的短回执替代，
否则会少算约 11.27K，并把这部分错误归到固定提示。

本组实验关闭 Skills、长期记忆和子 Agent，且 thinking=disabled；这些不是残留输入的大头。
Assistant 正文仍可能很长，表中与工具调用参数合并统计，不能把它称为 reasoning 字段。

## 为什么不能直接压到几 K

四个方案的续跑结构都是：

`固定上下文 + 用户原文锚点 + 一份活动摘要 + 未覆盖的近期历史 + 必要运行提示`

首次压缩前没有旧摘要；后续压缩会用新根替换旧根，已覆盖历史不会继续作为完整原文
常驻输入。原文留在 SQLite/blob 中供按需读取。B 的叶节点与中间合并节点存储在后台，
不是全部塞回主 Agent；A/双路径的摘要生成后缀和独立压缩角色也不作为新固定提示留存。

1. **近期原文占主要空间。** 上例 CURRENT/A/B/双路径分别保留
   36.66K / 20.90K / 24.80K / 23.82K 的近期 Assistant 与工具内容，占后续输入
   86.9% / 75.9% / 80.6% / 78.5%。摘要及封装仅 1.60K–2.71K。
2. **“最近 20K”采用字符启发式。** CURRENT 保留尾部的启发式估算为 19,119，
   模型 tokenizer 却算出 36,656；汇编、地址和数值让两种口径差距很大。
   CURRENT 不做 A/B/双路径的 40K 完整投影检查，因此留下的输入更大。
3. **A/B/双路径共用边界选择。** 先按近期历史目标选边界，再预留
   `ceil(8192 × 1.1) + 256 = 9,268` tokens 的摘要空间，推进到完整投影不超过
   40K；真实摘要通常比预留短，最终输入常在 30K 左右。三者主要改变摘要生成方式，
   并没有采用三个不同的尾部保留目标，所以释放率接近。
4. **摘要长度上限不是实际长度。** 本例摘要正文按 tokenizer 为
   1,454 / 2,562 / 1,880 / 2,385 tokens；4K 门禁使用另一套启发式估算。
   8K/32K 输出额度均不等于实际摘要长度。CURRENT 的 60K 是摘要请求输入上限，
   也不是每次必须从续跑输入中删掉 60K；本例摘要实际输入只有 35,824 tokens。

进一步缩短摘要的空间收益有限：在双路径例子中把整块 2.62K 摘要砍半，只能再释放
约 1.31K。若要从约 30K 降到 10K，主要需要减少近期原文，尤其是汇编、重复工具结果、
长代码和调用参数，并用引用按需回读。那是改变信息保留策略，需要另测任务正确性，
不能直接从当前通过率推定同样安全。本次未修改运行代码。

## 与 Codex、Claude Code、OpenCode 比较

本节为源码/官方文档比较，不是新增四框架同题测试。没有这些框架在本题上的前后请求，
不能给出它们实际“工具占 60%、摘要占 20%”之类的统计。压缩前的基本组成相似：固定
指令和工具定义，加用户消息、Assistant、工具调用/结果、既有摘要及可能的恢复内容；
具体比例由任务轨迹、模型 tokenizer 和配置决定。

Codex 的文本路径依据已归档的 `02a8f038b87a`（2026-09-11）源码；不声称是本机 Codex
当前启用路径。Claude Code 依据 2026-09-13 实际打开的官方文档，核心实现没有完整公开。
OpenCode 区分前次调研的 V1 源码 `193de13a88d6` 与当前 V2 文档，不能混用两代规则。

| 实现 / 路径 | 压缩后固定内容 | 摘要或 checkpoint | 近期 Assistant/工具原文 | 占比上的直接含义 |
|---|---|---|---|---|
| 本项目 A/B/双路径 | 系统/工具/环境、用户锚点保留 | 一份新根 | 本例约 21K–25K，双路径包含尚待消费的读取正文 | 原文尾部仍占约 76%–81% |
| Codex 文本路径 | 基础上下文保留或重建；预算内用户原文保留 | 文本摘要 | 替换历史不复制旧 Assistant/工具链 | 被替换范围的原始 Assistant/工具尾部为零，摘要及固定内容占比会更高 |
| Codex 原生路径 | 按路径重建初始上下文，保留服务端或客户端选定的 items | 不透明 compaction item | 由具体接口和返回窗口决定，不能套用文本路径的零尾部结论 | 需看返回 items 和续跑 usage，不能按加密字符串字符数算占比 |
| Claude Code | 系统、项目根指令、auto memory、计划等保留或恢复 | 会话摘要 | 近期交换及关键内容的保留、文件恢复随路径/状态变化；无公开统一尾部比例 | 文件/Skill 恢复可能重新占据明显空间，不能推定摘要占绝大多数 |
| OpenCode V1 | system/tools 继续组装 | 摘要消息 | 默认按 usable input 的 25% 选尾部，夹在 2K–15K 的估算预算内 | 与本项目同属摘要加尾部，但预算和切点不同 |
| OpenCode V2 本地 | 指令基线和工具继续参与请求 | 文本 checkpoint | 默认 `keep.tokens=15000` 的近期序列化上下文；工具结果缩至 2,000 字符，附件用描述符 | 尾部不是逐字完整原文，更主动削减工具内容 |

**Codex 的关键区别。** 文本实现 `build_compacted_history_with_limit()` 只把倒序挑选、
合计不超过约 20K 的用户消息写回，再追加 summary；这里的 20K 不是 Assistant/工具尾部。
对于本题这种只有一条短用户请求、绝大多数输入来自 Agent 执行的任务，采用这种保留
策略会释放更多原文空间。它同时让后续判断更依赖摘要，不证明任务正确性更高。
本地依据：[文本 replacement 构造](../artifacts/compaction-factuality-20260911/codex/codex-rs__core__src__compact.rs)
及归档 `sources.json` 中的 commit/文件 SHA。

OpenAI 当前文档明确原生 compaction 返回不透明状态，standalone 返回窗口可能另有保留
items，应该整体回放。因此不能把“272K 压到几 K”的观察普遍化，也不能将原生结果用
Markdown 摘要长度衡量。依据：[OpenAI compaction 文档](https://developers.openai.com/api/docs/guides/compaction)。

**Claude Code 的主要额外项是恢复内容。** 官方文档列出最多重读 5 个近期文件；单个
超过 5K tokens 时只给路径引用。Skill 恢复上限为每份 5K、总共 25K，另有 CLAUDE.md、
memory、计划与 compact hook 输出。不是每次都会填满这些上限；没有运行记录就不能
算固定占比。依据：[恢复规则](https://code.claude.com/docs/en/context-window#what-survives-compaction)。
SDK 文档也说明压缩会保留近期交换，不能把 Claude Code 全部入口说成“原文尾部恒为零”。
依据：[Agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop#automatic-compaction)。

**OpenCode 要区分代际与计数口径。** V1 选择尾部时对转换后的模型消息 JSON 做估算，
15K 不是模型 tokenizer 严格上限，因此不能直接声称一定小于我们实测 21K–25K。
V2 文档则描述独立保存的近期序列化上下文与工具结果缩短，默认目标也是 15K，允许
配置。之前归档的 09-12 core 源码曾为 8K 默认值，本次以当前 V2 文档的 15K 明确标注，
不改写旧版本记录。依据：[V1 选择器](../artifacts/compaction-research-20260911/anomalyco__opencode-193de13a88d6/packages/opencode/src/session/compaction.ts)、
[V2 官方说明](https://opencode.ai/v2/docs/compaction)。

### 固定其余条件后的算术对比

用本项目双路径首例的 72,446 输入为基线，固定“提示/工具/用户原文”3,914 和
“摘要及封装”2,619 tokens，只改原文保留量。下表是**本项目保留策略的假设投影**，
不是 Codex/OpenCode 的实测，也没有假定原生加密状态与这份摘要等价。

| 保留策略 | 压缩后总量 | 固定及用户占比 | 摘要占比 | Assistant/工具尾部占比 | 相对 72,446 的释放率 |
|---|---:|---:|---:|---:|---:|
| 本项目首例，实测轨迹复原 | 30,349 | 12.9% | 8.6% | 78.5% | 58.1% |
| 假设尾部恰好 15K，参考 OpenCode 的目标 | 21,533 | 18.2% | 12.2% | 69.7% | 70.3% |
| 假设只保留用户原文，参考 Codex 文本路径 | 6,533 | 59.9% | 40.1% | 0% | 91.0% |

这说明“压到几 K”很大程度取决于是否继续携带执行原文。Claude Code 无法代入一个
公开固定的恢复量，故不编造第四个数值。如果要得到各产品实际占比，需要在同一任务
边界记录压缩前请求、压缩后且尚未新增工作的请求，并将重新注入的文件/Skill 单列；
原生不透明状态使用服务端可用的计数或续跑 usage，不对密文做字符估算。本次未进行
这些跨框架模型调用。
