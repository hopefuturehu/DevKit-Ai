# 摘要改进设计：保留关键证据与判断状态

日期：2026-09-11。状态：设计，尚未实现或执行模型测试。
本方案基于此前的断点重放与[事实可靠性调研](compaction-factuality-research.md)，
用户可直接在 CLI 阅读完整设计说明，本文用于留档。

## 选择与目标

建议先给 `a_fallback` 增加一项可选的证据保留增强：关键结论标注证据性质，
少量关键原文由程序核对后随摘要保留。默认不增加第二个模型的事实审查请求。
现有前缀一次、失败后独立一次的机制继续承担生成失败恢复。

针对三项已观察问题：

| 问题 | 对应改动 | 能保证的边界 |
|---|---|---|
| 助手把 0x485adc 误读成 0.0f，摘要继承错误 | 保留工具原始字节，助手解释标为推断 | 原始片段不被模型改写；不保证自动完成所有数值推导 |
| 半径 1 与 2 同时写成事实 | 单列当前判断与未解决冲突，记录已否决说法及原因 | 提示与格式约束减少确定性升级；任意自然语言矛盾仍需语义评估 |
| 尾部 56–57 的结果混入覆盖 1–40 的摘要 | 新增条目引用必须属于本轮输入范围，旧条目须可回溯到父摘要 | 能拒绝越界引用，不能仅凭合法引用证明陈述没有偷用尾部信息 |

目标是让错误更难以被包装成确定事实，并让后续 Agent 能低成本核对关键证据。
不把“引用合法”“摘要发布成功”计作“事实已验证”。

## 1. 保持一次生成，把证据与解释分开

保留现有八个标题，不引入完整知识图谱或新的交接工具。
在 Critical Context、关键决定与完成状态条目中，区分以下标注：

- 观察：用户明确要求或实际工具结果的直接记录；不包含模型重新计算的技术结论。
- 推断：助手对证据的解释，包括普通正文和 reasoning 中的解释。
- 冲突：同一对象、属性和版本下存在互斥说法，尚无充分证据确定哪一个正确。

关键数值、执行结果、完成状态使用 `[m:N]` 引用。观察条目还提供一个待校验的短原文片段。
解释和原文不混成同一条“已确认事实”。章节之间尽量只保留一次技术结论，
Progress 记录做过哪些操作，关键数值及判断集中在 Critical Context，减少互相矛盾的重复表述。

提示新增的具体规则：

1. 用户最新明确指令更新任务要求；助手最新说法不自动覆盖已有工具证据。
2. 计划、已发起调用、调用返回成功、任务验收通过分别表达，不能跨级推断。
3. 旧摘要是派生记录，重复摘要不会提高它的可信程度；未核实状态必须继承。
4. 只有有证据的纠正才能让旧判断失效；保留必要的旧判断、否决原因及来源，防止重走错误路线。
5. 不得靠删去难以解释的关键值消除冲突；无法判断时保留证据与待核实状态。
6. 只读输入中已有信息，不调用工具或继续原任务。摘要后的 Agent 在需要依赖存疑结论时再核实。

同一个工具结果可能对应多个不同解读，来源是 tool 并不意味着解读正确。
运行器不能仅因引用了 tool 消息，就将自由文本结论标为已验证。

## 2. 程序核对并保存少量关键原文

模型在同一次摘要响应里选择引用与短原文，运行器从冻结消息中查找完全匹配的片段，
再用原文重新渲染证据部分。找不到、引用越界、误将助手解释标作工具观察时，候选校验失败。
不允许模型编造一个“差不多”的引文，也不使用匹配失败后的模糊纠正来掩盖错误。
字节、数值和命令的片段超长时，保留完整的较小片段或路径/消息引用，不从中间截断成新值。

对于已有结构化执行状态，可直接记录调用完成状态、退出码及明确提供的测试计数。
不为任意 shell 输出增加通用事实解析器；退出码为零只说明该命令成功返回，不能证明未执行的验收通过。

证据与判断的逻辑展示示例：

```text
工具证据 [m:38]：保留实际十六进制输出中的对应片段。
历史推断 [m:39]：助手曾将 0x485adc 解释为 0.0f，未独立验证。
待处理：如果需要使用此常量，应根据原始字节核对解释。
```

示例用于说明类型，不作为运行时固定答案或测试题专用提示。
若模型在当前输入中已经可靠识别冲突，可以明确记录冲突；程序本身不声称能自动完成逆向推导。

## 3. 固定预算与多轮继承

首版采用以下设计起点，最终以完整投影计数为准：

| 内容 | 预算 |
|---|---:|
| 状态与判断摘要 | 目标 3,000 tokens，硬上限 3,500 |
| 核对后的证据、引用及必要元数据 | 最多 500 tokens |
| 最终发布摘要，含标题与包装 | 合计最多 4,000 tokens |

这将原来 4K 的纯摘要上限划出一部分用于证据，不额外扩大压缩后的上下文。
主请求与前缀摘要输出额度仍为 32K，独立兜底仍为 8K；完整续跑低水位仍按现有 40K 检查。
这些容量约束与摘要 API 的输出额度不同。

证据优先保留当前待解决问题所依赖的原始值、冲突双方来源，以及关键执行失败/验收结果。
预算不足的证据保留引用供回读；若少量不可省略的证据仍放不下，候选进入现有兜底，
不能静默删去后把剩余结论当作已核实。

首次压缩可引用覆盖区间内的原文。增量压缩中：

- 新条目引用本轮实际提供的原文；尾部仍只保留在尾部，不扩大已归并覆盖范围。
- 旧条目沿用父摘要的原文位置、片段和原有判断状态；运行器以父链、范围与哈希核对。
- 父摘要中保留的关键证据片段再次随摘要提供，减少把旧摘要文本当唯一证据的情况。
- 历史摘要没有逐条来源时，将其标作“旧摘要继承、证据待回读”，不能补造已验证来源。
- 不声称所有历史原文都重新进入了模型输入；未选中的证据仍在原文存储中。

证据可随已有摘要 blob 一同留档，不需要先建立新的全局事实数据库。
源码已有 item 引用模式要求所有列表项带引用，与本方案“关键条目引用”并不相同；
实现时应增加专用校验，不能直接全局打开旧开关，也不能改变 current/a/b 对照行为。

## 4. 请求、发布与恢复流程

```text
冻结范围、父摘要和原文
  → 原请求前缀 + 新摘要后缀：一次
  → 现有结构校验 + 条目/引用/原文匹配校验 + 完整预算校验
      合格：原子发布摘要、证据及新游标
      可恢复失败：使用同一冻结输入，独立摘要一次，再走相同校验
      双失败：保留原摘要与游标
```

两条路径共用内容要求与验证。独立兜底仍从冻结输入生成，不把第一份错误候选作为事实来源。
取消、鉴权、费用/时间预算耗尽或源状态变化的终止规则不变。没有第三次自动修复请求。

在前缀路径中，新的约束、位置映射和父摘要证据只追加到摘要后缀，不回写已有 system、历史消息或 tools，
也不更改 tool_choice。因此保留已有缓存匹配条件，是否真实命中仍按 usage 计量。
发布后的新摘要必须重新建立缓存，这一点没有消失。

恢复时，主 Agent 已能看到随摘要保存的短证据。只有下一步依赖存疑结论、证据版本过旧或
片段不足时，才使用现有原文回读/文件读取能力核对相关范围，不在每次压缩后全量重读。
被标注的冲突可以随摘要发布为待核实状态；严重引用或原文匹配失败不能被静默忽略。

## 5. 验证与实施顺序

第一阶段只实现上述增强，作为 a_fallback 的可选实验项。

| 代码位置 | 职责 |
|---|---|
| compaction/handoff.py、strategies.py | 新路径专用提示、关键条目引用、父证据追加，两条生成路径一致 |
| 新 compaction/evidence.py | 解析标注、原文匹配、引用/父来源校验、证据渲染与预算 |
| 现有候选校验与发布逻辑 | 合并后的 4K 与完整 40K 预算检查、原子保存及失败分类 |
| 评测脚本 | 记录原文保留、事实质量、误改、费用和短续跑行为 |

先做行为测试，覆盖助手自述不能直接证明成功、引文改写/越界被拒绝、父证据跨轮继承、
存疑状态不自动升级、额外证据计入预算，以及保持最多两次请求和零摘要工具执行。
程序测试只覆盖可执行的格式/来源/状态规则，不能用假模型断言证明语义准确性提升。

随后在已有首个冻结断点上，两组各五次比较当前 a_fallback 与证据增强版。
固定模型与现有 32K/8K 额度、最终摘要总预算，随机交错顺序并分别记录缓存与费用。
提前固定原始事实标签，不向执行中的模型注入题解。

首轮至少报告错误确定结论数、关键约束遗漏数、未标注冲突数、尾部重复数、错误降级/纠正数，
以及结构成功率、证据校验失败率、发布后完整输入、耗时和已知费用/缺 usage。
“错误被标为待核实”和“错误被真正修正”分别计数，不能合并为准确率提升。

通过首轮后，再检查旧摘要已经含错、后续原文提供更正的断点，并做同环境快照的短续跑。
检查 Agent 是否继续采用错误数值、为核实增加多少读取，以及实际任务验收结果。
五次重放只能筛查，不能据此宣称总体成功率、成本或事实准确率已提升。

只有在关键原文已保留、错误仍频繁进入续跑决策时，才把“额外一次模型对照审查”作为第二阶段实验。
它应在离线先对比真实纠错、误改与费用，不能只看审查模型自己给出的通过分数。
