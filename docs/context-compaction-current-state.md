## 1. 快照结论摘要

当前压缩系统的持久化、原始证据和边界安全机制是正常的。高失败率不是 SQLite 写入慢、原始
Transcript 丢失，也不是压缩输入再次失控，而是下面几项策略叠加的结果：

1. `compaction_model` 未单独配置，执行 `/model deepseek-v4-pro` 后，压缩也继承了 reasoning
   主模型；
2. 可见摘要软目标为 8,000 token，API 输出上限为 8,192 token，几乎没有收敛余量；
3. Provider 的 `completion_tokens` 还包含大量 reasoning 消耗，实际 completion 经常达到
   12K–16K，而最终可见摘要平均只有约 2.3K；
4. 八个固定章节和“每个列表项必须带消息引用”的合同较脆弱，少一个引用就拒绝整份摘要；
5. 输出截断、引用错误、空摘要和输入过大最终都会进入相近的修复或缩范围重试路径，导致与
   输入大小无关的失败也重新调用完整摘要模型；
6. 压缩失败或缩范围后，活动游标推进不足，大体积原始尾部继续触发下一轮压缩。

截至本快照，共有 26 次压缩计划，其中 15 次失败：

| 指标 | 当前值 |
|---|---:|
| 压缩尝试 | 26 |
| 成功发布（`ready` + `superseded`） | 11（42.3%） |
| 失败 | 15（57.7%） |
| 全部压缩累计耗时 | 3,852.1 秒（约 64.2 分钟） |
| 失败记录累计耗时 | 2,157.0 秒（约 36.0 分钟） |
| 失败耗时占比 | 56.0% |
| 已发布摘要平均长度 | 约 2,266 token |
| Provider completion / 可见摘要 | 平均约 7.3 倍 |

最近一次上下文压力处理先运行了 245.4 秒并因长度失败，再缩小范围运行 246.2 秒成功，单次用户
命令因此在压缩阶段等待了 491.6 秒。

## 2. 快照时的压缩架构

### 2.1 运行时上下文

运行时只注入一份活动摘要：

```text
稳定 System / 项目指令 / Skill / Memory
                    +
             一份 ready 摘要
                    +
          摘要 cursor 之后的原始尾部
```

原始消息不会因压缩而删除。每个压缩版本记录覆盖范围、父版本、来源 SHA-256、消息引用、模型
usage 和状态。发布使用以下生命周期：

```text
building -> ready -> superseded
         \-> failed
```

只有完整校验并成功发布的 `ready` 版本才能推进活动 cursor。失败记录不会替换上一份可用摘要；
Resume 时还会重新验证原始范围的 SHA-256。因此当前实现属于“fail closed、原文可恢复”的滚动
摘要，而不是破坏性裁剪。

主要实现位于：

- [`ContextConfig`](../src/bot/config/models.py#L134-L157)：长度与压缩预算；
- [`TokenBudget`](../src/bot/core/context.py#L76-L109)：主请求硬限制和触发目标；
- [`ContextCompactor`](../src/bot/compaction/service.py#L72-L128)：压缩入口和版本投影；
- [`ContextCompactor.compact()`](../src/bot/compaction/service.py#L121-L314)：安全边界、计划与范围重试；
- [`SQLiteSessionStore`](../src/bot/sessions/store.py#L885-L1038)：压缩事务持久化。

出现过的 15 万至 17 万 token 无界 backlog 已经修复，当前请求的规划目标确实约为 48K。

### 2.3 快照时的执行流程

```text
主请求估算超过 96K
  -> 从最新消息向前保留约 48K 原始尾部
  -> 在完整 Tool 原子组边界确定待压缩前缀
  -> 将“上一份摘要 + 新增原始消息”规划到约 48K 输入以内
  -> 写入 building 记录
  -> 使用 compaction_model；为空时继承当前主模型
  -> 生成八章节 Markdown 摘要
  -> 校验输出长度、finish_reason、章节和逐条 [m:N] 引用
  -> 校验失败时最多修复一次
  -> 仍失败时缩小原始范围，最多再生成一次
  -> 成功则原子发布 ready，失败则保留旧 ready
```

## 4. 高失败率的原因

### 4.1 首要原因：压缩继承了 reasoning 主模型

`ContextConfig.compaction_model` 默认是 `None`。CLI 的 `/model` 会修改共享的
`runtime.config.model.name`；摘要请求使用：

```python
model=self.config.context.compaction_model or self.config.model.name
```

因此会话切换到 `deepseek-v4-pro` 后，压缩也自动切到了 Pro。数据库中的 26 次记录全部证实
使用的是该模型。

11 份成功发布的摘要平均只有约 2,266 token，但 Provider 报告的 completion 平均约为可见
摘要的 7.3 倍。最近成功记录的可见摘要为 2,257 token，completion 却是 16,282 token。
这表明大部分输出预算和墙钟时间消耗在不可落库的 reasoning，而不是最终 Markdown。

Provider 客户端的 `timeout_seconds` 是 HTTP 流读取超时，不是完整压缩调用的墙钟上限。只要
模型持续输出 reasoning，连接就有进度，单次调用可以持续 200 多秒而不触发 read timeout。

### 4.2 软目标与硬上限贴得过近

提示把摘要目标设为 8,000 token，wire `max_tokens` 为 8,192，只留 192 token、约 2.4% 的
余量。这不足以吸收：

- reasoning 模型的隐藏输出；
- Provider 与本地估算器的 tokenizer 差异；
- 八个标题、列表和来源引用开销；
- 增量摘要合并造成的输出波动。

更关键的是，当前 Provider 返回的 completion usage 可达到约 16,384，说明请求中的
`max_tokens=8192` 与“最终可见摘要最大长度”不是同一口径。可能的原因是 reasoning 计入
completion，或该模型路由对 `max_tokens` 使用了不同语义。现有预算模型没有区分这两部分。

一旦 Provider 以 `length`/`max_tokens` 结束，哪怕已经产生部分可用正文，当前校验也会拒绝整份
候选，不允许它成为活动摘要。

### 4.3 摘要格式和逐条引用合同过于脆弱

候选必须包含八个固定章节，并要求每个 Markdown 列表项都带 `[m:N]` 或 `[m:N-M]`。这提供
了原文导航能力，但带来三个问题：

1. 任意一个 bullet 漏引用都会拒绝整个版本；
2. 修复模型为了通过校验，可能删除无法补引用的有效事实；
3. 引用增加正文长度和模型遵循负担。

本快照中 4 次引用失败耗费 410.2 秒，占全部失败的 26.7%。而压缩记录本身已经保存完整覆盖
范围、来源 SHA-256 和原始 Transcript，逐条引用不是恢复正确性的唯一保障。当前校验也只验证
引用是否位于合法范围内，并不验证引用消息是否真正支持对应事实，因此它更接近导航索引，而
不是事实证明。

### 4.4 失败恢复没有按原因分类

当前外层范围尝试对多数 `compaction_failed` 使用相同策略：缩小原始范围，再运行一次完整摘要。
但不同失败需要不同恢复动作：

| 错误 | 缩小输入是否有效 | 当前风险 |
|---|---|---|
| Context overflow | 有效 | 应缩小 Tool 原子组范围 |
| 摘要没有比原文短 | 通常有效 | 可缩小范围或加强凝练 |
| 网络中断、429、5xx | 无直接关系 | 应同范围短退避重试 |
| 输出达到长度上限 | 通常无效 | 会再次支付 reasoning 输出 |
| 缺章节或引用 | 通常无效 | 应只修复候选，不重发原文 |
| SQLite 发布失败 | 完全无效 | 不应再次调用模型 |

最近的 245.4s 失败加 246.2s 重试就是典型案例：输入减半并没有缩短 completion 时间。统一缩
范围策略把格式和输出问题转换成了第二次昂贵模型调用。

### 4.5 压缩失败会形成上下文压力反馈环

失败不会破坏旧 `ready`，这是正确的；但它也不会推进 cursor。缩范围成功时 cursor 只推进一
部分。于是会出现：

```text
原始尾部增长
  -> 主请求超过 96K 目标
  -> 启动同步压缩
  -> 输出/引用失败
  -> 缩范围重试或保持旧 cursor
  -> 原始尾部仍然很大
  -> 下一轮再次触发压缩
```

在这个状态下，Context Planner 还要反复从大尾部中装箱，主模型请求不再是稳定的 append-only
前缀，Provider Prompt Cache 命中也会下降。因此压缩失败既产生直接等待，也会提高后续每一步
的输入成本。

### 4.6 输入大小仍有影响，但已不是当前主因

旧实现确实存在 15 万至 17 万 token 的无界 backlog；当前代码已经用 48K 规划目标和 60K
硬上限修复。最近两次调用进一步说明：

- 48,743 输入、16,384 completion：245.4s；
- 26,175 输入、16,282 completion：246.2s。

输入减半而耗时基本不变，说明当前阶段继续单纯缩小输入只能获得有限收益。优先级更高的是
压缩模型隔离、reasoning/output 预算和错误分类。

## 5. 哪些部分目前是正常的

以下机制有实际数据和测试支撑，不是本轮高失败率的根因：

- 压缩输入已经有 48K 规划目标和 60K 硬上限；
- Tool Call/Result 以原子组切分，不会主动制造孤立 Tool Result；
- 原始 Transcript 不删除，失败后仍可回读；
- `building` 失败不会覆盖旧 `ready`；
- 成功分块会逐块推进 cursor，后续从新 cursor 增量更新；
- Resume 会验证来源 SHA-256，不需要重新生成有效摘要；
- SQLite 事务耗时相对模型调用可以忽略；
- Tool 本身的执行耗时不是本批压缩记录中的主要成本。

因此不需要重写整个上下文系统。当前问题集中在“用哪个模型生成摘要、给它多少输出空间、
怎样判定失败和是否值得再调用一次”。

## 6. 根因链路

```text
/model 切到 deepseek-v4-pro
  -> compaction_model 为空，压缩继承 Pro
  -> reasoning 消耗远大于最终可见摘要
  -> completion 接近 12K–16K，单次持续 2–4 分钟
  -> finish_reason=length 或正文/引用校验失败
  -> 候选不发布
  -> 修复或缩范围后再次调用完整摘要模型
  -> 一次上下文压力产生两次长调用
  -> cursor 推进不足，保留 70K 左右原始尾部
  -> 后续请求再次进入压缩和滑动装箱
```

根因优先级如下：

1. **压缩模型与主模型未隔离**；
2. **reasoning completion 与可见摘要共用一个不准确的输出预算**；
3. **长度/格式/引用/传输错误没有采用不同恢复路径**；
4. **逐条引用合同显著提高了失败概率**；
5. **失败后的大尾部使问题持续复发**。

## 7. 当时提出的后续验证顺序

以下顺序是快照时提出的验证计划，现已由 `cff6338` 和推广评测执行完成：

1. 固定独立、非 reasoning 的压缩模型，保持其他参数不变，测量失败率和单次耗时；
2. 将“摘要软目标、可见正文硬限制、Provider completion 上限”拆成不同预算；
3. 增加完整压缩调用的墙钟上限，而不只依赖 HTTP read timeout；
4. 按 context overflow、transport、length、format、persistence 分类恢复；
5. 评测将逐条引用降低为章节级或范围级溯源；
6. 在压缩稳定后，再 A/B 近期尾部大小和输入上限。

在完成第 1–4 项之前，直接继续降低输入上限或增加范围重试次数，都无法解决当前最昂贵的
reasoning 输出和重复调用。

## 8. 数据口径

状态与耗时统计来自 `.bot/state.db` 的 `context_compactions` 表。核心聚合口径：

```sql
SELECT
    status,
    COUNT(*) AS attempts,
    SUM(duration_ms) / 1000.0 AS seconds,
    AVG(input_tokens) AS avg_input,
    AVG(output_tokens) AS avg_output
FROM context_compactions
GROUP BY status;
```

失败分类按持久化错误文本归类：输出长度、来源引用、空摘要、缺章节和其他。活动 cursor 后的
70,288 token 使用当前 [`TokenEstimator`](../src/bot/core/context.py#L339-L383) 对消息 674–740
逐条估算。Provider completion 与可见摘要比例只统计 `ready` 和 `superseded` 且摘要长度大于
零的 11 个已发布版本。

这些数字描述当前会话和当前 Provider 路由，不应直接外推为其他模型的固定性能；但失败类型、
代码路径和重复调用之间的因果关系可以从持久化记录复现。
