# 40 题批次中已覆盖 18 题的上下文管理分析

分析对象是 2026-09-09 08:10（Asia/Shanghai）停止的批次，源码基线为 `578f660`，模型为
`deepseek-v4-flash`。本文只分析已保存的运行过程，没有新增模型调用或重新运行题目。

**主要结论：常规推理的缓存复用较好，大工具结果外置有明显局部收益；18 题本身没有触发摘要压缩。
异常收尾的缓存利用、小结果的引用开销，以及压缩摘要与 Provider 的协议兼容，是这批记录暴露出的改进点。**
不能把输入长度控制正常，等同于任务交付正常。

## 1. 样本与计算口径

主样本 `main18` 每题只取一次模型运行：16 个原始 attempt 1，加上国际象棋 attempt 3
和大文本编辑 `native-1` 环境变体，共 Terminal 15 题、SWE 3 题。
后两个属于环境恢复，不能用于补写原始 attempt 1 的成绩。

`sam-cell-seg` 首次验收无效，但模型过程确实发生，因此保留在上下文统计中；同脚本验收复测不重复计入。
`largest-eigenval` 缺少独立 Agent 结果文件，使用事件日志及保留的 SQLite 状态。
其官方停止后仍返回的 2 次响应也计入实际用量，另列边界说明。
题目判分和环境问题参见[部分结果报告](public-benchmark-40-results.md)。

另有 4 次补充运行：heap attempt 3 原版复跑、heap attempt 4 协议候选、chess attempt 4
协议候选、SymPy attempt 2 协议候选。它们不增加题目覆盖数，只用于单列观察。

| 范围 | 运行数 | 有 usage 的 API 响应 | 实际输入 tokens | 实际输出 tokens | token 加权缓存命中率 |
|---|---:|---:|---:|---:|---:|
| 原始 attempt 1 | 16 | 544 | 13,406,865 | 336,163 | 91.37% |
| 本文主样本：18 个不同题目 | 18 | 604 | 14,528,126 | 393,124 | **91.52%** |
| 单列补充复跑/候选 | 4 | 223 | 9,367,984 | 209,146 | 94.09% |
| 全部已记录模型运行，供对账 | 22 | 827 | 23,896,110 | 602,270 | 92.53% |

计算规则：

- API 用量取逐响应 `raw_usage`，缓存命中率为 `Σ prompt_cache_hit_tokens / Σ prompt_tokens`。
  每个响应均检查 `hit + miss == prompt_tokens`，主样本 604 次全部有完整缓存字段。
  这是 Provider 报告的输入缓存，未测量本地 `TokenEstimator` 的缓存命中率。
- 不把 `model.response` 和 `model.usage` 当成两次请求；不重复读取 `trace/events.jsonl` 副本。
  压缩取 `context.compaction.request.completed`，其后累计 `model.usage` 不再次累加。
- 604 次响应包含 597 次常规推理及 7 次异常收尾；响应数不同于任务步数。
- 原文/摘录大小差只将每条持久消息计一次，字符数是实际长度，token 差使用冻结实现的
  `TokenEstimator` 估算。它既不是累计 API 节省量，也不是开关某措施的整题对照实验。
- 所有百分比按未四舍五入的数据计算；请求 p95 使用最近秩法。

## 2. 缓存：整体较好，异常收尾明显下降

| 阶段 | 响应数 | 输入 tokens | 缓存命中 tokens | 未命中 tokens | 命中率 |
|---|---:|---:|---:|---:|---:|
| 常规推理 | 597 | 14,313,350 | 13,292,544 | 1,020,806 | **92.87%** |
| 异常收尾 | 7 | 214,776 | 3,712 | 211,064 | **1.73%** |
| 主样本合计 | 604 | 14,528,126 | 13,296,256 | 1,231,870 | **91.52%** |

598/604 次请求有至少一部分命中，占 99.01%；单请求命中率中位数为 94.64%。
“有任何命中”容易显得很高，应主要看 token 加权值。按题目等权平均则为 86.55%，
说明长任务的高命中率抬高了整体加权值。各题第一次请求合计已有 80.30% 命中，
不能将所有命中都归因于单题内部的历史复用，也没有冷缓存对照来隔离固定前缀设计的贡献。

**7 次异常收尾只占输入量的 1.48%，却贡献全部未命中输入的 17.13%。**
源码的收尾路径会重新组装终止上下文，并设置 `tools=[]`；这些变化可能影响缓存前缀。
这是有源码支持的解释候选，缺少逐次实际发送请求的完整记录，不能把全部缓存下降精确归因于某一项变化。

缓存命中也不代表任务高效。例如 SAM 用了 95 次响应、338.9 万输入 tokens，命中率为 94.74%；
它仍承担这些请求和重复历史的处理。缓存指标应同时配合请求数、输入总量及产物验收。

`largest-eigenval` 有 133,713 输入、8,713 输出 tokens 在官方停止后才返回，其中包括长度截断及收尾。
若只统计官方停止前返回的响应，主样本变为 602 次响应，缓存命中率为 91.90%。
这里按“响应返回时间”划界，不表示这些请求全部在停止后才发起。

## 3. 压缩：主样本未覆盖，补充运行有两次

主样本中，`context.compaction.started/completed/failed` 均为 **0**；
压缩触发覆盖率是 **0/18**，压缩成功率是 **N/A（0 次尝试）**，不能写为 100%。
`context.packed`、`context.limit_reached` 和 `context.retry` 也均为 0。
`context.packed` 只在 Planner 实际丢弃消息时发布；其为零不表示没有执行预算检查。

主样本每请求实际输入中位数为 19,707.5，p95 为 60,339，峰值为 **68,913 tokens**。
配置上下文窗口为 131,072，硬输入预算为 120,000，自动压缩目标为 96,000。
触发使用启发式估算，不能直接用 Provider 实际 token 数替代判断，但这一规模与未触发压力压缩的日志一致。

补充运行中的两次压缩分别如下：

| 指标 | SymPy attempt 2 候选 | Chess attempt 4 候选 |
|---|---:|---:|
| 压缩位置 | 第 88 步前 | 第 52 步前 |
| 归并消息数 | 143 | 93 |
| 选中压缩源字符数 → 摘要字符数 | 140,997 → 4,720 | 146,643 → 3,131 |
| 该段字符削减率 | **96.65%** | **97.86%** |
| 可见摘要估算 tokens | 1,987 | 1,730 |
| 压缩 API 实际输入 / 输出 tokens | 47,876 / 2,131 | 37,674 / 1,974 |
| 压缩流程耗时 | 13.65 秒 | 17.33 秒 |
| 摘要生成 / repair / condense / 传输重试 | 1 / 0 / 0 / 0 | 1 / 0 / 0 / 0 |
| 压缩 API 缓存命中率 | 0% | 0% |
| 最近保留尾部估算 tokens | 19,874 | 19,400 |
| 压缩后成功返回的常规响应 | 31 次 | 0 次 |

两次都成功生成并安装摘要，**机械完成率为 2/2**，没有触发摘要修复或重试。
两次均保留了用户锚点并保留约 20K 最近历史；没有单独的关键事实召回验收，语义保真率未知。
96%–98% 只是选中压缩源的字符削减，不能当成整个上下文或整题成本削减比例。

SymPy 相邻常规请求实际输入从 **101,373 降至 28,738（下降 71.65%）**。
首次压缩后请求命中率降至 14.70%；之后第 4–31 次请求合计恢复到 95.06%。
这说明上下文缩短与缓存重新积累可以同时发生。前后请求也包含正常工具与运行状态变化，
这个差值是观测值，不是保持其他条件相同的消融结果；不能据此精确计算累计净节省或回本轮数。

两次压缩合计额外消耗 **85,550 输入 + 4,105 输出 tokens**，均没有命中缓存。
Chess 紧接着的正常请求因 `reasoning_content` 协议错误被拒绝；既有请求对照中，只补摘要的空
reasoning 字段即可使相应请求从 HTTP 400 变为 200。SymPy 压缩后先正常运行 31 次，随后也遇到
reasoning 协议错误，其整题错误尚不能仅凭时间关系归因于压缩。
详细对照见[已有归因记录](public-benchmark-40-results.md)。

因此，若要求“摘要安装后下一次正常请求成功”，本小样本只有 **1/2**；
若要求“安装后正常完成整个运行”，则为 **0/2**。这两个运行完整性指标不等于产物通过率：
SymPy 候选的补丁仍通过了官方测试。也不能用两次样本估计一般压缩可靠性。

## 4. 各类削减措施的实际效果

### 大工具结果外置及小结果开销

9/18 题发生真实内容缩短，共 **23 条**大工具结果。逐条验证 blob 的 SHA-256，并检查内联
head/tail 与原文一致；23/23 都可在保存状态中恢复原文。这里的“原文”是工具交给运行器的内容，
工具自身若已截断，blob 不会恢复它未返回的部分。

| 每条消息仅计一次的口径 | 原始字符数 | 内联字符数（含引用说明） | 字符净减少 | 估算 token 净减少 |
|---|---:|---:|---:|---:|
| 23 条发生缩短的大结果 | 920,592 | 187,643 | 732,949（**79.62%**） | 183,031 |
| 695 条没有缩短的小结果 | 483,003 | 571,268 | **−88,265** | **−30,427** |
| 全部 718 条普通工具结果 | 1,403,595 | 758,911 | 644,684（**45.93%**） | 152,604（**42.89%**） |

这些普通工具结果不包含另外 3 条一次性交付的引用读取。
内联规则同时受 4,000 估算 token 与 6,000 + 2,000 字符的限制，因此即便不足 4K token，
超过 8,000 字符也会缩短。

**外置收益很集中。** `count-dataset-tokens` 两次网页结果从 568,815 字符降到 16,317，
贡献大结果字符削减的 75.38%，以及全部普通工具消息净估算节省的 89.32%。
去掉该题，其余 17 题合计仍净减少 16,291 估算 tokens，但收益明显小得多。

每个未缩短的小结果也附带“完整内容已持久化”及完整引用说明，平均增加约 43.8 估算 tokens。
按全部普通工具消息各出现一次计算，**12/18 题的内联表示反而更长**，其中 SAM、Astropy、Django
虽然有大结果缩短，收益仍被小结果说明抵消。这个结论只覆盖普通工具消息的表示大小；
没有计入每条结果被回放的次数、引用读取及其他层，不能据此声称这 12 题的实际总成本变高。

### 其他措施

| 措施 | 主样本中的证据 | 能支持的结论与限制 |
|---|---|---|

| 一次性交付 | 3/3 持久结果为短回执 | 读取响应表示共 11,616 字符、估算 2,906 tokens；回执共 785 字符、估算 315 tokens。替换表示每套减少 2,591 估算 tokens，不能直接当作累计节省 |
| query 定位读取 | 0 次；3 次均为 offset/limit 读取 | 本轮没有验证 query 相对分页的调用或 token 收益 |
| 工具源头限量 | `tool.result.truncated=true` 3 次，均为 `search_text` | 覆盖限量输出，但完整未截断规模未知，不能计算削减百分比；不包含命令自行使用 head/grep 等限量 |
| 分层 Planner 丢弃 | `context.packed=0` | 未观察到该路径实际削减消息 |
| Provider 溢出应急压缩/外置 | `context.retry=0`，`context.limit_reached=0` | 未覆盖恢复路径，不能报告恢复成功率 |
| Tool schema 渐进披露 | DNA 有 1 次 `activate_tools`，请求成功 | 激活不等于发生过卸载；缺少逐请求 schema 清单与 token 差，无法量化收益 |
| Skill 正文按需加载 | 没有技能激活或资源读取调用 | 该行为未覆盖，不能量化正文卸载收益 |
| Memory 按需路由 | 18/18 决策为 `none`，候选均为空；无记忆读取调用 | 没有强塞无关记忆，但也没有非空记忆对照，不能估算节省量或检索正确率 |
| Reasoning 作用域收窄 | 持久历史仅 1 条有 reasoning 的非 Tool Call 助手消息，且其后无 API 响应 | 无法从主样本计算可归于该机制的后续请求节省；不能把 reasoning 输出量算成已削减输入量 |
| 工具协议修复 | BN 异常收尾补 1 条缺失 Tool Result，没有丢弃孤儿结果 | 是配对修复，会补信息；不能算 token 削减 |

回执与源码实现共同支持一次性交付机制已被使用，但本批次没有保存每次实际发送的完整请求，
所以不能像专门的上下文效率夹具那样报告实测 `replayed_reference_tokens=0`。
Astropy 的读取返回了完整 9,878 字符文件；SAM 两次只取 260 和 160 字符，后者主要是版权头。
这说明“调用成功”与“证据读取有效”还需要分别评估。

大文本编辑处理的是百万行输入，但 24 次模型响应的输入峰值仅 32,581 tokens，外置事件为零。
工具在环境内处理文件并返回较小结果，可以直接减少进入上下文的信息量；没有全量输出对照，
不能把这种源头处理的收益算到摘要压缩上。

## 5. 对交付失败的影响与改进顺序

主样本有 **6/18** 个运行返回过 `finish_reason=length`，六次都恰好输出 **8,192 tokens**：
heap、SymPy、chess、DNA、code-from-image、largest-eigenval。
最后一题的长度响应在官方停止后才返回；其余五题在官方结束前发生。
这些是模型输出长度限制，不能记作输入上下文溢出。主样本没有输入溢出恢复事件，
因此这批数据不支持“把压缩阈值调低就能解决这些中断”的结论。

根据现有证据，后续改进可按以下顺序验证：

1. **优先验证压缩摘要的协议兼容与后续请求。** 验收同时要求摘要安装、下一次正常请求成功、
   关键事实保留、最终产物通过；只看 `compaction.completed` 会漏掉 Chess 暴露的问题。
2. **检查异常收尾的请求构造和缓存。** 对同一终止状态比较前缀变化、未命中输入与总结质量，
   验证是否能缩小收尾上下文并保留可复用部分。7 次收尾已贡献 17.13% 的未命中输入。
3. **减少小结果的重复引用说明。** 保留必要的可恢复引用，验证短引用/集中说明是否降低每条
   小输出的固定开销。还需检查可发现性和引用读取行为，不能只优化字符串长度。
4. **加强有目标的引用检索。** 分开记录回读成功、命中任务所需证据、重新读取次数；
   用相同问题对比 query 与分页，本批次的 0 次 query 尚无法说明其实际收益。
5. **补齐逐请求观测。** 记录组装前后各层 tokens、schema 卸载量、外置与回执替换量、
   缓存 hit/miss 和阶段，以及压缩后第一请求状态。累计净节省、压缩回本轮数和语义保真，
   需要完整请求记录或同工作负载对照；本报告没有用局部字符差替代这些指标。
