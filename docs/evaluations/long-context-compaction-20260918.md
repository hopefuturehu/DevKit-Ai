# 96K / 256K / 512K：thinking 与压缩发布实验

日期：2026-09-18。本轮使用 gaming 的冻结真实历史，测试前缀摘要沿用 thinking、独立
摘要开启与关闭 thinking 的差异，并检查生成、预算、发布和早期用户输入保留。

**主矩阵中，a_prefix 开启 thinking 为 9/9 发布成功，a_isolated 关闭为 9/9，开启为
8/9。加上 96K 诊断，共 33 次摘要、32 次发布；另有 21 次预热。全部 15 次前缀摘要
新增 reasoning 都为 0，显式开启和局部措辞调整均未改变这一现象。**

唯一失败是 API 正常 stop、只返回 5010 个推理 token、正文为空；没有发生 length
截断，因此本轮仍不能证明长推理耗尽输出预算的风险已消除。还发现摘要来源范围串入
和部分要求在摘要正文中省略的问题。原始用户锚点在全部 32 个已发布样本中逐字保留。

[逐请求机器记录](../data/long-context-compaction-20260918.json)包含请求哈希、API usage、
发布结果、变量核验、缓存预热记录和定向内容核对。

## 数据和控制

来源为 gaming Run `85cab45ef30f4a39afa27218b73afc13`、Session
`a992ba7c14a94eb58cc1305c522b7071`。原数据库仅以 SQLite `mode=ro` 读取，包含 1000 条
原始消息，其中 458 条 assistant 消息带非空历史 reasoning。

冻结同一任务的三个连续前缀，按完整工具调用与结果的边界选取；没有重复日志、补写
推理或读取项目新文件凑长度。保留原首次压缩快照中的 system、环境、Skill 目录及工具
定义，组合原始消息构造实验请求。这是重建请求，不是声称生产曾发送过 512K 请求。

| 标称长度（K=1024） | 追加摘要指令前本地 tokens | 原消息数 | 摘要覆盖末位置 | 历史 reasoning tokens |
|---|---:|---:|---:|---:|
| 96K | 97,974 | 126 | 122 | 23,898 |
| 256K | 261,266 | 359 | 355 | 57,104 |
| 512K | 524,375 | 819 | 807 | 115,761 |

长度来自仓库固定版本 DeepSeek V4 tokenizer，实际 API 路由返回 `deepseek-flash`；
最终计量以 API usage 为准。前缀路径还会追加摘要指令和覆盖映射，独立路径会将证据
序列化为 JSON，因此同一档不同路径的实际输入长度不同。

保留尾部以约 4K 原生 token 为目标并在工具组边界取整，再由生产 select_boundary
核验恢复预算。这不是生产默认约 20K 的尾部策略；本轮专门控制保留尾部，避免其变化
与摘要生成的失败混在一起。

三档所处任务阶段分别为平衡调整、游戏展示层实现、E2E 调试。它们来自同一嵌套历史，
任务状态和证据也随长度变化，不能将所有差异单独归因于 token 数。

## 请求矩阵

主矩阵：3 档 × 3 次重复 × 3 条路径，共 27 次摘要请求。

| 组别 | 请求组织 | thinking |
|---|---|---|
| `prefix_enabled` | 原生消息及工具定义，追加生产摘要指令 | 主请求及预热先设 enabled，再由 a_prefix 继承 |
| `isolated_enabled` | 生产 a_isolated 的 system＋历史 JSON＋尾部提醒 | enabled |
| `isolated_disabled` | 与上一组逐字段相同 | disabled |

即使前缀成功，也强制单独测试两种独立摘要。关闭 thinking 只控制新生成的推理；
独立摘要 JSON 中原有的历史 reasoning 保留，避免同时改变证据。

同一档的摘要覆盖范围相同，但前缀请求还能看到范围之外的保留尾部，独立请求只收到
范围内证据。原生历史 / JSON、角色和工具定义也不同，所以两路径差异不能单独归因
于某一字段；主矩阵中的独立 enabled / disabled 对照才是只改变 thinking 的比较。

96K 另加两个诊断条件，各重复三次，共 6 次摘要：

- `prefix_default`：与 enabled 组只差 thinking 参数省略。
- `prefix_neutral`：保持 enabled，只将尾部的“直接输出完整摘要，不解释筛选过程，
  不调用工具，不继续原任务。”替换为“输出完整摘要，不调用工具，不继续原任务。”
  其他摘要规则（包括只写结论的要求）保持不变。

所有路径固定输出上限 8192，显式不修改 reasoning_effort。gaming 原生产前缀的
max_output_tokens 为空；本轮增加 8K 上限，因此不是对原 10 次压缩的逐字节重放。

实验配置窗口 1,000,000、输入预算 900,000、低水位 40,000、单次超时 300 秒；同时统计
90 秒以内的发布率。源会话、生产配置和生产 thinking 策略均不修改。

每条路径只有一次生成机会。前缀专项失败时抑制真实兜底，以便单独计算失败率；独立
专项跳过前缀。链路衔接另以离线可控失败验证，不将强制专项冒充自然发生的兜底。

## 预热、费用和隔离

前缀请求使用原生主请求预热，保留模型、tools、temperature、thinking、输出额度和
历史消息；摘要只追加尾部指令。每个长度、重复和 thinking 条件最多预热两次，相邻
预热及摘要前等待 8 秒，缓存命中率达到 95% 记为预热合格。即使未合格，仍保留测试
结果并单独标识，不把它算作热缓存条件。

预热返回的工具调用仅记录，整个实验不存在工具执行器。默认 / enabled 诊断的次序、
独立 enabled / disabled 的次序交替；独立路径不强行预热，冷、热状态另记。

最多 60 次 API 请求、保守累计预留最多 10 美元，每次按全部输入未命中及输出用满
计算，不释放失败请求的预留。实际费用按 usage、请求时段和当日 Flash 价格估算，
不是账户账单。[官方模型与价格](https://api-docs.deepseek.com/quick_start/pricing/)

首次自动审批因历史外发范围不清而拒绝，未发出请求。随后核验 gaming 原配置与本次
实验使用同一官方端点、同一模型别名及凭据；冻结文件不含已配置密钥，常见凭据模式
扫描为零。补充证据后获准执行。真实测试只读取已检查并校验 SHA256 的冻结文件。
模式扫描不是无敏感信息的形式证明。完整请求、响应和原文仅留在忽略的 artifacts 目录。

## 校验口径

- **候选通过**：正常结束、正文非空、八章节完整、没有工具调用；length 一律拒绝。
- **发布通过**：实际调用生产 StrategyCompactor.compact，完成来源校验、恢复请求预算
  和工具协议检查，在每次独立 SQLite 测试库中发布，随后重新读取活动检查点。
- **状态保留**：已发布样本逐个验证原始用户消息逐字存在、保留尾部逐条相同；失败样本
  验证游标保持 0、没有活动摘要。所有路径使用相同覆盖边界。
- **信息质量**：八项用户要求的关键词检索与选定事实的定向人工检查分开报告；检索
  命中不等同于语义正确，结构通过也不等同于全量事实无损。

历史 thinking 的存在、参数 enabled、新生成 reasoning 非零，以及发生推理截断，分别
记录。若前缀生成 reasoning 仍为零，不把成功率解释为该路径长推理截断问题已解决。

## 结果

### 主矩阵：实际发布与新增推理

候选通过数与发布通过数相同，没有“正文合格但恢复预算或发布失败”的样本。
下表耗时为单次摘要请求均值，包含失败样本，不含预热。

| 档位 | 路径 / thinking | 发布成功 | 三次新增 reasoning tokens | 三次正文 tokens | 平均秒数 |
|---|---|---:|---|---|---:|
| 96K | prefix / enabled | 3/3 | 0、0、0 | 3573、4697、4350 | 20.0 |
| 96K | isolated / enabled | 2/3 | 3356、0、5010 | 3384、3426、0 | 24.8 |
| 96K | isolated / disabled | 3/3 | 0、0、0 | 3318、2841、2999 | 15.9 |
| 256K | prefix / enabled | 3/3 | 0、0、0 | 5587、3534、4141 | 21.5 |
| 256K | isolated / enabled | 3/3 | 3157、2285、1656 | 2979、2930、2993 | 26.2 |
| 256K | isolated / disabled | 3/3 | 0、0、0 | 2643、3498、3486 | 16.6 |
| 512K | prefix / enabled | 3/3 | 0、0、0 | 3161、2648、2560 | 17.6 |
| 512K | isolated / enabled | 3/3 | 0、0、0 | 3020、2456、2136 | 19.1 |
| 512K | isolated / disabled | 3/3 | 0、0、0 | 2365、1812、2360 | 17.2 |

关闭 thinking 的独立摘要在本轮全部可发布、平均耗时更短；开启组有一次空正文失败。
每格仅三次且来自同一任务，不能将这些比例当作稳定的长期成功率或证明关闭没有质量
损失。512K 并没有比 96K 产生更多新增推理，长度不是本样本中推理量的单调决定因素。

实际 a_fallback 在这九次主前缀成功后不会进入第二段；上表独立路径为强制专项，
不代表观察到了九次自然兜底成功。

### 96K 诊断：零推理没有被这两项调整消除

| 前缀条件 | 发布成功 | 新增 reasoning | 平均秒数 |
|---|---:|---|---:|
| thinking 参数省略，原提示 | 3/3 | 全部 0 | 19.0 |
| 显式 enabled，原提示 | 3/3 | 全部 0 | 20.0 |
| 显式 enabled，删除末句两处措辞 | 3/3 | 全部 0 | 22.2 |

已核对实际 HTTP payload：enabled 未被客户端改写成 disabled；省略参数的请求也没有
被补成 disabled。三组仅改变预先声明的变量。21 次原生主请求预热全部产生非零推理，
而在前缀后追加摘要指令的 15 次请求全部为零。这支持“当前模型在这种前缀交接请求下
直接返回摘要”的观察，不能证明其服务端内部为何如此选择。

本轮不支持“只是没显式 enabled”或“只要删掉直接输出/不解释这两处文字就能恢复推理”
这两个解释。它也没有隔离整套提示、角色布局、工具定义和历史推理的各自贡献；不能
声称已确定某个单一根因，更不能把输入缓存命中解释成新增推理必然被省略。

### 唯一失败与未覆盖风险

`96k-r3-isolated_enabled`：输入 103133，输出 5010，其中 reasoning 5010、正文 0；
API 返回 `finish_reason=stop`。流诊断记录 reasoning 14466 字符、正文 0 字符，没有
未识别的 delta 字段。运行器报“上下文压缩模型没有返回摘要”，保持游标 0、没有发布
活动检查点。不是客户端漏存正文，也不是已观测到 8192 额度耗尽。

全部 33 次摘要 finish 都为 stop，最大单次输出 6740；其中五次有非零 reasoning，
只有这一次超过输出额度的 50%。**没有真实 length 样本，也没有真实前缀长推理样本。**
离线 length 注入只验证拒绝与兜底链路，不能替代真实模型截断概率测试。

### 原始要求保留与内容质量

32/32 已发布检查点重新恢复后：原始 1175 字符用户消息逐字存在，保留尾部逐条相同，
恢复请求预算计数为 12684～17201，均低于 40000。失败样本原文与游标保留。

摘要本身仍存在以下问题，来源位置与样本哈希在机器记录的 quality_review 中：

1. **摘要混入保留尾部。** 96K 声明仅覆盖 1～122，但九份前缀摘要均写入第 124 条
   工具结果“三关满生命通关、canyon 327s、corridor 443s”。256K 覆盖至 355，该位置
   实际报 theme.ts 目录不存在；三份前缀摘要却使用尾部 357、359 的结果，称 theme、
   format、audio 文件已落盘。这些结果在完整历史中真实存在，问题是超出了摘要声明
   的来源范围；源哈希、章节和预算检查不会检测这种语义越界。
2. **正常模式试玩要求容易被省略。** 独立关闭组九份摘要均未匹配“正常/普通/非测试
   模式”字样；人工检查 `96k-r1-isolated_disabled` 确认其保留了固定种子/测试模式，
   却漏掉独立的正常模式试玩要求。关键词探查不是九份语义遗漏的完整判定；其他模式
   也有遗漏。这项原始要求仍在恢复后的 user 锚点中，没有从整体上下文消失。
3. **验证状态的措辞不一致。** `512k-r1-prefix_enabled` 将 5 passed / 2 failed 的
   Playwright 运行放在“已完成并通过验证”条目中，同时又在 Failures 写明两项失败。
   后续续跑仍需以具体测试结果为准。

这是选定事实的定向检查，没有给出全量事实准确率，也没有执行游戏任务的后续验收。
本轮保存、恢复了摘要与原始消息，没有重建并运行全部工作区工具和外置附件读取链路，
因此发布成功率不等同于任务续跑成功率。

### 实际输入、缓存与成本

| 档位 | prefix 实际输入 | isolated enabled / disabled 实际输入 | prefix enabled 输入缓存命中率 |
|---|---:|---:|---:|
| 96K | 101592 | 103133 / 103108 | 99.79% |
| 256K | 269081 | 290998 / 290973 | 96.71% |
| 512K | 540470 | 598737 / 598712 | 96.58% |

96K 默认组输入 101592，措辞组 101586。12 个预热条件全部达到 95% 门槛，共用 21 次
请求；15 个前缀摘要逐个核验与其预热请求的消息前缀和其他参数一致。

独立摘要两种 thinking 的首次调用命中分别约 0.74%、0.26%、0.13%（对应三档），重复
后接近全命中，三次加权约 66.7%。96K 诊断间也共享了相容缓存；这些数字包含实验
冷热顺序，不能直接当成生产长期成本比例。

北京时间 **14:36:08～14:53:44**，真实请求阶段共 **17 分 35.412 秒**，其中 Provider
时间累计 872.848 秒，预热后固定等待 168 秒，其余为本地校验、发布和序列化等开销。
全部摘要请求均在 90 秒内返回，最大 31.376 秒；90 秒内发布数仍为 32/33。

54 次请求累计输入 **14872773**、缓存命中 **10152576**、输出 **156600**（已含推理
25761）tokens；usage 全部完整、无传输错误、无自动重试、无工具执行。全部输入冷缓存
且用满输出额度的累计预留为 **$5.227137**，按实际峰时 usage 估算 **$1.664894556**。
