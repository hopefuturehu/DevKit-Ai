# 前缀摘要一次 + 独立摘要兜底：32K 实测

日期：2026-09-11。实现冻结在 `b390981`，新策略为 `a_fallback`，默认仍为 CURRENT。
本轮包含原 A32 首次失败断点的三组重放，以及同一道 `path-tracing-reverse` 的完整重跑。
[机器可读数据](../data/compaction-prefix-fallback-results.json)、[具体设计](../designs/compaction-prefix-fallback-design.md)。

**结果：断点的可发布摘要率提高，完整运行也未再出现摘要工具调用或重新装箱，但整题
只通过 2/3，低于上轮 A32 的 3/3；本轮没有证明任务效果或总费用更好。**

## 实现和测试口径

实际 AgentRunner 已接入两条路径，并非另写一个仅供评测的摘要器：先复用真实出站请求
快照、完整追加已结束的工具往返和摘要指令；失败后，用专用摘要 system、JSON 历史数据
与空工具列表再请求一次。两条路径各至多一次，校验通过后才发布，失败工具调用不会执行。

| 配置 | 旧 A32 | 新 a_fallback |
|---|---|---|
| 主模型 | deepseek-v4-pro | deepseek-v4-pro |
| 摘要模型 | 同主模型 | 两条路径均同主模型 |
| 主请求输出上限 | 32,768 | 32,768 |
| 前缀摘要输出上限 | 8,192 | 32,768，继承主请求 |
| 独立兜底输出上限 | 无此路径 | 8,192 |
| thinking / temperature | disabled / 0 | disabled / 0 |
| 摘要正文目标 / 硬上限 | 3K / 4K | 3K / 4K |

32K 指主模型单次输出额度，不是摘要正文目标。新后缀和前缀输出额度同时发生变化，
本轮没有单独分离这两个因素的贡献。独立路径不进入 CURRENT 的 60K 分块、格式修复
或多级重试循环；保留 A 的覆盖范围选择、完整请求低水位检查和原文回读。

修改后的 125 项相关单元/集成测试通过，Ruff 通过。覆盖成功只请求一次、工具调用/
空输出/缺章节/截断/断流后独立请求一次、双失败保留游标、取消/鉴权/配额不重试、费用
预检和源状态变化中止。真实 Agent 循环的集成测试确认原出站前缀和 32K 额度保持，
失败摘要中的 read_file 不执行，发布后继续主任务。

## 失败断点重放

输入复原自上轮 A32 的消息 1–70，三组都选择覆盖 1–40、保留 41–70。旧第一请求
3,914 tokens 和旧摘要请求 73,262 tokens 两个计数检查通过；原数据库只读且哈希不变。
原 HTTP 请求未保存，所以这仍是重建断点，不能声称恢复了原始 HTTP 字节。

每组独立重复三次、固定随机顺序、串行请求，没有人工预热。压缩器和发布逻辑使用上述
运行时代码；只读摘要重放没有工具执行器，真实续跑另在 Harbor 中检验。

| 指标，三次事件合计 | 旧 A | 双路径 | 直接独立摘要 |
|---|---:|---:|---:|
| 通过校验并发布 | 0/3 | 3/3 | 3/3 |
| 模型请求数 | 6 | 4 | 3 |
| 前缀直接成功 | 0 | 2 | 不适用 |
| 独立兜底挽救 | 不适用 | 1，前缀超时后成功 | 不适用 |
| 请求返回工具调用 | 6 | 0，另有一次无完整响应的超时 | 0 |
| 每次事件平均耗时 | 11.49 秒，均未得到摘要 | 56.51 秒 | 21.12 秒 |
| 完整 usage 数 | 6/6 | 3/4 | 3/3 |
| 统一峰时费率下的已知费用 | $0.026869 | ≥ $0.031252 | $0.087515 |

旧 A 六次响应为两次 update_plan、四次 run_shell。后者准备通过 Python struct 解码
已有十六进制常量，包括 `0x485adc`；仍在继续原任务，没有生成交接摘要。命令均未执行。

双路径第一轮前缀请求已返回 1,708 个文本 delta、4,781 字符的摘要正文，但流未结束，
在 90 秒达到超时，没有 finish/最终 usage。随后独立请求用约 26.55 秒成功，整个事件
约 116.56 秒。这不是“模型没有开始摘要”，也没有输出额度触顶的证据；无法仅凭日志
确定后续延迟来自服务端还是网络。费用不能记为零。第二、三轮前缀直接成功，分别约
27.82 和 25.16 秒。

成功后完整请求的本地预算占用为：双路径 31,851–32,003 tokens，直接独立摘要
31,388–31,780 tokens；压缩前同状态为 76,766。这里是带余量的本地预算，不是续跑 API
实测输入，也不能用它计算纯摘要文本的压缩率。

## 缓存与费用不能怎样解读

- 两次有完整 usage 的新前缀请求均为输入 74,921、命中 74,880，命中率 **99.95%**。
  三轮重建请求的前缀、工具和其他请求参数一致性检查通过；超时的第一次命中率未知。
- 独立摘要首次输入 49,108，命中为 **0**。后续相同独立请求为命中 49,024 / 49,108，
  即 99.83%；这是重复摘要输入自己的缓存，不是复用主任务历史前缀。
- 因此双路径整组已知输入命中率 99.92%、独立组 66.55% 都受重复请求与缺 usage 影响。
  不能据表中的费用宣称双路径稳定节省某个百分比。旧 A 虽便宜，但没有交付摘要。
- 使用冻结于 2026-09-10 的统一比较费率：命中/未命中/输出为 $0.044/$1.32/$3.96 每百万
  tokens，金额是 usage 重算值，不是账单。

## 内容质量：结构成功不等于事实完全正确

抽查六份已发布摘要，均保留 mystery.c 目标、静态编译命令、gzip <2k 约束、800×600
P3 输出格式。这只是四项定向检查，不是完整事实保留率评估。

同时发现三个问题：

1. 两份前缀直接生成的摘要都写入“已创建第一版代码、gzip 1444 bytes”。该证据来自
   原文 56–57，位于保留尾部，超出 1–40 的摘要归并范围。追加的索引映射没有阻止尾部
   内容进入摘要。这是重复与溯源边界问题；原始尾部仍保留，没有因此被提前删除。
2. 四份由独立路径生成的摘要中，三份沿袭消息 39 的错误解读 `0x485adc=0.0f`。
   范围内的工具消息 38 已有 `485ad0 ... 0000803f`，支持该地址为 1.0f；保留尾部的
   消息 70 又给出相同字节。因此这里不是缺少证据，而是摘要采用了历史助手的错误解释，
   没有处理它与工具证据的冲突。独立角色能控制行为，但不会自动证明历史说法正确。
3. 两份前缀摘要虽读出了 `0x485adc=1.0f`，但正文中仍混有半径 1.0 与 2.0 的矛盾描述。
   八章节、长度和版本校验无法验证这些语义冲突。

本轮准确结论是“提高了这个断点的可发布摘要率，并实际挽救一次超时”。尚不能将其写成
“事实准确率 100%”或“完全解决摘要时继续任务”。后续需要将事实检查、重复取证与任务
验收和摘要结构成功率分开统计。

## 本轮可以采用的结论

- 新实现确实改善了这些样本中的摘要行为：重放旧 A 六次都调用工具，新方案能发布；
  完整任务四次已结束的摘要均一次成功，并避免了本轮输入重新装箱。
- **不能据此选定为全面优于旧 A。** 本轮更长时间运行后只通过 2/3；已知费用没有降低。
  上轮在非峰时、本轮在峰时，费用比较必须统一费率，不能直接拿 $0.737853 与 $1.505814
  做算法成本比较。两边均有未知 usage，实际费用差额也不能精确确定。
- 本轮 108 个进展标签中有 105 个 weak、3 个 none。这是运行器启发式标签，不等于
  105 步全无价值，但压缩成功显然没有自动解决持续探索与任务收敛问题。
- 下一步优先验证摘要中的事实冲突与尾部重复，再做同断点短续跑和完整任务配对重复。
  单个断点、单次完整轨迹不能证明图像失败由压缩造成，也不能证明结构成功会提高验收率。
  保留 `a_fallback` 为可选策略，默认策略不变。
