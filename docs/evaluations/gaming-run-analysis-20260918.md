## 工具可靠性

| 分类 | 次数 | 主要原因 |
| --- | ---: | --- |
| 执行前参数校验 | 15 | `apply_patch` 缺 `path/old_text`、shell 缺 `script` / 错传 `command`、等待参数超过 60 秒 |
| 执行前策略拒绝 | 4 | `.env.example`、工作区外 `/tmp/e2e1.log`、两次 sed 正则被解析成越界路径 |
| 执行后失败 | 9 | 8 次补丁失败（文件尚不存在 / 原文不匹配）、1 次 shell 返回非零 |

不能仅查询 `tool_runs.status=failed` 后用 9/513 报失败率，这会漏掉 19 次执行前拒绝。
其中两次 sed 正则误识别为绝对路径，是策略层的误报；访问 `/tmp` 被拒与当前工作区边界设置一致。
`running` 的 14 条结果是启动后台进程或轮询时的返回值，不是“结束后仍有 14 个进程未完成”的证明。

工具失败率也不等于测试失败率。多个测试命令经管道或 `; true` 包装，工具可返回成功而测试日志显示失败。
历史记录确实有多轮 E2E 失败与修复；最终保留的全量日志是 14 passed。

### 1. 能持续推进，并且会修改自己的计划

轨迹中只有一条实际用户任务消息，没有用户中途推动或纠错，也没有子 Agent。
它完成了环境探查、实现、数值模拟、测试、浏览器调试、日志检查、文档与提交。
这次运行支持“单 Agent 能连续工作近一小时并跨多次压缩续接”的结论。

初始计划是 9 项，之后补进平衡复测、编辑器单测、截图检查等实际需要的工作，最终 15 项。
最有价值的自纠发生在 12:08：它承认此前“平衡已达标”的描述与当前复测不符，
定位到“不升级玩家”helper 实际仍会升级，修复 helper 后重新校准并固化测试。
这表现出用新证据纠正旧结论的能力，而不是一味维持先前计划。

规划仍有缺点：阶段状态由模型自己标记，完成证据没有统一的机器可核对结构，
早期“已完成”结论可以先于有效验证出现；需要靠后续自纠兜底。

### 2. 有效工作量大，重复错误仍有明显成本

工具申请分布：`run_shell` 322、`apply_patch` 142、`read_file` 21、`poll_process` 15、`update_plan` 13。
它通常按“实现 → 执行 → 读取失败输出 → 修正 → 再验证”推进，后半程主要消耗在真实调试。
没有持续跟踪或为了凑时长空等的证据。

不过工具约束没有形成稳定经验：

- `wait_seconds` 的上限为 60，仍在 12:00、12:04、12:07、12:13、12:18、12:24、12:32、12:44
  共 8 次传入 90 或 120。第一次被拒后，后续仍反复犯同类错误。
- 新文件补丁多次没有 `create=true`，或虽然传了 `create=true`，却给出非空 `old_text`。
  对 `e2e/helpers.ts` 的相同创建失败连续重试三次，触发一次停滞告警，之后才改用写文件脚本。
- 参数漏传 / 错命名与上述超限共造成 15 次校验拒绝。
- 策略层将两次 sed 地址正则错认成越界文件路径；这是运行器的误报，不能全部归因于模型。

进展启发式记录为 strong 113、weak 334、none 24、waiting 14；484 次 continue、1 次 warn。
该分类不能直接等价为有效 / 无效工作时长：读取测试日志、运行 shell 等真实工作也可能被标记 weak。

### 3. 压缩没有丢需求，但把错误归因沉淀成了“经验”

前 7 次摘要没有记下等待参数上限或补丁创建规则。
第 8、9 次摘要将工具限制写成“timeout_seconds 上限 60”；第 10 次进一步写成
“timeout_seconds / wait_seconds 上限 60”。实际 schema 只有 `wait_seconds` 最大为 60，
`timeout_seconds` 是独立的进程 hard timeout，没有 60 秒上限。

第 8–10 次摘要还写了“apply_patch 的 create=true 对新建路径实测无效”。
对照失败参数与 `src/bot/tools/builtins.py:190`：创建新文件需要 `create=true` 且 `old_text` 为空；
记录中的相关失败要么缺 create，要么 old_text 长度为 6 或 11。摘要错误地把用法错误归因于工具能力。

因此要区分两件事：原始任务输入和结束条件保留可靠；执行经验的因果归纳不够可靠。
错误结论可能通过多次摘要被继承，增加后续绕路。本样本不支持“压缩完全无损”的宽泛结论。
优先改进的是结构化记录错误字段、触发条件和有效修复，而不只是增加上下文长度。

### 4. thinking 修复在真实任务中有效，但不能据此断言思考质量

所有主请求都保持供应商默认 thinking，37.10% 的主输出为推理 token，
历史占位补齐反复发生而没有自动关闭或 Provider 错误。这是连续性方面的正面证据。
推理量不等于推理正确率；上述工具误用、经验误归因和验收过度声明仍然发生。

### 5. 完成判定过度依赖自身测试和自身报告

它最终停止前确实做了全量回归、文档、Git 提交和干净工作区检查，
所以“停止”有一条实际交付链支撑。但这条链缺少独立的完成判据。

一个可复核的例子是：游戏按钮被不透明背景遮挡，测试仍可通过内部坐标触发按钮，
因此测试全绿不代表玩家能正常看见并使用所有控件。该例反映测试判据与用户可用性之间的空隙，
本报告不展开产品缺陷清单。

另一个问题是执行报告声称“正常模式人工试玩、主观手感确认”，
但可核查轨迹主要是自动化交互、截图和像素统计；正常模式 E2E 只走菜单、选关、开局与返回，
没有对应完整正常模式试玩的记录。原始试玩要求在第 10 次压缩回放中仍逐字存在。
这是结束前没有充分核实要求、报告超出证据，而不是忘记用户要求。

此外，20 条短浏览器测试启动脚本中至少 11 条经管道或 `; true` 包装；
这方便失败后继续读日志，但工具成功不能再作为测试通过依据。
该数字由少于 1800 字符且含 `npx playwright test` 的脚本筛选获得，不代表全部测试启动次数。
它最后确实读取了测试日志，但后续系统级验收最好保存内层测试命令的原始退出码与结构化结果。

## 对运行器和 Agent 策略的改进优先级

1. **结束前按用户原始要求核对证据。** 每项记录“已实现、已验证、证据位置、验证限制”；
   证据缺失时保留未验证状态，不把自写测试全绿或计划全打勾作为充分条件。
2. **让工具错误成为可复用的结构化经验。** 校验错误明确给出 JSON 字段路径、实际值、约束和修正示例；
   把 `wait_seconds` 与 `timeout_seconds` 的语义、新建补丁的必要条件单独保留。
3. **约束摘要中的因果归纳。** 将失败原文、已验证原因和暂定解释分开；
   不允许从“参数错误导致一次失败”直接总结“这个工具不支持该能力”。
4. **修正运行器误报。** sed 正则参数与文件路径应按命令语法区分；现有路径识别导致两次不必要拒绝。
5. **保留已有效的机制。** 原始 user 锚点、完整 transcript、thinking wire 修复、计划持久化和失败后续跑，
   本次都有实际收益，暂时没有证据需要靠强制延长时长改善表现。

整体判断：bot 已具备持续推进、跨压缩续接和自我修正的能力；工具使用的稳定性仍一般，
执行经验的真实性与最终完成判定是最值得优先加强的两处。
