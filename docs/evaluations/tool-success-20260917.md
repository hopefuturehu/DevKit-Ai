# 历史工具执行成功率与失败归因

采集时间：2026-09-17 14:26（北京时间）。只读分析主库 `.bot/state.db`，调用时间覆盖
2026-07-17 17:11 至 2026-09-17 11:55。结果基于冻结快照，不代表当前版本的独立可靠性测试。

**常规工具终态执行成功率为 96.41%；补齐执行前失败和内置工具后，整体终态调用成功率为
94.18%。** 75 次失败中，权限限制与调用方式/参数/结构假设问题共 58 次，占 77.33%。
记录更支持优先改善调用规划、参数检查和失败反馈；不能把所有失败都归为工具实现故障。

## 统计范围与口径

主库共 40 个会话、133 个 Run，其中 20 个会话、90 个 Run 产生了工具请求。
不混入 `artifacts/`、`.bot/benchmarks/` 下的独立评测、合成工作负载、历史回放和导出副本。
本报告因此是**主会话库历史**统计，并非所有公开基准执行的合并结果。

| 口径 | 成功 | 失败 | 返回 running | 无结果 | 成功率 |
|---|---:|---:|---:|---:|---:|
| 常规工具执行表，共 1,235 条 | 1,182 | 44 | 9 | 0 | **1,182 / 1,226 = 96.41%** |
| 全部请求，共 1,302 次 | 1,214 | 75 | 9 | 4 | **1,214 / 1,289 = 94.18%** |

成功率分母为有终态的调用；9 条 `running` 和 4 条缺少返回的请求单列。若以全部请求为
分母，“已确认成功占全部请求比例”为 1,214 / 1,302 = **93.24%**，它是另一种指标。

核算方法：

- 以 `(session_id, run_id, tool_call_id)` 合并同次调用的 `tool.requested`、`tool.completed`、
  `tool.result` 与执行表，不能将 1,235 条 completed 事件与 382 条 result 事件相加。
  不同调用 ID 的重试保留，衡量每次尝试的结果。
- 按 `success` 与 `status` 判断。`tool.completed` 是事件名称，不能仅凭事件名认定成功；
  `success=true, status=running` 也不能视为任务执行完毕。
- 执行表以外的 67 次请求为：32 次内置检索/读取成功、31 次执行前失败、4 次无返回。
  因此 `1,235 + 32 + 31 + 4 = 1,302`。
- 老版本缺少统一 result 事件，50 次调用依据历史 Tool 消息恢复：21 成功、29 失败。
  其中 8 次成功正文已截断，只能依照已知成功返回外壳推断；其余 11 次内置成功和 2 次
  执行前失败有结构化事件。96.41% 的执行表口径不依赖这项旧文本推断。
- 4 次无返回均为 `run_shell`：所属 Run 中 1 个已取消、3 个历史状态仍为 running。
  不能据此判为工具失败，也不能认定它们现在仍在执行。

9 条 running 来自 6 个进程的启动/轮询收据，不是 9 个当前活跃进程。后续记录中可找到
4 个进程被主动终止、1 个进程完成；其余 1 个在本次读取的工具结果中没有终态。
终止/轮询本身是独立调用，不能将后续进程状态回填多次后再混算工具调用率。

## 75 次失败的逐条归因

每次失败按一个主要原因计数，来自参数、错误信息和输出的人工审阅；不是自动因果推断。
完整调用标识及类别保存在[数据附件](../data/tool-success-20260917.json)的 `attribution` 中。

| 主要原因 | 次数 | 失败占比 | 具体证据 |
|---|---:|---:|---|
| 权限或路径限制 | 30 | 40.00% | 工作区外路径 19；用 `run_command` 包装 `shell -c` 被拒 6；敏感路径 2；内部 memory 路径保护 3 |
| 工具、参数或脚本用法错误 | 13 | 17.33% | 把管道符放进 argv 4；`wait_seconds=120` 超上限 3；不存在的 `list_files` 1；反向行区间 1；Python 脚本/API 使用错误 3；shell 语法错误 1 |
| 数据库或代码 API 假设错误 | 10 | 13.33% | 查询不存在的表/列 9；导入不存在的 `RunStatus` 1 |
| 探测或搜索未命中 | 7 | 9.33% | `grep` 无匹配 3；`which` 有命令未找到 2；`lsof` 无监听和 `ps` 无目标各 1 |
| 代码检查或测试未通过 | 5 | 6.67% | Ruff 报问题 3；WebSocket 测试/探针退出抛 `CancelledError` 2 |
| 文件不存在或创建方式不符 | 5 | 6.67% | 读不存在文件/数据库 2；对不存在文件调用 patch 且未指定创建 3 |
| 网络请求失败，细分原因缺失 | 3 | 4.00% | GitHub 请求只记录“网络请求失败: ”，未保存异常类型，无法区分超时、DNS、TLS 等 |
| 环境变量缺失或端口占用 | 2 | 2.67% | `BOT_MODEL_API_KEY` 未设置；8080 端口已占用 |

执行前的 31 次失败为 27 次策略拒绝、3 次参数校验失败、1 次未知工具；其余 44 次进入了
执行表。内部 memory 路径保护的 3 次是在 `read_file` 内返回失败，因此归于权限原因，
但没有计入“执行前 31 次”。

几个能直接指导改进的例子（编号为 `tool_runs.id`）：

- **#52、#76、#161、#653**：`find` 的 argv 内含 `|`，报 `unknown primary or operator`。
  模型混淆了 argv 执行与 shell 语法；另有 6 次通过 `sh -c` 调用被策略拒绝。涉及管道时应
  使用显式 `run_shell` 并接受相应策略检查。
- **#226、#230、#231、#242、#246、#248、#769、#965、#996**：SQLite 报不存在的表/列。
  应先读取 `.schema` / `PRAGMA table_info`，再按实存字段生成查询。
- **#308**：`start_line=280, end_line=200`；**#363、#934、#935**：patch 目标不存在，参数未
  指定 `create=true`。这些可以用明确的参数反馈和先检查目标状态减少重试。
- **#519、#650、#831 等**：搜索无结果、部分命令缺失、端口未监听。这些非零退出有诊断
  价值，不能直接解释为执行器损坏；#519 的搜索表达式还有转义问题嫌疑，不能反推目标
  内容实际不存在。主成功率仍忠实保留原始失败状态，没有人为改记成功。
- **#348、#365**：WebSocket 探针与测试暴露退出清理异常；只能确认被测路径存在问题，
  不能仅凭该输出确定是应用、依赖兼容性还是测试写法所致。
- **#920**：shell 报参数展开未闭合；保存的脚本已脱敏，不能进一步还原原始表达式。

## 改进优先级与解释边界

1. **减少可预防的调用错误。** 强化 argv 与 shell 的使用示例；对非法等待时间、反向行范围、
   patch 创建方式给出可执行的纠正建议；数据库/API 使用前先检查定义。调用用法、结构假设
   和文件状态问题合计 28/75，约占失败的 37.33%。
2. **让权限边界更早进入规划。** 当前拒绝记录说明策略发挥了作用，不应为提高成功率解除
   保护。优先解释允许的路径和专用 memory 工具。`.env.example`、虚拟环境符号链接的边界
   是否符合产品意图，可单独审查；本次没有将这些拒绝自动认定为策略缺陷。
3. **改进结果分类与错误证据。** 将搜索未命中、检查发现问题、策略拒绝、启动中、执行异常
   分开报表。记录网络异常类型、阶段、耗时和重试次数，避免只有空错误字符串。
   不宜全局把退出码 1 视为成功，更不能靠追加 `|| true` 改善指标。

月度终态调用成功率（北京时间）：7 月 **94.57%（174/184）**，8 月
**92.37%（581/629）**，9 月截至采集为 **96.43%（459/476）**。任务、工具组合和版本均不同，
这里只作描述，不能据此证明某次代码改动提升了可靠性。

75 次失败分布在 15 个会话、29 个 Run，前三个 Run 占 35 次，约 46.67%；重复尝试并非
独立样本。一次 `run_shell` 可能执行多条命令，最终退出码也可能掩盖前序错误；高频读取
会提高调用层成功率。这些指标不能替代任务完成率、产物正确率或工具实现可靠性的专项测试。

## 复现与核验

[统计脚本](../../scripts/analyze_tool_success.py)通过 SQLite 只读事务采样，或读取冻结 JSON：

```bash
# 重算本报告的冻结样本（本地快照未纳入 Git）
.venv/bin/python scripts/analyze_tool_success.py \
  --snapshot .bot/analysis/tool-success-20260917/source.json \
  --output .bot/analysis/tool-success-20260917

# 采集主库当前状态，结果会随新增记录变化
.venv/bin/python scripts/analyze_tool_success.py \
  --database .bot/state.db --output .bot/analysis/tool-success-current
```

快照 SHA-256：`f2dc4a020aa3eb400088a864e13ad39e4ce8297bb0967bb889df9886cc671750`。
原始参数、输出留在忽略目录；入库附件只含汇总及失败标识/分类。脚本生成指标和本地逐调用
索引，不自动生成或推断人工根因标签。复查归因时可按附件的三元组定位事件，或按执行行 ID
定位原始结果。

核验包括执行表独立 SQL 汇总、事件/执行记录对齐、分工具与分月份加总、75 条人工分类
无遗漏/无重叠，以及脚本静态检查。样本不存在重复请求身份、孤立执行记录或结构化结果冲突。
本次没有重新执行历史命令或调用模型。
