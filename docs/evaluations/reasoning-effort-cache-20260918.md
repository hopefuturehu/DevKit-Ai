# reasoning_effort 切换与摘要缓存复用实测

日期：2026-09-18；用户希望核验截断后降低摘要推理强度是否损失缓存。本实验只验证输入
缓存行为，不修改生产 thinking、摘要恢复或 Provider 实现，不评价摘要续写成功率。

**本轮四个从默认或 high 切到 low 的条件，首次 low 均为 0% 命中；重复 low 后约 99%，
切回原设置也约 99%。旧缓存没有被清空，但此次 low 请求没有复用已预热的原设置前缀。**
仅追加相同形状的续写尾部、不改变 effort 的对照仍命中 99.05%。
逐请求证据见[机器记录](../data/reasoning-effort-cache-20260918.json)。

## 实验控制

- 使用当前工作区配置的官方 DeepSeek `deepseek-v4-flash` 别名，响应记录实际返回模型。
  thinking 字段始终省略，维持供应商默认；只在实验 Provider 子类中透传 `reasoning_effort`。
- 每个条件有独立的 system 起始 namespace；历史为约 24K tokens 的合成数据。
  前缀夹具保留工具定义、auto 选择及完整工具调用／结果；无工具夹具模拟独立摘要请求的形状。
  不发送用户任务正文，不执行任何模型申请的工具。
- 五个条件各五次请求：冷启动 → 同设置预热 → 切换／追加尾部 → 重复该请求 → 返回基线。
  相邻请求完成后等待 8 秒。冷启动命中 <5%、预热命中 ≥95% 才进入有效比较；
  最多允许两次额外预热，失败和缺失 usage 不自动重试。
- 三个原消息对照只改变 `reasoning_effort`；另外两个条件分别追加同形状的合成 assistant
  和 user 尾部，一组同时改 low，一组保持默认，区分参数与追加消息的影响。
- 生成上限固定 256，温度字段固定 0；要求短答以控制实验成本。没有用长思考或真实截断
  输出构造续写，因此不能用本实验推断推理质量或截断恢复率。尾部是预定义合成内容。
- 最多 35 次请求，按当日 Flash 峰时价格预留最多 $0.40；不释放失败请求的费用预留。
  密钥只用于已配置官方端点的认证，不写入请求产物或结果附件。

## 实测结果

25/25 请求正常结束为 `stop`，usage 完整，无错误、工具调用或额外预热。五个条件首次
请求均为 0% 命中，第二次均超过 99%，满足事先约定的有效预热标准。API 返回型号均为
`deepseek-flash`；服务端具体权重与缓存键实现不可见。

| 条件 | 切换前预热 | 首次切换／追加 | 重复切换后的请求 | 返回原设置与原消息 |
|---|---:|---:|---:|---:|
| 带工具，默认 → low，消息不变 | 99.16% | **0%** | 99.16% | 99.16% |
| 带工具，high → low，消息不变 | 99.16% | **0%** | 99.16% | 99.16% |
| 无工具，默认 → low，消息不变 | 99.09% | **0%** | 99.09% | 99.09% |
| 带工具，默认 → low，同时追加尾部 | 99.16% | **0%** | 99.05% | 99.16% |
| 带工具，保持默认，仅追加尾部 | 99.16% | **99.05%** | 99.05% | 99.16% |

前两个条件实际输入均为 24,010 tokens，切换前后没有变化；预热命中 23,808，
首次 low 命中为 0、未命中为 24,010。无工具输入为 24,026，行为相同。
追加两条尾部消息后输入为 24,037，保持默认时仍命中原来的 23,808 tokens。

已逐文件核验保存的 HTTP payload：前三个条件只改变 `reasoning_effort`，消息、tools、
tool_choice、输出额度等完全一致；尾部条件只有预先声明的追加和 effort 变化。
相同输入 token 数不证明服务端内部表示完全相同，但排除了客户端删减历史或工具造成的解释。
本轮结果支持 effort 切换影响缓存复用兼容性；不据此推定服务端缓存键的具体字段或编码。

每个条件只有一次首次切换，重复 low 是检查其自身能否缓存，不是独立重复试验。
本结论限定于此次官方 Flash 路由、账户、请求形状与时间；不能外推所有模型、未来版本和
任意上下文长度。它已足以否定当前场景中“只改 low 就一定保住原前缀缓存”的假设。

## 用量与验证

全部请求累计输入 600,438 tokens，命中 380,928、未命中 219,510；输出 353，
其中 reasoning 303。Provider 请求时间共 62.13 秒，实验另含人为等待，不将其计作模型延迟。
本轮不测试生成质量、长推理或输出截断，不能用这些短答推理量评价 low 的摘要效果。

按本次请求所在峰时和当日官方 Flash 价格，usage 估算费用 **$0.068562168**，不是账单查询值。
按每次全未命中及输出用满的本地预算累计预留 $0.1967148，低于 $0.40 上限。
包含人为冷启动的总体命中率不代表生产命中率。

离线预检、Ruff、编译检查通过；导出时核对脚本与请求哈希、仅声明变量变化、五组预热门限、
25 条 token 收支、API 模式与模型、重复 low 和返回基线的结果。没有改动生产会话数据库。

## 对摘要恢复设计的意义

需要分开三个问题：改变 effort 后能否复用原设置的热缓存；low 请求能否建立自己的缓存；
返回原设置时旧缓存是否仍可复用。单看首次 low 未命中，不能声称缓存被清空或以后都会未命中。

如果恢复时才切 low，需要把切换请求的未命中输入费用和延迟计入整次恢复；原生成时的
高缓存命中率不能直接用于预测恢复请求。若从一开始就使用 low，缓存也需要在该设置下
预热，但推理与摘要质量必须另行比较。不能为保缓存直接推导全局降低 thinking 的方案。

官方文档支持 `reasoning_effort=low/high/max`，默认 effort 为 high，但没有承诺跨 effort
复用缓存。缓存按已持久化前缀匹配，属于 best-effort。

## 复现

[实验脚本](../../scripts/probe_reasoning_effort_cache.py)默认只做本地预检，只有 `--live`
发送真实请求。每次使用新目录；复现前核对模型、价格及 API 参数支持。

```sh
.venv/bin/python scripts/probe_reasoning_effort_cache.py --output artifacts/effort-cache-new-dry
.venv/bin/python scripts/probe_reasoning_effort_cache.py --output artifacts/effort-cache-new-live --live
```

本次本地请求与清单保存在 `artifacts/reasoning-effort-cache-20260918-live/`，
清单保存脚本 SHA-256、运行前代码版本、单变量检查及预先声明的门限。
