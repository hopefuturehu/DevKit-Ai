# 摘要生成稳定性优化：故障、对照实验与连续任务验证

整理日期：2026-09-18。本文汇总已有真实请求与本次只读轨迹核查，没有新增模型调用，
没有修改运行时、工作区配置或历史摘要。面试表达见[手册实测案例](../career/context-management-interview-guide.md#compaction-selection-case)。

核心结论：内容取舍与历史后交接提醒减少了这批困难输入的输出截断；后续一次 59 分钟
gaming 运行中，10 次前缀摘要均一次生成并成功发布。两项证据分别支持提示优化的候选生成
收益和连续运行的可用性，不能合并成总体成功率，也不能证明摘要事实完全正确。

## 1. 原来发生了什么

上下文增长后，运行器需要把旧历史归并为交接摘要，再带着原始用户锚点与近期历史继续任务。
摘要生成失败会保留旧摘要和游标；后续请求可能继续积累历史，或由 Planner 省略可选历史。
因此 Agent 还能回复，不等于压缩已经成功，更不等于历史完整进入了下一次请求。

需要区分三段历史，不能把它们当成同一版本、同一负载的连续 A/B 测试：

| 阶段 | 观察到的问题 | 证据与适用范围 |
|---|---|---|
| 早期 CURRENT 快照 | 26 次压缩计划失败 15 次（57.7%）；输出长度 7、引用 4、空摘要 2、缺章节或其他 2 | [历史故障快照](../archive/context-compaction-current-state.md)；全部使用当时的 V4 Pro |
| 前缀与双路径早期实验 | 旧 A 在重放时继续调用工具；另有正文已含章节却因标题括号说明被拒的情况 | [双路径实验](compaction-prefix-fallback-evaluation.md)、[标题兼容修复](compaction-heading-compatibility.md)；模型、参数和版本分别冻结 |
| 09-16 默认双路径事故 | 6 个压缩操作成功 1 个；7 个模型请求成功 1 个，其余 6 个全部 `length` | [事故记录](compaction-incident-20260916.md)；一个多轮调查会话，不是全站故障率 |

09-16 的主要矛盾是生成空间不足，而非输入缓存丢失或数据库故障：

- 前缀失败请求输出达到 8,192 tokens，正文仍未完成最后章节；输入缓存命中已有 88.8%。
- 五次独立摘要都用满 8,192；其中推理消耗 3,661～8,192 tokens，两次没有任何正文。
- 第一份成功摘要已有 15,261 字符，后续不断携带；旧内容没有充分重新取舍。
- 后四个操作处于新 Run 开始，记录 `snapshot_missing`，直接走独立摘要；内存中的
  300 秒失败退避也不会跨 Run 继承，导致失败输入较快重试。

当时正文流与推理流已经分开，4K 正文发布门限也已经取消。不能将该事故解释为
“把 thinking 拼入了摘要”或“完整长摘要被 4K 校验拒绝”。

## 2. 摘要在哪里生成，两条路径解决什么问题

五级上下文管理中的第 4 级负责 LLM 单摘要生成；预算、装配、卸载、恢复分别是其余职责。
本次优化发生在这一生成环节，默认策略仍为 `a_fallback`：

| 路径 | 请求结构 | 用途与代价 |
|---|---|---|
| `a_prefix` 前缀复用 | 保留真实主请求快照的消息角色、工具定义、模型和参数，在尾部追加交接指令 | 尽量复用已处理的输入前缀；模型仍可能继续原任务，工具调用候选会被拒绝且不执行 |
| `a_isolated` 独立摘要 | 专用摘要 system；将旧摘要与新增历史按角色标注为 user JSON 数据；末尾追加交接提醒 | 前缀不可用或可恢复失败后至多尝试一次；改变摘要语境，不保证事实正确或有足够生成空间 |

两条路径处理同一选定覆盖范围，成功后发布一份替代摘要。重复压缩是
`旧摘要 + 新增历史 → 新摘要`，不意味着多层摘要树。B 策略的叶子／合并树是另一个可选方案，
gaming 本次未使用。机制见[默认双路径](../designs/compaction-dual-path-default.md)、
[生成实现](../../src/bot/compaction/strategies.py)和[五级定义](../architecture/design.md#72-压缩策略)。

## 3. 为什么没有直接关 thinking 或一律加额度

09-17 先用事故中的四个不同独立摘要输入，各组重复两次，共 24 次真实模型请求：

| 方案 | 候选生成通过 | 通过且正文 ≤8,192 | 平均推理 / 正文 tokens |
|---|---:|---:|---:|
| 供应商默认 thinking，共享 8K | 0/8 | 0/8 | 6,373 / 1,819 |
| 关闭 thinking，共享 8K | 0/8 | 0/8 | 0 / 8,192 |
| 开启 thinking，总额度 16K | 8/8 | 3/8 | 4,767 / 8,598 |

关闭 thinking 后正文仍写不完，说明问题包含摘要本身过长。额外额度能缓解截断，
但其中五份完整正文超过 8K，不能把收益全部归为推理预算分离。
这是实验组，没有把关闭 thinking 或全局扩额改成生产默认。

此外，`compaction_max_output_tokens` 同时参与摘要边界选择和恢复空间预留。
事故输入的离线推演中，单独调到 32K 会使固定层加预留超过 40K 低水位；
“更多生成额度”必须与恢复后实际正文预算、输入窗口一起处理。
详见[预算对照实测](compaction-thinking-budget-20260917.md)及[事故中的预算分析](compaction-incident-20260916.md#3-新发现直接调到-32k-会撞上另一处预算耦合)。

## 4. 实际落地的修改与两轮实验

最终落地提交为 `8f5c7bc`（`fix: prioritize current task in compaction handoffs`），
修改默认双路径共用的内容取舍提示，并在历史之后再次追加交接提醒：

1. 旧摘要与新增原文一起重新筛选；曾经写进摘要，不自动获得继续保留的资格。
2. 优先当前目标、有效用户约束、未完成事项、阻塞和下一步必需证据。
3. 已完成工作按成果合并，不复述工具调用流水、无关旧任务和整份文件清单。
4. 同一事实不跨章节重复；八章节建议总篇幅约 3K，每章短要点。
5. 历史末尾再次要求只输出交接、不继续任务，并保留未核实状态、反证和回读线索。

第一轮只改独立请求的 system；第二轮在第一轮新提示基础上加尾部提醒。
合计 48 次真实请求，仍使用四个冻结独立摘要输入，生成额度仍为 8,192：

| 提示版本 | 默认 thinking 的候选通过数 | 关闭 thinking 的候选通过数 | 完整正文观察 |
|---|---:|---:|---|
| 旧提示 | 0/8 | 0/8 | 关闭组全部写到 8,192 后截断 |
| 仅加强内容取舍 | 1/8 | 6/8 | 完整候选仍有 6,408～7,892 tokens |
| 内容取舍 + 尾部提醒 | 7/8 | 8/8 | 默认组完整正文均值 3,062；关闭组 2,996 |

最终默认组唯一失败仍是推理挤占额度：推理 7,030、正文 1,164，服务端结束为 `length`。
3K 仍是软目标，没有新增正文硬裁剪；不能说每份摘要都严格控制在 3K。

第一轮采用固定输入的交错对照；第二轮是在观察第一轮后进行的自适应补测，没有同时重跑
旧组。请求核对证明第二轮相对新提示只增加尾部提醒，但它同时改变措辞、短要点要求和位置，
没有单独隔离这些因素。真实实验只覆盖独立路径，前缀接入由运行时测试验证。
报告记录 97 项相关测试通过，属于当次历史验证，不是本文新增执行。

原始证据：[内容取舍实测](compaction-selection-20260917.md)、
[48 次请求机器记录](../data/compaction-selection-20260917.json)、
[24 次预算实验记录](../data/compaction-thinking-budget-20260917.json)。

## 6. 为什么这次没有失败：事实与归因分开

| 因素 | 可以确认 | 不能据此声称 |
|---|---|---|
| 提示修改 | 当前 10 次都使用新提示；旧失败输入实验中截断减少 | gaming 的全部改善都由提示单独造成；缺少同轨迹旧提示对照 |
| 生成长度 | 本次约 3.3K～5.0K 即正常结束；09-16 失败请求用满 8K | 本次靠将额度扩大到 32K 成功；记录实际为未显式设置额度 |
| 推理消耗 | 本次没有可观测的摘要推理输出 | 程序主动关闭了 thinking，或已经解释了供应商为何返回零推理 |
| 前缀可用性 | 同一连续 Run 的 10 次都有快照，且首请求成功 | 跨 Run 的快照缺失、退避重置和独立路径风险已经修复 |
| 缓存 | 本次命中率 95.29%；旧失败前缀也有 88.8% 命中 | 缓存命中能防止正文截断或保证事实正确 |
| 任务与样本 | 本次是单一游戏开发目标；旧事故包含多轮调查 | 任务难度是确定原因；两个样本没有控制任务内容、轨迹和供应商状态 |

与更早的 57.7% 历史失败率比较，还存在发布规则变化：标题括号说明已兼容，
默认逐条引用要求已放宽，正文 4K 硬门限在 `1f9053c` 中取消。
本次本地估算有 7/10 份超过 4K，按旧长度规则也会被拒；这仅是历史规则的离线判断，
不是七次额外失败，也不表示历史模型会生成完全相同的候选。
09-16 事故发生时已取消门限，所以它不能解释 09-16 到本次的改善。
此次八个章节均为普通标题，不能把标题兼容修复计作本次实际挽救次数。

10 次全成功来自一个连续轨迹，输入彼此相关；它不是 10 个独立任务，也不能推出长期失败率为零。

## 7. 成功发布仍不等于事实正确

原始用户锚点的逐字保留与摘要的语义正确性是两项检查。本次 10 次都保留了原始需求，
但第 8～10 次摘要仍传播了错误工具经验：把 `wait_seconds` 的 60 秒上限错误归给
`timeout_seconds`，以及把缺少正确创建参数的补丁失败写成“create=true 对新文件无效”。

实际规则是单次 `wait_seconds ≤ 60`，进程 hard timeout 独立；新建补丁需要
`create=true` 且 `old_text=""`。来源哈希、八章节、协议完整和恢复预算校验不能证明这些
因果解释正确。优化改善的是生成稳定性和篇幅取舍，事实保真仍需独立验证。

| 待改进 | 跨 Run 的快照策略、持久退避、总生成额度与摘要恢复预留的解耦 | 新 Run 首请求前压缩、重复失败退避、低水位可达性及取消反例 |
| 待评测 | 摘要错误归因、早期反证与结束条件的使用 | 固定事实与冲突样本，多次压缩后检查可见性、回读行为和下游决定 |

后续仍分别记录四层指标：请求正常结束、候选通过校验、发布后恢复与原文保留、
下游任务独立验收。各层有各自分母，失败调用也计入耗时和费用；不能用结构通过率替代质量。

## 9. 面试使用口径

推荐讲“从故障分类到固定输入对照，再到连续任务观察”的过程，重点是根据证据否决
单纯关闭 thinking 的方案，改为内容取舍与交接指令优化。可以引用旧提示 0/8 与最终
默认提示 7/8 的候选结果，但要说明四个冻结输入、每个两次及第二轮自适应补测。

gaming 的 10/10 单独作为一次连续运行证据：约 59 分钟、10 次前缀摘要、约 155 秒
摘要请求时间、原始要求保留。不要写“生产失败率从 83.3% 降到 0%”“任务成功率 100%”
或“缓存命中使摘要不再失败”。具体口述与简历句分别见
[面试手册](../career/context-management-interview-guide.md#compaction-selection-case)、
[简历素材](../career/resume-materials.md#compaction-selection-resume)。
