## 2. 已证实的原因

### 2.1 生成额度不足，且两条路径的实际 thinking 不同

前缀请求保留 29 个工具定义，出站 `tool_choice=auto`，没有显式发送 `max_tokens`。
其主请求和压缩请求的实际 thinking 都为 disabled，未在压缩时临时切换模式。
两次前缀分别命中 90,752/95,124（95.4%）和 86,912/97,842（88.8%）输入 tokens。
失败发生在正文生成阶段，不能归因为前缀缓存丢失。

独立请求显式发送 `max_tokens=8192`，没有工具定义，`thinking=None` 导致参数省略。
这次服务端实际采用 enabled，五次推理分别消耗总输出的约 95.7%、100%、75.9%、
44.7%、100%。五次独立输入中的历史 `reasoning_content` 字符数均为零；这里的耗尽
来自本次新生成的推理，不是大量历史推理被重新塞进输入。

机制位于 `providers/openai_compatible.py::_payload`：当历史工具调用缺少推理字段时，
适配器会显式关闭 thinking。独立请求将历史序列化进 JSON 字符串，不触发这个工具链规则。
所以继承相同的配置值 `None`，并不保证继承相同的实际模式。

正文流和推理流已经分开收集；只有正文发布为摘要。当前约 3K 正文目标是软目标，旧 4K
正文门限已移除。今天的问题不是 Bot 把 thinking 拼进摘要正文，也不是完整正文超过 4K
后被拒绝，而是服务端先耗尽了总生成额度。

相关代码：`strategies.py::summarize_with_fallback`、`summarize`；
相关变更：[取消摘要正文发布门限](../designs/compaction-summary-body-limit-removal.md)。
API 的生成上限和结束原因定义见 [DeepSeek Chat Completions](https://api-docs.deepseek.com/zh-cn/api/create-chat-completion/)。

### 2.2 已有摘要偏长，后续摘要没有充分收敛

首次成功摘要为 15,261 字符，本地正文估算 6,582 tokens，已高于约 3K 的软目标。
后续独立请求反复携带这份旧摘要；前缀失败候选写到 17,680 字符仍未完成全部章节。
这些现象说明“完整写出后再发布”的空间不足。提示是否过度鼓励保留已完成细节、章节重复
是否是主要成因，还需要同断点内容对照，不能单凭长度断言摘要质量差。

### 2.3 第一阶段在跨 Run 场景中缺失

后四轮操作都记录 `prefix_skip_reason=snapshot_missing`，直接进入独立路径。
`AgentRunner.run` 结束时删除 `_finalization_frames[run_id]`，下一条用户消息创建新的 Run。
在新 Run 第一次主模型请求之前触发压缩时，没有已发送快照可以复用。
这是前缀阶段未被尝试，不是尝试后缓存未命中。

### 2.4 失败退避仅在同一对象内有效

`StrategyCompactor.retry_after` 是内存字段。失败后设为当前时间加 300 秒，但每个 Run
都会新建 `StrategyCompactor` 并将该字段初始化为零。
17:20:52 失败后，约 89 秒就再次发出相同请求；两次请求 blob 引用完全一致。
现有 `test_double_failure_keeps_cursor_and_backoff` 只复用了同一个对象，没有覆盖跨 Run。

### 2.5 现有恢复链不能处理这种输出截断

当前双路径约定是前缀一次、独立一次。两次都失败就结束，不进入旧 CURRENT 策略的
格式修复、凝练、空响应重试等循环。这符合当前双路径调用次数设计，但没有适配
“thinking 耗尽额度”和“正文过长”两类不同恢复需求。

尤其不能把今天的截断候选直接交给仅看候选的凝练器，然后把结果声明为覆盖完整原文：
没有写出来的信息已经不在候选中，压短不能自动找回它。空正文更不能靠格式修复恢复。

## 3. 新发现：直接调到 32K 会撞上另一处预算耦合

`select_boundary()` 使用以下值预留压缩后摘要的空间：

```python
reserve = ceil(compaction_max_output_tokens * 1.1) + 256
projected = count(restored_request_without_summary_body) + reserve
```

`compaction_max_output_tokens` 是服务端生成额度，包含 thinking；恢复后的上下文只注入
摘要正文，却也按这个总额度预留，两个预算被绑在一起。

对今天第一个前缀请求做离线下界计算：只保留原 system 与 29 个 tools，按原实际模式
disabled 计数，得到预算值 **5,804**。这还不含摘要、用户锚点和任何保留尾部。

| 总生成额度 | 代码预留摘要量 | 固定层＋预留的下界 | 对比默认 40,000 低水位 |
|---|---:|---:|---|
| 8,192 | 9,268 | 15,072 | 尚有尾部空间 |
| 16,384 | 18,279 | 24,083 | 尾部空间减小 |
| 32,768 | 36,301 | **42,105** | 固定层已超限 |

这说明在当前配置与这类请求下，单独把 `compaction_max_output_tokens` 改到 32K，可能
在生成前就报 `fixed_context_exceeds_low_water`。此结果是本地固定版本 tokenizer 的
预算推演，不是新增真实 Provider 实验。

另一个独立限制是压缩生成请求自身的输入窗口。按本地配置 131,072 总窗口、4,096
协议及安全余量，最后一次独立请求的规划输入为 107,711，只剩 **19,265** 生成余量，
即使拆开上述预算，也不能原样发送 32K 生成请求。需提前触发、减少本次覆盖范围并逐段
推进，或在已验证能力下调整窗口配置；不得只是放宽计数让超限请求通过。

## 4. 失败后继续对话的代价

唯一活动摘要一直覆盖 1–115。17:15、17:18、17:20 三轮失败后未出现裁剪事件，主请求
沿用旧摘要与后续历史，仍能在硬输入预算内执行。

17:23 起出现历史省略：第一次丢掉 116–118；到 17:26，单次最多省略 25 条历史消息。
共 12 个 `context.packed` 事件，其中 11 个省略历史，涉及 27 个不同消息位置。
省略发生在输入视图，数据库原文仍保留；被省略的位置也未由新摘要覆盖。

这不是新的压缩成功，而是打包器按软目标和优先级裁剪出的不完整上下文。五个失败操作
所在 Run 均完成回复，不足以证明记忆完整或任务判断正确；本次没有做裁剪与错误回答之间
的因果实验。

## 5. 建议实施顺序

### 第一批：预算、模式与恢复状态

1. **拆开三种预算。** 分别表示总生成额度、摘要正文软目标／规划预留、恢复后完整输入
   上限。只有正文计入摘要的恢复预留；服务端窗口仍按输入＋thinking＋正文的总额度检查。
   最终发布继续使用完整真实正文验算，不恢复旧 4K 正文硬门限。另修复前缀
   `max_output_tokens=None` 时的有效默认额度预留和费用预留，不能把未设置视为零。
2. **以实际模式为准。** 由 Provider 适配层提供解析后的模式用于快照、预算和审计。
   第一阶段保留真实主请求的模式、工具及历史前缀。第二阶段若声明“继承主模型”，就应
   显式继承已解析的模式；无法解析时记录 unknown 并采用保守预算，不能把 None 当成关闭。
   主请求确实开启 thinking 时，独立阶段为推理提供足够总额度，而非默认关闭主模型思考。
3. **显式配置并验证生成额度。** 第二阶段可对 16K 等候选额度做同断点实验，以剩余
   窗口、费用和时间为约束，不能保证某个固定值必然成功。第一阶段优先从主 Run 开始就
   采用明确额度，保留已发送快照的字段；若要在摘要时单独改输出额度，先做真实缓存对照。
4. **持久化失败和退避。** 将退避至少保存到 session 级持久状态，以父摘要、增量起点及
   配置身份关联失败；同一增量不能通过新 Run 或追加少量尾部绕过退避。正常重启继续有效；
   显式重试、配置修复与硬窗口恢复应有明确且有次数／费用限制的例外。
5. **修正错误分类。** 保留 `finish_reason`、reasoning tokens、正文 tokens/字符、
   configured/effective thinking、阶段、缓存、剩余窗口。对于 `length` 且正文为空，主因
   记录输出额度耗尽，附带 empty-body，而不是普通 empty/unknown。复用已有错误类型，
   将生成、候选校验、发布、续跑裁剪分别统计。

### 第二批：保证第一阶段覆盖率与续跑信息完整

6. **跨 Run 保留可复用快照。** 会话级保留最近真实出站请求及位置映射、父摘要、配置
   身份、一次性内容状态。新 Run 可在严格校验后追加已完成工具组和新用户消息。
   项目/工具/system/Provider 改动、父摘要变化、过期一次性内容及缺失证据必须使快照失效；
   并发续跑不得共享一个可变快照。缓存过期不等于快照非法，也不能保证保留快照就必然命中。
7. **将压缩触发阈值与失败后的裁剪目标分开。** 压缩失败后先按校准计数检查完整上下文。
   若仍在硬预算内，允许暂时超过压缩软目标继续；不要为了回到 96K 就删除未摘要覆盖的历史。
   若确实超硬预算，进入有界恢复；仍失败则给出可恢复的上下文受限状态。若保留显式有损
   续跑选项，必须记录并展示省略范围，不能称为摘要替代。工具原子组、用户约束和必需 Skill
   始终受保护。这个调整会改变当前默认“尽量继续”的取舍，应独立验收。

### 第三批：提高摘要收敛与困难断点恢复

8. **减少摘要重复，而非删除关键证据。** 历史已完成任务压成结果与回读线索；优先保留
   当前目标、用户更正、未完成事项和关键反证。针对各章节分配软篇幅，避免在 Goal、Progress、
   Files、Critical Context 重复叙述。软目标应实际取配置值，避免双路径提示固定写死 3000。
   用同断点原始证据评估事实与归因，不能只比较摘要更短或成功率更高。
9. **按失败类型恢复，限制额外请求。** 完整候选仅缺格式时可修复；完整候选确实太大时
   可凝练。`length` 或正文为空时，应基于同一冻结证据调整额度重新生成，或分段覆盖原文，
   不能仅靠残缺候选生成一份外观完整的摘要。若分段压缩不能立即降到 40K，可在连续覆盖、
   净释放和硬预算都成立时逐段推进，不要求每一小段都完成整个积压的低水位目标。
   新恢复请求必须显式纳入总次数、费用和墙钟预算；默认双路径的“一次＋一次”不是已有
   多层重试。是否增加第三次请求应由同断点收益验证决定。

## 6. 验证与推广门槛

本次已完成：逐事件与 blob 对照、出站参数离线序列化、固定层预算下界计算、正文与推理
分离核查、裁剪范围核查，以及机器可读附件内部一致性检查。没有修改运行时代码、会话或
配置，没有实际重发请求，因此没有声称修复后成功率。

后续实现应覆盖：

| 验证 | 必须观察的结果 |
|---|---|
| 同 session 新 Run／重启后再次触发 | 相同失败增量仍退避，不新增 Provider 请求 |
| 前缀请求保持与出站快照一致 | tools、历史、实际 thinking 不被改写；真实命中率另行测量 |
| 32K 总生成、较小正文预留 | 不因把推理当作恢复摘要而错误拒绝边界，完整请求仍守窗口 |
| thinking 吃光额度，正文为空 | 归类为 length，保存真实 usage，无摘要发布 |
| 完整正文超过旧 4K | 满足整体预算即可发布；thinking 不注入摘要 |
| 截断且缺后续事实 | 不通过候选修复伪造完整覆盖，不推进无依据游标 |
| 压缩失败且完整历史仍装得下 | 未覆盖历史保持完整，不仅为软目标裁剪 |
| 固定层／必需内容确实超限 | 明确恢复或停止；原文、父摘要和工具协议完整 |
| 快照失效与并发父版本变化 | 正确跳过或拒绝发布，不复用错误证据 |

离线回放优先复用附件引用的七个请求及响应，不访问付费模型。需要真实验证时，以同一
冻结断点比较基线、预算拆分、实际模式继承、提示收敛，再评估组合；多次重复并统一模型、
输入和计费口径，避免一次通过就宣称稳定。每次同时报告操作成功率、兜底挽救率、覆盖推进、
未覆盖消息省略数、关键事实保留、推理／正文 token、缓存、耗时和实际费用。

建议先完成第一批及“失败后不按软目标省略历史”的保护，再推进跨 Run 快照和摘要恢复策略。
前者解决本次确定的预算与重复失败问题，后者收益需要继续用真实断点验证。
