# 历史会话裁剪容量分析

> 日期：2026-09-08。基于仓库内已有 SQLite 历史的只读离线回放，没有调用模型，没有修改会话库，也没有启用生产裁剪。
>
> 本文所有 token 均使用项目 `TokenEstimator` 估算，与历史打包报告采用同一口径；不是 Provider 账单 token。结果衡量候选策略的容量潜力，不证明任务质量、摘要成功率或缓存费用已经改善。

## 1. 结果与建议

这批历史支持优先实现“较旧成功工具结果的有界收据”，精确去重可以保留为低成本规则，但不是主要收益来源。

- 在主库 201 个可对齐的高压力请求窗口中，保护最近 20K tokens 后，平均可释放 **7,930 tokens，约占请求的 8.29%**；中位数 7,010，最高 24,020。
- 对主库 **13 次成功压缩**的历史源部分，同一规则平均可减少 **8,002 tokens，29.97%**。这部分不包含摘要 System 提示词、上一版摘要和修复/凝练请求。
- 纳入失败尝试，按不同源范围去重后的 28 个主库样本，平均减少 **13,306 tokens，35.01%**。它与成功压缩子集的差异说明，不应只引用较大的一个数字。
- 要求保留完整可见副本时，精确去重在本次压缩前候选历史、摘要源片段和主库压力窗口中的净回收均为 **0**；不能将相同 blob 的重复预览直接当作完整副本。
- 没有可验证的 `activate_skill` / `load_skill_resource` 工具记录，因此本次不能量化 Skill 生命周期或独立全文层移除的收益。

建议首版保留 20K 近期保护，从输入负担最大的 `read_file`、`run_command`、`run_shell` 成功结果做起。先接入已有压缩路径，再验证任务质量与缓存费用；不据此启用每轮主动裁剪。

## 2. 样本范围与限制

| 数据来源 | 会话 / Run | 消息 | 工具执行记录 | 压缩记录 |
|---|---|---:|---:|---:|
| `.bot/state.db` | 32 个会话，其中 20 个非空；100 个 Run | 1,643 | 866 | 34 |
| TerminalBench jobs 的原始 `agent/state.db` | 18 个执行会话 / Run | 1,398 | 754 | 1 |
| 合计 | 50 个会话，其中 38 个非空；118 个 Run | 3,041 | 1,620 | 35 |

主库消息覆盖 2026-07-17 至 2026-09-04；评测记录覆盖 2026-07-30 至 2026-08-31。

- 不重复读取同一任务的 `trace/state.db` 和报告 snapshot；额外以消息指纹识别重复数据集。
- `.bot/benchmarks/context-efficiency` 的合成工作负载不混入实测历史。
- `path-tracing-reverse__dtXXMAc` 的一个评测数据库报 `database disk image is malformed`，已排除；未尝试修复或修改它。
- 主库 34 条压缩记录中，13 条最终成功、21 条失败；触发类型为 23 条 `context_pressure`、11 条 `explicit_compaction`。
- 35 条压缩记录的原始消息哈希和重建源文本字符数均与记录匹配。主库按 `(session, source_start, source_end)` 去重为 28 个范围，同范围重复尝试取最后一次观测；不同范围仍可能重叠。
- 主库的压缩来自两个会话；201 个可对齐压力窗口全部来自同一个长会话。这些不是 201 个独立任务，不能当作广泛领域平均值。

## 3. 回放方法

### 3.1 重建两个不同的输入

**执行请求窗口**：读取 `context.packed` 的时间、活动摘要边界及已丢弃条目，恢复仍进入请求的会话和 Tool Result。202 条记录中，201 条的工具结果层和会话层 token 都能与原报告一致；另 1 条工具层相差 1 token，未纳入主统计。请求总分母使用该时点记录的 `estimated_tokens`。

**摘要历史源**：按 compaction 的重建/增量模式、源范围和历史逻辑闭合记录，使用当前 `_canonical_source_payload()` 重建。先应用既有逐消息 12K 字符限制，再计算新增裁剪的净收益，不能把已经被截掉的文本再次计为节省。用原始消息 hash 和 `source_chars` 校验重建结果。

执行输入和摘要输入不同：执行请求还有工具 schema、环境、摘要、Assistant 工具调用推理等内容；摘要源通常更集中于工具结果。因此“摘要历史源减少三成”不等于“整个 Agent 请求减少三成”。

### 3.2 固定的实验规则

| 项目 | 本次规则 |
|---|---|
| 大结果门槛 | 当前视图正文至少 1,024 tokens |
| 最小净回收量 | 换成收据后至少减少 256 tokens |
| 原文可恢复 | 必须有现存且有 session 访问权的 blob，校验 SHA-256；没有完整引用的结果跳过 |
| 精确重复 | 同 Run、同工具、相同参数与来源字段、成功完成且未被上游截断；原文 hash 命中后再比较字节 |
| 保留副本 | 原文完整存在于当前目标视图；仅有 blob 或头尾预览不算。后续裁剪不再缩短该代表，原调用与结果身份保留 |
| 普通结果裁剪 | 只处理有可靠来源的成功 `read_file`、`search_text`、`run_command`、`run_shell`、`fetch_url` 结果 |
| 近期保护 | 按 Assistant / Tool 原子组保护末尾约 20K tokens；另做 8K 敏感性对照 |
| 收据内容 | 状态、原文引用、来源字段、退出码/数量、原始返回内容大小、上游截断标志，以及头 512 / 尾 256 字符 |
| 不裁剪内容 | 用户输入、Assistant 推理、调用参数、失败/运行中结果，以及缺少所需来源的结果 |

1K、256 和收据大小是本次实验参数，不是已验证的最佳配置。原始 blob 中保存的若是上游截断后的返回内容，收据也保留这一事实，不声称能恢复从未保存的输出。

第一版设计中的 Skill 保护与恢复没有可用样本，未模拟收益。旧数据没有完整的通用任务依赖清单，因此“成功且较旧”仍是价值判断的代理条件；首尾片段也不能证明关键证据全部保留，必须后续做任务验收。

## 4. 执行请求能释放多少空间

样本为 201 个能够对齐历史层的压力窗口；分母是当时已经打包的整个请求。每个窗口独立进行反事实替换，不累计改变后续轨迹。

| 策略 | 平均净回收 | 中位数 | P90 | 最大值 | 平均请求缩减比例 |
|---|---:|---:|---:|---:|---:|
| 仅精确去重 | 0 | 0 | 0 | 0 | 0% |
| 去重 + 旧成功结果，保护 20K | **7,930** | **7,010** | 18,780 | 24,020 | **8.29%** |
| 去重 + 旧成功结果，保护 8K | 9,899 | 8,515 | 23,881 | 31,316 | 10.34% |

P90 采用脚本固定的排序索引计算方法。20K 策略平均替换约 5.43 条结果，最低回收 1,101 tokens；8K 策略平均替换约 6.82 条。

这些窗口平均包含约 95,750 个估算 tokens，其中工具结果约 34,263、会话层约 55,127。工具结果只占总请求的一部分，对它裁剪不会移除占用较多的 Assistant 推理和其他上下文。

在这些重叠观测点中，20K 策略回收量约 51.7% 来自 `read_file`，28.4% 来自 `run_shell`，18.7% 来自 `run_command`，1.2% 来自 `search_text`。这是来源贡献比例，不是跨请求可相加的独立数据量。

把近期保护从 20K 降到 8K，平均只多释放约 **1,969 tokens、2.05 个百分点**。本次没有质量证据支持为这部分增量立即缩小保护区。

## 5. 摘要模型要处理的历史能减少多少

| 样本口径 | 数量 | 平均净回收 | 中位数 | 最大值 | 平均源输入缩减比例 |
|---|---:|---:|---:|---:|---:|
| 主库成功压缩 | 13 | **8,002** | 8,547 | 24,024 | **29.97%** |
| 主库不同源范围，含失败尝试 | 28 | 13,306 | 12,749 | 30,234 | 35.01% |
| TerminalBench 成功压缩 | 1 | 30,302 | 30,302 | 30,302 | 65.35% |

均为保护 20K 的策略。28 个范围中 26 个存在回收空间。均值包含零收益样本；百分比是每个范围比例的算术平均，不是先相加再除总数。TerminalBench 只有一个实际压缩样本，单独列出，不用它代表全部评测任务。

部分可核对的例子：

| 来源 / 压缩记录前缀 | 历史源 tokens | 候选裁剪后 | 净回收 | 缩减比例 |
|---|---:|---:|---:|---:|
| 主库 `7655c6e7` | 37,561 | 27,914 | 9,647 | 25.68% |
| 主库 `3006c79f` | 44,059 | 20,035 | 24,024 | 54.53% |
| 主库 `544409f5` | 15,726 | 15,726 | 0 | 0% |
| TerminalBench `9322144e` | 46,372 | 16,070 | 30,302 | 65.35% |

不能将这些差值直接从历史 `input_tokens` 账单中扣除：后者来自 Provider，而且一次压缩记录可能累计生成、修复、凝练等多次请求。这里只替换历史源部分，其他输入和后续模型行为保持未知。

## 6. 为什么精确去重收益小

压缩源和当前请求必须分别检查副本是否同时存在。不能把“整份历史最终存在重复”当作“过去那个压缩时点已经可以去重”。

本次主库压力窗口未发现满足全部门槛的重复大结果。规则要求同 Run、精确参数和完整正文一致，尚未做跨 Run 身份归一化、近似重复或公共段落提取，所以它是保守范围的测量。

TerminalBench 的 `9322144e` 压缩覆盖位置 1～75；触发时，位置 37、87、117 的三个同源读取结果已经存在，而且 blob hash 相同。但原文有 **10,540 字符**，每条当前消息只有 **8,158 字符且包含引用说明**，仍只是头尾预览，没有一个完整可见代表。只比较 hash 就合并这些预览，会算出约 4K tokens 的空间；严格按本方案的完整可见条件，本次不计入这部分收益。

这个例子说明，实现时既要比较原文，也要检查保留副本的实际交付范围。若后续允许先恢复完整代表再去重，应扣除恢复增加的 token；若只合并相同预览，则需要单独定义范围契约。两种扩展都未计入本次数字。Pruner 还需要协调压缩源与保留尾部，避免让摘要模型只看到指向未见后文的空标记。

## 7. 能否因此不做 LLM 压缩

这批记录能回答空间潜力，尚不能精确回答“能省掉几次 LLM 压缩”。

- `context.packed` 记录的是 Planner 之后的窗口，通常发生在摘要尝试之后；它不是完整的压缩前请求快照。
- 在 201 个窗口中，仅裁剪已保留的结果后，有 **12 个窗口（5.97%）** 从容量上足以容纳当时全部原始候选条目。判定为 `已打包 tokens + 已淘汰条目 tokens - 净回收 <= target_limit`。
- 这个 12 表示减少 Planner 淘汰的充分容量条件，**不表示省掉 12 次 LLM 压缩**。它也没有计算进一步裁剪已淘汰内容的空间。
- 若从更早时点启用裁剪，后续触发时机、模型行动、摘要和缓存都会变化，不能沿用原轨迹逐项相减推算完成率或费用。
- 11 条主库压缩由显式命令触发，不能仅因为输入变小就假定应该取消。

下一轮行为评测应记录压缩前完整候选视图及其预算，先做裁剪并重新计数，再比较触发次数、摘要费用、恢复次数和独立任务验收结果。历史回放的当前结论是：**具有约 7K～8K 的典型压力窗口减载潜力，并能明显缩短部分摘要源；尚不能证明可以替代摘要机制。**

## 8. 复现与产物

在仓库根目录运行：

```bash
.venv/bin/python scripts/analyze_history_pruning.py \
  --output .bot/analysis/history-pruning/results.json \
  --summary-output docs/data/history-pruning-summary.json
```

- [分析脚本](../../scripts/analyze_history_pruning.py)：SQLite `mode=ro` + 读事务，不构造会修改源库的 `SQLiteSessionStore`；不会调用 Provider。
- [可提交的统计与逐压缩结果](../data/history-pruning-summary.json)：包含输入消息指纹、脚本 hash、参数和排除项，不包含原始提示词、调用参数或工具正文。
- `.bot/analysis/history-pruning/results.json`：项目内的详细观测与裁剪位置审计；受既有 `.bot/` 忽略规则管理。
- [测量规则测试](../../tests/unit/test_history_pruning_analysis.py)：13 个用例，覆盖精确/伪重复、来源差异、失败/运行中结果、原文缺失、完整副本可见性、预览计数、原子组保护和收据标志。

已运行上述离线分析、13 个规则测试和相关文件 Ruff 检查。未运行新的在线任务或缓存实验。与[设计方案](../designs/skill-run-lifecycle-design.md)配套使用时，应将这些数据标为“历史容量回放”，不能写成生产优化已经实现的成果。
