# 输出截断后的恢复方案：开源实现与本项目建议

核对日期：2026-09-09。依据为本项目停止批次日志，以及 Hermes、Aider、Pi 的公开源码和官方文档。
本文是方案分析，没有修改运行器、重跑模型或验证新的通过率。既有统计见
[18 题上下文分析](public-benchmark-context-analysis.md)。

建议优先实现**有限的输出截断恢复、恢复后继续工具执行，以及交付检查**，并先补齐 DeepSeek reasoning
协议兼容。扩大输出预算可以作为单独对照；不能假定它能解决反复分析和未交付文件的问题。

## 1. 本项目实际缺口

主样本 6 次 `finish_reason=length` 的响应均为 8,192 completion tokens，且全部没有原生工具调用。

| 任务 | 步数 | 正文字符数 | reasoning 字符数 | 工具调用数 |
|---|---:|---:|---:|---:|
| custom-memory-heap-crash | 9 | 31,646 | 0 | 0 |
| sympy__sympy-18532 | 20 | 33,867 | 0 | 0 |
| chess-best-move | 35 | 37,715 | 0 | 0 |
| dna-insert | 24 | 33,164 | 0 | 0 |
| code-from-image | 76 | 30,381 | 0 | 0 |
| largest-eigenval | 65 | 38,049 | 0 | 0 |

reasoning 字段为零，不表示正文没有推导或反复检查；它说明不能把这些响应直接归类为
“全部 token 花在独立 reasoning 字段、没有可见正文”。eigenval 的这次响应在官方停止后才返回，
不能通过延长运行时间把它纳入截止前恢复成功数。

本项目收到无工具调用的长度终止后，[主循环](../src/bot/core/agent.py)直接抛出
`_RunTermination(reason_code="model_output_limit")`；随后 `_finalize_termination()` 用
`tools=[]` 请求总结。该总结流程不承担写文件或执行验证。

这对 code-from-image 特别不利：此前已有诊断确认，最终总结中的原样程序能通过官方测试函数，
但运行中没有执行它、没有生成 `output.txt`。Chess 原版也在工具输出中找到了正确着法，
却未交付 `move.txt`。这些是恢复工具执行的具体动机，并不等于尚未实测的恢复方案一定能通过。

主模型 `max_output_tokens=None`，Provider 因而不主动发送 `max_tokens`。
8,192 是这六次响应的观测边界，不是代码写死的全局上限；Chess 候选曾在相同未显式配置下返回
9,590 completion tokens，说明不能把 8,192 当作所有模式下统一的能力上限。

### 已测量的发生率与恢复基线

统计范围为 `main18`：16 个原始 attempt 1、Chess attempt 3 环境恢复和大文本编辑 `native-1`
环境变体，共 18 个不同题目、604 次有 usage 的响应。基线为 `578f660`，模型为
`deepseek-v4-flash`；另外 4 次复跑/协议候选不计入以下分母。

| 指标 | 本批实测结果 | 分母与解释 |
|---|---:|---|
| 出现输出截断的题目 | 6/18（33.33%） | 含 eigenval 官方停止后的迟到响应；不是任务失败率 |
| 官方结束前已返回截断响应的题目 | 5/18（27.78%） | 按响应返回时间划界，不等于已确认仍有恢复预算 |
| 输出截断响应占比 | 6/604（0.99%） | 604 包含常规推理及异常收尾 |
| 六条截断响应累计输出 | 49,152 tokens（12.50%） | 占主样本全部 393,124 输出 tokens；不是可全部省掉的浪费量 |
| 截断时独立 reasoning / 原生工具调用 | 0 / 0 | 六条均为较长可见正文，不支持“全部耗在独立 reasoning”归因 |
| 截断后再次发起工具调用的运行 | 0/6（0%） | 六条响应后均无 `tool.requested`，随后结束运行 |
| 新方案恢复率、通过率增量及额外成本 | N/A | 有限恢复、提高输出预算和交付检查尚未做整题对照 |

六条截断响应合计输入为 212,869 tokens；输入和输出用量均来自对应响应的 `turn_usage`，
不重复累加 `model.usage` 副本。原始事件路径与 SHA-256 见
[结构化指标](data/public-benchmark-context-metrics.json)各运行的 `events_path/events_sha256`；
发生次数和用量可由 `responses_finish_length` 重算，正文大小和后续工具行为由原始事件核对。

既有任务诊断提供了两个量化线索，但不属于上述新恢复方案的效果测量：

- **code-from-image：**原始官方验收为 0/2 项通过，缺少 `output.txt`；把收尾中的原样程序
  在本地执行后，两项官方测试函数为 2/2 通过。这定位了执行与交付缺口，不改写原始成绩。
- **heap：**两次有效原版运行均未通过（各 5 passed、1 failed），保留空 reasoning 的协议
  候选一次通过（6 passed）。最大单轮输出从原版的 8,192 降至候选的 4,725 tokens，候选未提高
  输出上限。样本为 2 次原版和 1 次候选，仍有采样与运行条件差异，不能估计普遍通过率提升。

这些诊断的条件与限制见[任务结果及归因记录](public-benchmark-40-results.md)。后续应分别
对照“仅修协议”和“协议修复＋截断恢复”，避免把已有协议候选的通过归功于尚未实施的续接机制。

## 2. 开源项目具体怎么处理

### Hermes：正文续接与工具参数重新生成分开

在固定版本的 `conversation_loop.py` 中，Hermes 对正文截断保存片段并追加续接提示；
正文路径计数达到 4 时停止（初次截断也计数），保留部分结果。工具调用截断则不把损坏消息加入历史，
最多重试 4 次，并可临时放大输出预算；最终仍失败就明确不执行不完整参数。
对部分流中断还会区分网络与输出上限，存在提示模型拆成较小 patch/文件的分支。
这些数量是该版本实现细节，不是推荐本项目无条件照搬的预算。
[源码：长度分类与恢复](https://github.com/NousResearch/hermes-agent/blob/eac1e25127a75c61116a0bbb8ce7681a2f8b61b4/agent/conversation_loop.py#L3202)。

**对本项目的建议：**先增加两类独立恢复动作：正文可保留后继续主循环；截断的工具参数须完整重新生成。
后者的判定应在 `_parse_tool_call()` 前完成，避免先解析半截 JSON 才进入通用异常收尾。
不能只把异常终止改成无条件 `continue`，也不能拼接或补括号后直接执行半截命令。

### Aider：支持 prefill 时续写输出，并以小范围编辑降低输出需求

Aider 在 `FinishReasonLength` 分支检查模型是否支持 assistant prefill；支持时，将累积的部分响应
作为助手前缀再次请求并续接。不支持时不会启用这条路径。
[固定源码](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/coders/base_coder.py#L1492)、
[Infinite output 文档](https://aider.chat/docs/more/infinite-output.html)。

Aider 的 diff 格式只生成被修改的片段；它还支持编辑后 lint，以及配置后自动测试和错误反馈。
[编辑格式](https://aider.chat/docs/more/edit-formats.html)、[lint/test 流程](https://aider.chat/docs/usage/lint-test.html)。

**对本项目的建议：**长文件创建采用较小、完整的工具请求，已有文件优先局部 patch；每个阶段在工作区
形成可检查产物。已有 `apply_patch`/`write_script` 能力不代表模型一定及时使用，仍需运行流程引导。
Aider 的前缀续写适合补完确有必要的大段代码；对正在重复推导的长正文，机械续写可能只是延长循环。

### Pi：有限的上下文恢复，并区分期望输出预算

Pi 的 `isRecoverableLength()` 检查 `stopReason=length` 且实际输出低于原始期望上限；
主会话把该情况或上下文溢出放入有限的 compact-and-retry 路径，最多恢复一次。
被截断助手消息保留在会话存档中，但从这次活动请求历史移除。
[判定函数](https://github.com/badlogic/pi-mono/blob/a4453b79bb8d66b5f385b28ae0e33843c947504a/packages/ai/src/utils/overflow.ts#L166)、
[恢复流程](https://github.com/badlogic/pi-mono/blob/a4453b79bb8d66b5f385b28ae0e33843c947504a/packages/coding-agent/src/core/agent-session.ts#L1988)。

**对本项目的建议：**借鉴“保留审计记录、恢复请求使用完整状态、只做有限尝试”的原则。
Pi 的 length 判定是其恢复启发式，不足以证明所有类似响应都由输入过长引起；
本轮未出现输入溢出事件，不能为六次输出截断统一强制压缩。

## 3. 适合本项目的恢复策略

### 第一优先级：在终止总结之前增加有限恢复

建议初版将每次运行新增的截断恢复模型请求限定为最多 2 次，并同时受原有步数、费用、墙钟期限约束。
“2 次”是待验证的初始参数。恢复状态应持久化，重新装载会话不能重置为无限重试。
成功恢复到工具执行后可清除连续失败计数，但不能清零整次运行的恢复总数。

| 观察到的状态 | 建议动作 |
|---|---|
| 有正文、没有工具，因输出上限结束 | 保留正文原件并标记未完成；重新进入带工具的主循环，要求执行当前最小交付或验证动作 |
| 工具调用参数被截断 | 保留原始响应供诊断；从未执行该调用前的完整请求状态重新生成，不执行不完整参数 |
| 只有 reasoning，没有正文或工具 | 单列预算耗尽；有限地调整已支持的 effort/输出预算，避免相同请求无限续写 |
| 实际上下文接近硬边界或收到 context-length 错误 | 使用现有上下文恢复路径，并为本次输出预算重新核算输入余量 |
| 剩余期限、费用、步骤或恢复次数不足 | 进入终止总结，保留部分结果和明确原因 |

对第一种状态，建议用有来源标记的运行提示，而非冒充新的用户目标：

> 上一响应因输出长度限制中断，任务尚未完成。不要重复已有分析。根据已有证据，调用工具完成当前最小的文件修改或验证步骤；只有交付检查通过后才给出简短最终回答。

提示本身不保证恢复成功。还要检查下一轮是否出现有效工具执行，以及是否产生要求的文件/修改。
所有工具仍经过既有参数校验与权限策略；正文里的代码不能被运行器自动提取并执行。

### 第二优先级：显式输出预算与按需扩大

可以将 `16,384 → 32,768` 作为预算对照候选，不应未经验证就设为所有请求默认值。
恢复请求必须同时考虑模型能力、输入余量、实际时间和费用；如果动态增加输出上限，
也要动态扩大输出 reserve，不能只修改 HTTP 字段。
本项目固定配置的较大输出上限已会影响构造时的 TokenBudget；逐请求临时扩大仍需相应实现。

当前 DeepSeek 官方文档给出的最大输出为 384K，但本项目配置的上下文窗口是 131,072，
不能直接把官方最大输出抄进当前配置。文档还明确输入与生成内容受上下文总长度约束。
[模型能力](https://api-docs.deepseek.com/quick_start/pricing/)、
[Chat Completions 参数](https://api-docs.deepseek.com/api/create-chat-completion/)。

若已经有长篇可见正文却迟迟不执行工具，应优先改变下一步动作；增加预算可能让重复分析继续增长。
若新样本确实是独立 reasoning 耗尽，可以测试降低 effort。DeepSeek 当前支持 `low/high/max`，
`medium` 和 `xhigh` 均映射到 `high`，不能用 medium 作为“降低思考强度”的实验组。
本项目目前没有直接暴露 `reasoning_effort` 配置，需先补接口。
[官方 thinking 文档](https://api-docs.deepseek.com/guides/thinking_mode/)。

### 第三优先级：把文件交付变成完成条件

基于用户明确要求建立最小交付检查，例如输出文件存在、非空及必要格式检查；
需要代码修改的任务检查是否形成实际修改，并运行可用的项目检查。文件存在本身不等于正确。

如果模型准备返回完成状态，但交付检查失败且仍有预算，转回工具循环处理具体缺项。
这借鉴 Aider 的编辑后检查流程，是本项目拟增加的机制；不能描述成 Aider 自带本基准的文件门禁。
评测侧隐藏测试和标准答案不能注入 Agent；只使用任务说明、当前工作区及可用检查。

对超时问题另需协调外层 harness 的取消信号。eigenval 在官方停止后的迟到响应不允许触发新的恢复，
不能以延长外层时间换取看似更高的截断恢复率。

## 4. DeepSeek 协议是恢复前置条件

续接截断正文会让这条助手消息再次进入带工具的请求，因此必须同时正确保存并回传 reasoning 的
字段状态和内容。当前官方文档要求：带 `tools` 时，历史助手 reasoning 需完整回传，
即使那一轮没有工具调用。这个要求正好涉及此前遗漏的非工具摘要/助手消息。
[官方说明](https://api-docs.deepseek.com/guides/thinking_mode/#tool-calls)。

真实返回的空值、未保存的历史 reasoning，以及系统生成的摘要不能混为同一种状态。
先修工具轮空 reasoning，再补非工具助手消息与合成摘要的协议处理，才能可靠评价续接方案；
否则 length 恢复可能转化为 HTTP 400。

DeepSeek 当前也提供 Chat Prefix Completion Beta，要求末条助手消息 `prefix=true`，使用 `/beta`
端点。本项目当前消息结构与序列化未支持该字段，需要单独适配并验证与 thinking/tool calling 的组合。
因此初版可优先采用普通对话中的“带工具恢复”，将严格前缀续写作为后续能力。
[官方前缀续写文档](https://api-docs.deepseek.com/guides/chat_prefix_completion/)。

## 5. 如何验证收益

先用确定性 Provider 夹具检查状态和副作用，再进行明确区分版本的真实对照：

- 正文截断后，下一轮完整工具调用能够执行，随后才结束任务。
- 截断工具参数从未执行；恢复后的完整调用只执行一次。
- 恢复次数、用量及截止时间正确累计；取消后不再调用模型或工具。
- 非工具助手消息和压缩摘要在恢复请求中满足 Provider 协议，不触发新的 400。
- 交付不存在时不误报完成；读取/解释任务不会被错误强制要求修改文件。

真实比较建议先分为“原版”“仅修协议”“协议修复＋有限恢复”；
再单独比较输出预算和编辑策略，避免一次同时修改多个因素后无法归因。
code-from-image、chess、DNA、heap、SymPy 可用于交付恢复分析；eigenval 主要用于超时取消验证。

至少报告：截断响应数、恢复触发数、下一有效工具调用恢复率、官方产物通过率、
新增输入/输出 tokens、额外耗时、恢复预算耗尽数、重复工具执行数与协议错误数。
恢复率的分母应是截止前有资格恢复的截断事件；不能把正文续写成功直接算成任务成功。
长度截断事件可能仍存在而最终通过率提高，因此不能只优化 `finish_reason=length` 的发生率。
