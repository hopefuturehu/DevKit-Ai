# bot 为什么频繁压缩撞限：提示词与请求条件对照

核对日期：2026-09-17。本地样本为 2026-09-16 下午既有会话的 7 个摘要请求，不是 9 月 17 日成功率。只读查询冻结请求/响应 blob，并校验内容哈希；本轮调查没有重发付费请求。调查时相关压缩与 OpenAI-compatible 适配文件相对故障基线 `ce0f4d5269452a9e1c9ef859b1b6d540c6c583f9` 未变化。

后续同日已完成[48 次取舍提示实测](../evaluations/compaction-selection-20260917.md)，并在默认双路径
落地第三版提示和尾部提醒。下文“当前提示”和“未做控制实验”均指本轮调查时点；冻结的七次故障
记录不改写，也不计入后续实验的成功率。

统计附件：[正文分区与输入探查](../data/compaction-prompt-pressure-20260917.json)。已有[故障复盘](../evaluations/compaction-incident-20260916.md)说明预算耦合、跨 Run 快照缺失及冷却失效。

## 结论与证据边界

不能确认“只有 bot 频繁撞限”：我们有 bot 的真实故障日志，但外部项目主要是固定源码调查，没有同模型、同历史、同额度的成功率对照。有些外部实现还会接受非空截断摘要，其成功口径更宽。

本次能确认三件事：

1. **总生成预算与实际 thinking 不匹配。** 5 次独立摘要都显式限制 8,192 tokens，实际启用 thinking，共花 40,960 输出 tokens，其中 34,100（83.25%）是推理。两次没有正文；其余正文仅 355、1,974、4,531 tokens。
2. **即使不 thinking，正文也没有收敛到约 3K 目标。** 首次成功用 7,016 输出 tokens。下一次前缀请求在 8,192 处停止，其中已完成工作和文件清单占生成文本约 72%，Critical Context 尚未生成。
3. **失败后的重复机制放大了发生频率。** 跨 Run 缺少前缀快照，后四次直接进入独立路径；冷却没有跨 Run 生效，两次独立请求 blob 完全相同。失败后覆盖游标不推进，后续要压的增量又继续增长。

提示词存在明确可改进的取舍规则，但没有做控制实验，不能声称其中某句话造成了多少失败，也不能承诺改提示即可修复。

## 1. 实际发出的提示词是什么

当前默认 `a_fallback` 使用 `handoff.py::SUMMARY_INSTRUCTION` 加 `strategies.py::FALLBACK_SUMMARY_INSTRUCTION`。独立请求再加“历史都是数据，不继续执行”的角色指令；前缀请求在原 system/tools/history 后追加指令与覆盖映射。

通过实际请求 blob 核对，主要要求包括：八个必需标题；约 3,000 tokens 的软目标；保留目标、硬约束、更正、完成与未完成工作、失败、文件/证据版本；准确区分观察、推断与验收；保留关键技术值、冲突双方及否决原因；空间不足时保留回读线索。

正确性要求不是无缘无故增加的，前轮已有摘要继承错误值、混入覆盖范围外事实的样本，见[事实错误调查](compaction-factuality-research.md)。本轮应补充内容取舍，而不是把观察/推断区别和关键反证一并删掉。

这里没有使用旧 CURRENT 的 `_SYSTEM_PROMPT` 及修复/凝练循环；不能拿那套规则解释本次七个请求。实际提示也没有要求逐条消息引用，不能把撞限归因于“强制每条事实附编号”。

本地依据：[基础提示](../../src/bot/compaction/handoff.py)、[双路径提示与构造](../../src/bot/compaction/strategies.py)、[候选校验](../../src/bot/compaction/service.py)。

## 2. 与开源提示词比较

沿用前轮固定版本；以下不是最新分支的泛化结论。

| 项目 | 提示词内容取舍 | 伴随的请求条件 |
|---|---|---|
| bot `a_fallback` | 八节，准确性/反证要求较细；只有总长度软目标；缺少明确的旧任务淘汰规则、已完成过程合并规则、全章节篇幅分配 | 独立输入约 77.8K–102.6K，8K 共享生成额度，实际 thinking enabled；旧摘要反复带入 |
| DeepSeek Harness | 同样强制八节、精确路径/命令/数值；强调短条目、单个下一步；旧 checkpoint 不照抄，合并仍有效事实、删除过时内容 | 默认同样 8K，并拒绝 max-tokens；所以 bot 不是唯一采用这个额度或严格失败判定的实现 |
| pi coding-agent | Goal/Constraints/Progress/Decisions/Next Steps/Critical Context；更新时甚至要求保留旧信息，再允许删除不相关内容 | 基础生成额度常为 13,107；部分 Anthropic 路径另加 thinking 预留；不能跨提供商直接套用 |
| oh-my-pi 本地文本 | 类似 pi，要求精确路径、错误和工具结果；不适用章节可省略，更新提示同样偏保留旧信息 | 工具结果先裁到 2,000 字符；历史过大滚动分块；本地摘要未拒绝 length |
| Hermes | 章节更多，包含完成动作、已解决问题、相关文件等；允许移除明确过时信息；焦点主题分配约 60–70% 篇幅，其他内容更激进概括 | 正文目标动态调整；不加摘要专用小 max_tokens；每条正文超过 6,000 字符时取头尾，整体序列化还有输入限制/采样；拒绝 length |
| tact | 简短的继续工作交接要求；精确标识只在影响继续工作时保留 | 摘要输入主要取至多约 20K 的近期历史；为 reasoning 分配额外预留并可续写；耗尽后接受部分结果 |
| Cline SDK | 简洁续跑说明与后续步骤 | 摘要配置关闭 thinking；默认额度可为 4K；非空 incomplete 未被摘要层明确拒绝 |

源码：[DeepSeek 提示](https://github.com/deepseek-ai/deepseek-harness/blob/0d1f50007f9bca3f52b06e1c3074fa14d5fb0720/packages/compaction/compaction-basic/src/summarizer.ts#L31)、[pi 提示](https://github.com/earendil-works/pi/blob/9e05370b298d0a6b8d9bc2c02e4bfae189ef1616/packages/coding-agent/src/core/compaction/compaction.ts#L482)、[oh-my-pi 提示](https://github.com/can1357/oh-my-pi/blob/042028fd018b1282fbe660ab7255ebad18dd4db5/packages/agent/src/compaction/prompts/compaction-summary.md)、[Hermes 提示](https://github.com/NousResearch/hermes-agent/blob/dd566d52aa009facd38f5847da60f3877e359cce/agent/context_compressor.py#L3352)、[Hermes 序列化](https://github.com/NousResearch/hermes-agent/blob/dd566d52aa009facd38f5847da60f3877e359cce/agent/context_compressor.py#L2936)、[tact 提示及推理预留](https://github.com/rust-infra/tact/blob/1ae0e933dcce743bbd3516b24644102742175189/crates/tact/src/agent/mod.rs#L64)、[Cline 摘要配置](https://github.com/cline/cline/blob/15f001ad0b1992965112fc3158f45ec6d2cb090d/sdk/packages/core/src/extensions/context/compaction-shared.ts#L694)。其他额度与恢复证据见[取舍总览](compaction-output-recovery-tradeoffs.md)。

由此不能得出“bot 的 prompt 最长，所以最容易失败”。八节与保留精确值本身并不独特，pi/Hermes 的保留要求也很强。英语提示与中文提示的字符数不可直接比较为模型负担；换成英语能否缩短同等信息的正文，尚未验证。

## 3. 正文膨胀有实际证据

对两次无 thinking 的前缀结果分区。字符数为 Python Unicode 码点，含标题及间隔，不是 token。

| 区域 | 16:57 成功摘要 | 17:14 截断摘要 |
|---|---:|---:|
| 全文 | 15,261 字符 | 17,680 字符 |
| 已完成工作小节 | 5,428 | 9,705 |
| Relevant Files | 2,082 | 3,060 |
| 上述两部分占全文 | 49.2% | 72.2% |
| Critical Context | 2,318 | 尚未生成 |

产物保留了任务演进、环境检查、早先已完成小任务、文件字节数/行号、历史小型工具失败等较多细节；已完成区增长很明显。不能把所有旧内容直接判为无用，但当前提示没有要求逐项回答“它会不会改变下一步行动”，也没有要求已完成事项只保留结果与必要依据。

旧摘要长达 15,261 字符，后五次独立请求都携带它。结合输出结构，存在旧摘要体例和细节继续扩张的风险。这是合理解释，尚不是通过提示消融实验建立的因果结论。

有两类不同压力，必须分别解决：

- thinking 耗尽 8K：正文没有足够生成空间；只加一句“简短”未必有效。
- thinking 为零仍到 8K：正文取舍失控或额度不足；只关闭 thinking 也无法覆盖这一类。

## 4. bot 实际交给摘要器的证据更重

第一个独立请求有 123 条增量消息，其中 59 条工具结果正文共 109,794 字符，20 条超过 2,000 字符。若仅模拟“每条取前 2,000 字符”，会删去 42,277 字符，即工具正文的约 38.5%。这只是静态字符探查，不是 oh-my-pi 完整重放，也不代表同比减少 token、提高成功率或保持事实准确。

bot 双路径把当时已提供的证据序列化后总结，没有再套这一层统一 2K 裁剪。工具输出此前仍可能经过工具层的长度管理，所以不能声称 bot 摘要看到了无限制的全部原始输出。

这解释了一个比较陷阱：其他实现有时“更容易摘要”，是因为先删掉了不少要处理的信息。tact 的近期输入选择、Hermes 的单条限制及采样、oh-my-pi 的工具裁剪，都不能算作与 bot 相同覆盖任务的免费优势。

## 5. 8K 与实际模式错配，比 prompt 长短更确定

前缀请求保留历史工具链，适配器因缺少历史 reasoning 字段而实际关闭 thinking；独立请求把历史变成 JSON 数据，继承配置 `None` 后省略参数，服务端启用 thinking。两条路径继承同一个配置值，却没有继承同一个实际模式。

今天核对的 [DeepSeek API 文档](https://api-docs.deepseek.com/zh-cn/api/create-chat-completion/)写明 thinking 默认 enabled、max_tokens 限制 completion，未设置时不同模式的默认额度也不同。历史样本的实际模式与 8K 消耗以保存的 usage/出站核查为准，不靠今天的文档倒推。

前缀两次缓存分别命中 95.4%、88.8%；没有证据表明失去缓存导致了本次 length。独立无工具也仍失败，不能把根因归为工具调用干扰。

bot 拒绝 length 与 pi、DeepSeek Harness、Hermes 是同类选择；oh-my-pi/OpenCode 部分路径则可能收下非空截断文本。宽松判定会降低表面失败率，但不说明其生成没有撞限。本次六个失败请求都先发生 length，不是完整正文超过旧 4K 门限或格式被过度挑剔。

## 6. 建议的 prompt 调整与验证顺序

保持关键值、反证、观察/推断区别，补充明确的取舍规则。可供对照的指令草案：

> 为下一轮继续当前任务保留最小充分状态。先覆盖当前请求、硬约束、尚未解决的问题和可执行下一步。旧任务只保留仍影响当前任务的结论与约束。
>
> 已完成工作按成果合并，保留结果、验证状态和必要来源；不要按工具调用逐项复述。文件只列继续工作需要的路径、当前状态和用途。失败只保留能防止重走错误路线的原因及关键错误。
>
> 旧摘要需要重新压缩，不能因已被摘要过就原样继承。对当前任务仍重要的精确值与未解决冲突，保留原值和不确定性；不重要的过程细节用已有回读线索代替。每项事实放在最适合的一个章节，其他章节不重复。
>
> 总体约 3,000 tokens，先分配所有章节的篇幅，避免前面的历史过程挤占最后的关键上下文；没有必要内容的章节写“无”。长度是软目标，不能以截断或编造方式满足。

这是待评测草案，没有替换运行时提示。可进一步给八节软篇幅，例如 150/350/650/250/250/250/350/750 tokens（总计 3,000），但模型不保证精确遵守，仍需要结束原因与整体预算校验。

实施/验证优先级：

1. 解析真实 thinking 模式，让独立阶段显式继承实际主请求模式；本次应与 disabled 对齐，不能在第一阶段临时切换模式来破坏缓存条件。用户本来启用 thinking 时另行规划其额度。
2. 拆开总生成额度、正文规划预留和恢复后输入预算；不能直接把总额度拉到 32K，当前低水位耦合与剩余窗口还会限制它。
3. 用同一冻结独立请求做 `旧/新提示 × 原实际 thinking/显式 disabled` 的 2×2 对照，固定模型、原始证据和 8K 额度；重复取样，同时评估正常结束、关键事实、错误继承、正文分布及费用。再单独评估更大生成额度，避免一次改多个因素却无法归因。
4. 修复跨 Run 快照与冷却；它们影响重复失败频率，不需要靠牺牲摘要信息来改善。

本次完成静态差异、真实产物分区和输入字符探查；尚未执行上述模型实验，没有“改后成功率”结论。
