# DeepSeek tool_choice 缓存实测

2026-09-11（北京时间）。**`auto → none` 会使本次请求失去已预热的 auto 前缀；旧缓存
没有被清空，切回 auto 仍可命中。** 此前“保留 tools 字段并设置 none 即可保住收尾缓存”
的假设不成立。用户要求先核实摘要工具调用的内容；暂未调整运行逻辑，收尾仍为
`9ff2388` 中的 none，A 压缩仍为 auto。

## 实验控制

- 模型为官方 `deepseek-v4-pro`，thinking disabled，temperature 0，输出上限 64。
  28 次响应 fingerprint 均为 `a307abda487cd1b463329ccb945ce396`，与之前四轮任务相同。
- 合成历史包含两个工具 schema 和一组完整的工具调用/结果；基准输入均为 24,000 tokens。
  不发送真实任务内容，不执行工具。全部响应为 `OK`，finish_reason=stop，实际各输出 1 token。
- 三组不追加消息的 auto/none 对照，另有一组尾部追加已生成的 `OK` 和收尾指令。
  每个条件使用独立的 system 起始 namespace，顺序交替，避免前一条件预热后一条件。
- 每个条件先发送两次 auto，相邻请求完成后等待 8 秒。8 个条件首次均为 0 命中，第二次
  均为 99.73%，全部满足预先设定的冷启动 <5%、预热后 ≥95% 要求。
- 主实验 24 次请求；按预先声明的诊断规则，对前两个低命中的 none 条件各追加
  `none → none` 和返回 auto，共 4 次。无重试、无错误、无缺失 usage。
- 已核对完整请求：前三组 treatment 相对各自预热请求只改变 `tool_choice`；最后一组
  还追加了尾部消息。所有工具定义与原消息前缀均保持不变。

## 结果

表中 token 数为每次请求，重复条件中每次结果相同；命中率也与加权命中率一致。

| 条件 | 次数 | API 输入 | 命中 | 未命中 | 命中率 |
|---|---:|---:|---:|---:|---:|
| 已预热 auto → auto，原消息不变 | 3 | 24,000 | 23,936 | 64 | 99.73% |
| 已预热 auto → none，原消息不变 | 3 | 23,665 | 0 | 23,665 | **0%** |
| 首次 none 后重复 none | 2 | 23,665 | 23,552 | 113 | 99.52% |
| 随后返回 auto | 2 | 24,000 | 23,936 | 64 | 99.73% |
| 追加收尾尾部，保持 auto | 1 | 24,029 | 23,936 | 93 | 99.61% |
| 追加收尾尾部，改为 none | 1 | 23,694 | 0 | 23,694 | **0%** |

改变 tool_choice 并未清空旧缓存，也不是 none 完全无法缓存；问题是两种请求之间的复用。
在 none 条件已热之前，原有 auto 历史不能直接提供这次请求所需的热前缀。

## 为什么会这样

客户端工具 schema 保持不变，但 API 输入每次恰好减少 **335 tokens**。本地分别编码
“保留 tools”和“移除 tools”两种输入，后者与所有 none 请求的 API 输入数完全一致；
前者与所有 auto 请求完全一致。两种本地输入的共同 token 前缀只有 52 tokens。

这与 **服务端在 none 模式下省略工具定义** 的解释高度一致。我们没有服务端渲染源码或
实际 token 序列，因此这是基于 token 数、受控参数变化和复用行为的推断，而非源码证明。
已实证的是：本轮切换 none 导致输入量变化，并且失去原热前缀的命中。

本地 `render_deepseek_input()` 没有处理 tool_choice，先前的“编码结果相同”检查不能代表
服务端行为。在本夹具下，none 输入会被本地多估 335 tokens；本次没有修改 token 计数器。
[官方缓存说明](https://api-docs.deepseek.com/guides/kv_cache/) 要求匹配已持久化的前缀单元，
并不承诺修改 tool_choice 仍保留缓存。

## 对实现的影响与待评估方案

可评估的方案是保留原请求的工具定义和消息、尾部追加收尾指令，同时维持 auto。
工具执行仍由收尾消费循环禁止；若模型返回调用，忽略它并使用确定性收尾，不额外采样。
API 允许生成工具调用，不代表执行器必须执行；代价是可能退回固定格式摘要。
**这项运行逻辑修改尚未实施**：曾作出的未提交修改已按用户要求撤回。

A 压缩保持现有 auto，暂不实施此前的 none 建议。应先核实它调用工具的具体意图，
再决定是否调整提示、允许受限检索或引入有明确缓存成本的 none 重试。
不能继续把 none 描述成无缓存代价的修复。

这不是完整 AgentRunner 收尾或任务验收的端到端收益测试。三组重复与一组尾部场景足以
否定本轮的“不影响缓存”假设，但不应推广为所有模型、thinking 设置、工具规模或未来
服务版本均相同。实际收尾正文质量和不同任务下的命中仍需后续任务对照。

## 追查此前摘要工具调用：原始参数未被记录

A 32K 第一次压缩的两次失败分别为北京时间 9 月 10 日 23:13:42、23:13:45，
输入均为 73,262，输出分别为 129、77 tokens；finish_reason 均为 tool_calls，
error 均为 unexpected_summary_tool_call。API response IDs 分别为
`ba513937-2fee-4549-aab4-61e40c73e4ea` 和 `f8482c3e-90e0-4613-837f-ccd7189b48ed`。

核查冻结 Worker wheel 与当前 [strategies.py](../src/bot/compaction/strategies.py) 完全相同
（SHA256 `4948408684d253307586de270f886a4bceb5ee3100b86eabaaabfdf2b56b383c`）：
summarize() 收到 TOOL_CALL_DELTA 时只设置 calls=True，没有累积或记录 name、id、arguments；
失败事件保存 usage、finish_reason、error，但不保存这些字段，也不保存已生成的正文。
原始 events、Worker 日志及只读 SQLite trace 均未提供这两次调用的具体内容。

所以目前只能确定“摘要响应含工具调用且因此被拒绝”，**无法确认请求的工具、参数、
调用次数或意图**。这些调用没有进入主 Agent 工具执行循环。不能据此断言模型是在继续
执行任务，也不能排除它想检索摘要所需信息。

压缩前后主 Agent 的相邻请求确实都是 run_shell，分别运行 objdump 查看 mystery 的
.rodata 常量：压缩前地址范围 0x485ac0–0x485ae0，压缩后 0x480000–0x480060。
它们属于主循环第 30、31 步，不是摘要请求；不能用相邻调用冒充丢失的压缩工具调用。

后续若重放，先在评测记录层保留完整工具名、参数增量及正文，再观察工具意图。重放
产生的是新样本，无法恢复这两次已经丢失的原始输出。本次没有新增这类重放或修改记录代码。
