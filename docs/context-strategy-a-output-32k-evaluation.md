# A 的主输出额度补测：8K → 32K

日期：2026-09-10。同一道 `path-tracing-reverse`，从新环境重新执行一次 A。
**本轮最终文件通过官方 3/3 验收，reward=1；Agent 在继续探索时因 SSL 断流退出，
没有正常结束任务。** 这证明本轮 A 经连续两次摘要后仍能产出通过验收的文件，
尚不能证明提高输出额度导致成功，也不能据此估计稳定通过率或节省比例。

[逐请求量化数据](data/context-strategy-a-output-32k-results.json)与
[原三组评测](context-strategy-path-evaluation.md)分别保存，原始成绩不覆盖。

## 改了什么

评测入口增加 `--main-output-tokens` 和 `--strategies`，本轮只运行 A，主模型输出
从 **8192 提到 32768**；摘要请求仍为 8192。脚本默认值保留 8192，日常配置未修改。
输出触顶时的停止逻辑、弱进展管理、A 的摘要算法均未修改。

运行冻结在 `e76d15047419e5cc6e529a090924b6ca0aab27ef`，产物目录为
`artifacts/context-strategy-path-20260910/a-output-32k/`。
新旧 A 配置只有 `model.max_output_tokens` 不同；两个 wheel 的 Python 文件只有
只读审计模块不同，Agent、Provider 和压缩实现相同。任务文件哈希一致，响应中的
模型指纹也一致。保持 `deepseek-v4-pro`、thinking=disabled、temperature=0、240 步、
Worker 1740 秒和保守 $10 费用预算，关闭 Skill、记忆与子 Agent；未给模型额外题解。

增加输出预留同时挤占输入预算，这不是严格隔离的输出上限实验：

| 预算 | 旧 A | 本轮 A |
|---|---:|---:|
| 主模型输入硬预算 | 118,784 | 94,208 |
| 主模型压力阈值（80%） | 95,027 | 75,366 |
| A 摘要输入预算 | 118,784 | 118,784 |
| 摘要输出额度 | 8,192 | 8,192 |

主输入预算为 `131072 - 主输出额度 - 2048 - 2048`；A 摘要请求独立使用摘要输出额度
计算输入预算。因此本轮自动压缩更早触发，A 摘要输入额度没有降低。

## 连续压缩与失败记录

| 成功发布 | 第一次 | 第二次 |
|---|---:|---:|
| 累计覆盖原文消息位置 | 1–80 | 1–144 |
| 同状态完整请求预算：压缩前 → 后 | 109,587 → 32,502 | 75,834 → 32,764 |
| 净释放 | 77,085（70.34%） | 43,070（56.80%） |
| 摘要正文启发式 tokens / 字符 | 1,117 / 4,415 | 1,388 / 5,490 |
| 发布后第一主请求真实输入 | 30,962 | 31,216 |
| 发布后第一主请求缓存命中率 | 12.82% | 12.71% |
| 发布阻塞时间 | 54.58 秒，含本次重试 | 30.83 秒 |
| 首个工具往返 | 完成 | 完成 |

5 次摘要请求的输入共 427,940 tokens，缓存命中 **94.82%**，输出共 6,024。
原文哈希、两次发布的父链、真实用户锚点及仅一个活动根核验通过。
这里的预算包括安全余量，不能与 API 输入或摘要正文启发式估算直接互减。

三次失败均不是输出截断：

1. 最早一次触发的两次尝试返回工具调用，分别输出 129、77 tokens，被
   `unexpected_summary_tool_call` 拒绝；随后进入现有的 300 秒退避。
2. 退避后再次触发，首个候选输出 1952 tokens，但缺少 `Key Decisions` 章节，被拒绝；
   重试输出 1710 tokens 后成功发布。之后第三次触发一次生成即成功，输出 2156 tokens。

A 复制了主请求的工具定义，同时设置 `tool_choice=None`；Provider 将其序列化为
`tool_choice="auto"`，所以提示词中的“不调用工具”没有形成协议约束。这是明确的
待修缺口，下一次可先显式设置 `tool_choice="none"`，保留工具定义以争取前缀缓存，
通过 Provider 序列化检查和真实摘要请求验证。本轮没有夹带该修改。

首次失败至首次成功发布之间还出现 7 次输入重新装箱，逐步移除旧上下文项；这些是
预算兜底，不计作成功摘要压缩。运行器将 84/89 步标为弱进展，这是诊断标签，不能等同
84 步全部无效，也不因本轮验收通过就认为反复探索的问题已经解决。

## 能得出的结论与验证范围

- 32K 配置已实际生效，本轮未触顶；但没有任何完整主响应超过 8192，因此额外输出空间
  没有被直接使用。新轨迹与更早的压缩触发都是混杂因素，不能将 reward 0→1 归因于额度。
- A 本轮连续两次发布后均可调用工具，最终产物通过官方检查；这是有用的正向样本，
  单次运行仍不足以改变默认策略或宣称稳定提升。本轮也没有覆盖 30–60 分钟持续执行。
- 费用高于旧 A，且旧 A 未通过，不能计算“完成同一任务节省多少”；需同预算配对重复。
- 本次新增了只读审计对“已有流式输出、缺最终 usage”的识别，避免 SSL 断流被漏记。
  15 项审计测试与 Ruff 通过；新审计重算旧 CURRENT/A/B 的计数、成本结果逐项不变。
  冻结资产 3 项、任务文件 8 项哈希通过，Worker 累计 tokens 与逐请求已知 usage 一致。
