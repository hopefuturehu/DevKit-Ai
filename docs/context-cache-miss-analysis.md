# 真实任务缓存未命中拆解与优化建议

2026-09-11。只读分析 9 月 10 日 `path-tracing-reverse` 的 CURRENT 8K、A 8K、B 8K、A 32K 四轮，
没有新增付费模型调用或修改运行机制。
[分组数据及事件来源哈希](data/context-cache-miss-analysis.json)与原始逐请求 usage 对齐。

**全程 85%–90% 不是每一步的缓存上限。** 新内容、摘要替换、重新装箱、独立摘要和异常
收尾混在同一个分母中。新 A 最突出的问题是连续重新装箱，B 则是独立摘要与收尾。

## 指标与服务规则

加权命中率为 `Σ命中输入 / Σ全部输入`，不是有命中的请求比例。首次出现的工具结果通常
需要新计算；旧文本移动到不同前缀之后，也不能仅凭内容相同复用。

DeepSeek 当前规则要求完整匹配已经持久化的缓存前缀单元。请求输入和模型输出的结束位置、
共同前缀检测和固定间隔都可能形成单元；缓存建立需要时间，服务不保证 100% 命中。因此
上轮模型输出也可能已有缓存，不能全部算作必然未命中；也不能沿用旧版本“任意 64-token
前缀必命中”的假设。[官方缓存规则](https://api-docs.deepseek.com/guides/kv_cache/)

命中率不等于费用收益。假设历史已缓存、每轮新增 2K：保留 80K 历史时命中率为 97.56%，
保留 20K 时为 90.91%。按本批 Pro 峰时命中 $0.044/M、未命中 $1.32/M，两者输入费
分别为 $0.00616、$0.00352；后者命中率更低，输入费却少 42.86%。这是说明性假设，
不含摘要和切换成本，不是本轮实测收益。[官方价格](https://api-docs.deepseek.com/quick_start/pricing/)

## 已定位的问题

1. **新 A 连续重新装箱。** 首次摘要的两次尝试均返回工具调用，随后退避 300 秒；
   输入继续增长。32K 输出预留使主输入硬预算降至 94,208，压力目标为 75,366。
   [Planner](../src/bot/core/context.py) 用完整计数发现超硬预算后逐组删除，降到硬预算
   以下就停止，没有保证降到压力目标。下一轮稍有增长就可能再次改写历史前缀。
   第 46、47、50、51、52 步各有约 82–90K 输入，却都只命中 3,840 tokens。
   这五步贡献 420,318 未命中；全部 7 次重新装箱贡献 432,135，均位于首次失败与首次成功发布之间。
2. **摘要发布改变前缀。** 新摘要位于保留历史之前，摘要与历史起点改变后，尾部原文
   相同也不保证命中。CURRENT 四次首请求约 54–55K、新 A 两次约 31K，均只命中约 4K。
   A 减少了切换时需要重算的输入，不能消除切换成本。
3. **独立摘要较冷。** A 摘要请求命中为 96.14% / 94.82%，前缀复用已有效。B 叶子整体
   命中 12.65%，根合并为 0%；摘要占其全部未命中的 34.76%。CURRENT 三次有 usage 的
   首次生成整体命中 0.57%，另一次重试为 99.78%，不能只报告热重试。
4. **收尾重建请求。** [Agent 收尾](../src/bot/core/agent.py) 重新组装历史并设置 `tools=[]`，
   与正常请求的工具定义和消息视图不同。三个收尾请求仅命中 512 或 768 tokens，产生
   约 31–71K 未命中。代码与观测相符，各字段的独立影响仍需请求对照。

## 开源实现与对应建议

| 项目与固定版本 | 核实的做法 | 我们可借鉴的部分 |
|---|---|---|
| Hermes `110736c0` | 默认关闭每轮微压缩；可选 proactive prune 有最小回收量及再次增长门槛 | 一次腾出足够空间，减少连续前缀失效；单纯失败冷却不足以解决问题 |
| Hermes `110736c0` | 稳定提示与临时上下文分开；记忆写磁盘不逐步重建已有系统提示快照 | 固定前缀，动态状态尽量追加；我们已有基础排序，需验证实际请求 |
| OpenCode `b3f1a96c` | 可选 prune 保护最近约 40K 工具输出，待删除量超过 20K 才批量提交 | 批量裁剪、最小收益门槛；这些是该项目的估算参数，不直接照搬 |
| DeepSeek Harness `c291e79` | 摘要重放 system、tools、消息前缀，尾部追加压缩指令，默认沿用路由模型 | A 方向一致；不代表发布后尾部缓存仍保留 |
| OpenCode `b3f1a96c` | 按 Provider 设置缓存边界和 session cache key | 按服务能力适配；给 DeepSeek 随意增加缓存参数不能解决前缀改写 |

建议先做两个小改动，分别验证：

1. **减少 A 失败和连续装箱。** 摘要保留 tools，但显式 `tool_choice="none"`，验证服务
   行为及缓存影响。硬超限裁剪按完整计数一次降至现有约 75K 压力目标，冻结保留边界，
   后续追加，避免每轮移动起点或旧项重新进入请求。必须保留工具原子组、用户锚点、
   必要 Skill 和未消费资源，不能满足时显式失败。
2. **收尾保留请求前缀。** 保留最后合法请求的工具定义，补齐已经执行的工具结果，尾部
   追加收尾要求并设 `tool_choice="none"`；不回放损坏的半截调用，执行器仍禁止执行工具。
   信息齐备的终止情况也可采用无模型的确定性收尾。

其他措施随后考虑：已发布摘要保持不变；大工具结果在首次进入上下文前限量或 query；
B 减少重复叶子和无用后台生成。工具排序、常规动态提示尾置已实现，不能再当作新增收益。
一次性交付的语义约束也不能为了缓存而取消。

验证先冻结真实失败前的状态，比较原/新收尾形状及裁剪后的连续请求，再做同题配对重复。
观测 system/tools 哈希、首个变化的历史位置、最长公共输入 token 前缀及裁剪边界；
公共输入前缀不等于服务端可命中上界，但能帮助区分本地改写和服务缓存行为。无需记录完整敏感正文。
主要指标为总 miss tokens、输入费加摘要/收尾费、改写后的连续冷请求数及任务验收，命中率
作为辅助指标。目前未做优化后的真实对照，不承诺从 85% 提升到某个固定比例。
