# V4 Flash：四种压缩策略的三次完整任务复测

日期：2026-09-13。任务为 `path-tracing-reverse`。

结论：在 12 场有效比较中，双路径三次均正常交付且通过完整官方验收，CURRENT、A、B
均为 0/3 次完整任务通过。优先继续验证双路径；这不是跨任务成功率估计。
另有一场通过验收的 CURRENT 因宿主机休眠被预先判定排除并补跑，原始数据完整保留。

## 预先固定的测试方案

在首轮 CURRENT、A、B、双路径 `a_fallback` 各一次的基础上，各补两次完整任务：
原计划新增 8 场，累计每组 3 场、合计 12 场。执行中第三轮 CURRENT 遇到宿主机休眠，
因此额外补跑一场：实际新增 9 场、累计执行 13 场，其中 12 场进入有效比较。
这个规模用于检查单次结果是否重复出现，
不足以估计稳定成功率，也不代表在三个不同任务上验证。新增测试是在看过首轮结果后
决定的，所以同时报告新增两场与累计三场，保留所有失败和缺失 usage。

串行执行，不人为预热缓存，不向模型注入题解、验收源码或其他场次的经验。
第二、三轮采用首轮顺序的循环移位，在发起任何新增模型请求之前写入冻结清单。
这让每组在三轮中处于不同位置，但四组只有三轮，不能声称完全消除了顺序或缓存影响。
顺序索引不是模型 seed；temperature=0 也不保证完整轨迹可重复。

| 轮次 | 执行顺序 | 性质 |
|---|---|---|
| 1 | B → 双路径 → A → CURRENT | 已完成的先导测试 |
| 2 | 双路径 → A → CURRENT → B | 新增复测 |
| 3 | A → CURRENT → B → 双路径 | 新增复测 |

直接引用并校验首轮的 wheel、tokenizer、四份配置和八个任务文件，不重新构建运行包。
运行时仍为 `99d70d8`，wheel SHA-256 为
`d36fd61bd44499567262faeb50c834dc58e7768b471d72a1dc4035ad6963ddd2`。
新增脚本仅负责排列场次、只读审计及汇总，没有中途修复工具循环或修改压缩逻辑。

- 主模型及摘要模型均为 `deepseek-v4-flash`，temperature=0、thinking=disabled。
- 主请求输出额度 32,768；CURRENT/A/B 的摘要为 8,192，双路径前缀继承 32,768、
  独立兜底为 8,192。保留被比较实现的差异，不声称摘要参数全部相同。
- 软件窗口 131,072，主输入预算 94,208，压力线约 75,366；A/B/双路径低水位 40K。

| 组别 | 摘要如何生成 | 关键限制与失败处理 |

| CURRENT | 专用角色 + 旧摘要/原始历史 JSON，增量压缩并周期性从原文重建 | 摘要请求上限 60K，按 80% 规划；支持修复、精简及缩小覆盖范围 |

## 结果口径

主要指标为每场完整任务的官方验收结果：三项测试全部通过且 reward=1。
同时列出正常完成、单次输出触顶、步数耗尽、时间耗尽及基础设施异常。
费用包含所有主请求、摘要、兜底、失败请求的已知 usage 和后台未发布节点。
缺少 usage 的请求费用标记为未知，已核实金额只作为下界。

每组给出通过数、三场逐场结果，以及费用和耗时的中位数、范围。
成功场费用单独列出，不能因失败场提前结束而判定该策略更省钱。
缓存率使用全组的 `Σcache_hit_tokens / Σprompt_tokens`，不平均百分比。
摘要发布数、启动数、失败原因、前缀/兜底采用路径以及发布后的首轮续跑单独统计。
启动数对应 `context.compaction.started`，不把失败退避期间每次高压力检查都算成新尝试。
同状态的 before/after 预算用于净释放率，实际下一次请求输入另列。

## 环境异常与替补规则

第三轮原始 CURRENT 执行期间，宿主机发生多次 Idle Sleep / maintenance sleep，
系统日志记录的休眠时长合计 2,901 秒（48.35 分钟）。这会污染墙钟耗时和缓存条件。
在该场 Harbor 官方验收结束前，已将排除理由、事件文件哈希和休眠窗口写入
`sleep-contamination.json`，决定保留原始结果但用相同配置补跑一次。
原始这场后来通过了全部三项官方测试；仍按先前的环境规则排除，不根据成败更改规则。
不能简单从总耗时中减掉 2,901 秒后把余数当作准确的活跃执行时间。

替补 CURRENT 排在原计划剩余场次之后，使用相同的 wheel、配置、任务文件和预算，
只改变场次目录和执行时间。汇总器校验替补指向的原始清单哈希和全部实验控制，
将原始结果保留在 `excluded_runs`，替补结果进入第三轮的有效统计。
后续运行使用随测试进程自动退出的 `caffeinate -i -w <pid>`，避免再次空闲休眠，
没有更改系统长期设置。由于替补改变了顺序，缓存及时间差异仍按观察结果解释。

## 已核实的故障链路

### 重复工具调用与压缩失败需要分开判断

CURRENT 三次有效场均以 `model_output_limit` 停止，三场的摘要请求却全部成功。
替补场第 49 次主响应生成了 32,768 个 completion tokens、77,318 字符普通正文，
没有工具调用，`finish_reason=length`；并非摘要请求输出被截断。其源码能编译，
但官方图像相似度为 0.91116，未达到 0.995。单次主输出额度已经是 32K，
这次复测没有证明再提高额度就能解决问题。

A 第二轮同一条 `strings` 过滤命令执行 230 次，CURRENT 第二轮同一段反汇编查询
执行 186 次。循环都在首次摘要发布前已经开始；后续摘要甚至明确要求停止重复，
主模型仍继续。因此不能把这些失败全部归因于摘要遗忘，也不能把高缓存率视为任务收益。
现有进展识别把新 `process_id` 放入证据键，相同输出的新进程仍可能被判成弱进展，
而弱进展使无进展计数回落。测试中没有修改这条运行逻辑。

A 第三轮较前两轮有实质进展：生成了能编译的 C 源码，官方通过 2/3 项，
但图像相似度仅 0.92033，未达到 0.995。后段同一组图像/日志检查又重复 80 次。
这能证明交付仍失败，不能单凭结果证明图像偏差由摘要中的事实错误造成。

### A 的完整输入与 B 的不可拆分组

A 第三轮先发布三份摘要，随后两次压缩各尝试两个请求，最终分别因摘要估算
4,494、4,298 超过 4,000 而失败。再之后，组装的摘要输入增长到 122,790 和
129,858，超过 118,784 的摘要请求输入预算，在调用模型之前被拒绝。
A 从裁剪之前的完整 frame 组装摘要，主请求即使还能通过裁剪满足自己的预算，
摘要请求仍可能超限；也可能无法复用上一条已裁剪请求的完整前缀。

B 第二轮先遇到 `fixed_context_exceeds_low_water`，随后四次根摘要尝试遇到
`atomic_group_exceeds_leaf_budget`。单个完整工具调用组超过 24K 叶节点额度，
当前 B 没有拆分或兜底处理，整场未发起付费摘要请求、未生成节点、未发布根摘要。
它没有长时间重复同一个命令，但在时间预算内未留下验收要求的 C 源码。

B 第三轮则是另一条失败链：源码存在且能编译，图像相似度 0.92136，官方仍为
2/3 项。共有 18 个摘要请求：11 次叶节点成功、1 次合并成功、6 次合并失败。
六次失败均覆盖 `[1, 105]`，正文估算分别为 5,587、5,729、5,719、5,479、
5,456、5,436，均以 `stop` 正常结束后被 4,000 门限拒绝，没有输出长度截断。
12 个持久化节点中，只有 4 个进入已发布摘要的祖先链，另外 8 个叶节点未被发布采用，
已知费用 $0.07179，已包含在摘要费用 $0.17141 和整场费用下界 $1.12983 内。

A/B 共用的 `summarize()` 对同一份 request 最多调用两次，
没有把超限反馈改写进下一次请求，也没有在这里缩短来源或专门做正文精简。
因此“重试过”不等于采取了针对长度失败的纠正措施。CURRENT 自己的修复/精简流程
与这一实现不同；双路径则切换请求组装方式，但也不能保证第二份摘要一定低于门限。

双路径第三轮展示了两种结果：前六次均通过前缀发布；第七次前缀估算 4,442 超限，
独立请求生成 3,826 的摘要后成功发布；第八次前缀 4,675、独立摘要 5,292 均超限，
保留旧摘要继续执行。上述三份被拒绝的摘要均以 `stop` 结束，不属于输出截断。
主模型早期重复 `strings -n 4 /app/mystery` 30 次后
离开循环，最终在第 151 步正常完成，官方 3/3 项通过。兜底救回过失败，但不是必然成功；
一次压缩失败也不必然导致任务失败。

### 压缩失败后的裁剪既影响缓存，也消耗时间

B 第二轮出现 51 次主请求裁剪。最近一次 `run.progress` 到 `context.packed`
的观测区间合计 1,076.3 秒，约占 Agent 墙钟时间 61.1%；这些区间没有付费摘要
调用等待。一次只读容器观测显示约 100% CPU。源码中的 packing 循环每移除一组
历史后会重新计数整个请求，与该现象一致，但这些证据不是 CPU profiler，不能把
全部区间精确归因于 tokenizer。A 的相同区间还包含同步摘要请求，不能照搬此解释。

新方案第二轮第三次压缩的前缀与兜底分别因 4,407、4,090 超过摘要门限失败，
进入 300 秒退避。此后 13 次主请求裁剪中，6 次改变被删历史集合的请求缓存率
只有 8.78%，7 次保持同一集合的请求为 99.76%。这是上下文变化与未命中的关联，
不是供应商内部缓存追踪。它解释了为何该轮步骤更少，费用却未比首轮明显降低。

B 第三轮的现象更明显：21 次裁剪中，19 次改变被删历史集合的主请求缓存率为
8.17%，已知费用合计 $0.70963，占整场已知费用约 62.8%；另外两次集合未变的
请求缓存率为 99.33%。因此其主要额外开销并不只在摘要请求本身，还在压缩失败后
反复变化的主请求。该轮准备区间合计 681.9 秒，包含同步合并等待，不当作纯本地 CPU 时间。

## 选型与后续验证

就这道任务，优先保留双路径继续验证，CURRENT 留作对照；暂不优先推进单独 A 或 B。
三次复测已足以揭示“只提高摘要缓存率”或“只看发布成功”无法预测交付，现阶段不必
继续原封不动地把同一道题扩到五次、十次。下一步先处理重复工具调用的稳定指纹、
长文本无工具输出，以及压缩失败后的请求准备开销，再用另一种任务检验是否仍有收益。
如果要重测 A/B，应先针对已复现的错误处理超大原子组和长度失败后的纠正措施。

本实验比较四份实际实现的完整组合：摘要输入组装、额度、发布门限和回退行为
均可能不同。因此即使某组更容易通过，也不能把差异单独归因于前缀缓存、兜底、
标题兼容或某一句提示词。这需要后续单变量消融。重复同一道题三次只适合发现
明显的波动和故障链路，不能解释为跨任务成功率，也不能把三次全通过写成稳定 100%。
发布摘要的原文哈希、父节点和用户锚点检查属于可追溯性验证，不是摘要事实正确率。
