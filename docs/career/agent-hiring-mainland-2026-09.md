## 1. 调研结论与适用范围

09-10 原始样本选取字节跳动、阿里巴巴、腾讯、百度、京东、美团、快手、小红书 **8 家公司**的 12 条招聘样本，其中小红书团队公告包含两个岗位。09-15 另补充小团队岗位，不并入原始样本数。公司内部岗位差异很大，以下结论针对这些 JD，不代表全公司统一标准，也不构成整个招聘市场的比例统计。

从这些样本归纳，Agent 工程岗位关注的主线是：**将模型、上下文、工具和任务状态组织成可交付的系统，并通过评测持续改进可靠性、效果和成本。** 规划、工具调用、RAG 等是常见能力入口；上下文管理、失败恢复、状态一致性和可观测性可以成为项目深度的证据。具体依据见第 2 节各岗位。

结合 bot 已有证据，适合优先呈现的定位是：

> **Agent 运行时与上下文工程：面向代码和终端长任务，建设上下文预算、可恢复压缩、工具执行、会话状态及评测能力。**

这是项目匹配建议，不等于已经满足岗位的工作年限、生产规模或算法训练要求。

### 来源与时效

- **A：招聘官网正文**。本次直接读到具体 JD。
- **B：招聘者或团队直接发布**。例如牛客上标注企业身份的招聘者、团队开源仓库招聘公告；身份描述来自页面，未额外核验任职关系。
- **C：第三方转载**。读取到 JD，但官网正文因动态渲染、访问失败等未能独立核对。找到原始链接时一并记录。
- 发布日期、收录日期、投递时间各按页面原字段记录，不互相替代；未能读取官网正文不等于岗位关闭。
- 本文分析招聘要求，不保证仍有 HC。美团样本在原采集时曾被平台标记过期；09-15 读取时未见该标记，官网仍未取得正文，因此继续作为历史要求样本，不据此判断恢复招聘。
- 未将聚合平台的 AI 薪资估算、面试建议、公司评分和自动生成岗位解读作为证据。

## 2. 具体招聘样本

### J01｜京东：软件开发岗（AI 应用方向）

- **来源 A**：[京东招聘官网](https://zhaopin.jd.com/web/job-info-detail?requementId=220736)。北京，C 端 AI 技术部；官网发布时间 2026-07-14，要求 3 年以上相关工程经验。
- **关注点**：将业务需求拆成规划、工具、路由和上下文模块，同时处理权限与失败兜底；接入知识库；建立离线回归、线上质量与调用链观测。
- **读法**：岗位同时考查 Agent 机制和后端交付。面试准备应包含异常路径、验证方式和服务设计。
- **bot 对应**：C01—C04、C06—C09、S01—S03、E01、E04。

### J02｜百度：北京－智能体算法工程师（J101017）

- **来源 A**：[百度校招官网](https://talent.baidu.com/jobs/detail/GRADUATE/02f73086-be71-4d09-8d6e-f1c6981b8b48)。北京，本科及以上；官网日期 2026-07-21。
- **关注点**：全链路 Agent 设计，规划、意图、工具、记忆与多智能体协同；把完成效果、效率、资源消耗一起纳入评估。要求理解相关推理范式及大模型原理，兼顾算法和落地。
- **读法**：岗位名有“算法”，但职责也覆盖系统建设；需要逐项确认自身算法基础，不能仅凭项目是 Agent 就推断匹配。
- **bot 对应**：C01—C16、M01—M03、E01—E04；训练经验需另行证明。

### J03｜阿里巴巴集团：AI agent 开发（2027 届）

- **来源 B**：[牛客招聘页面](https://www.nowcoder.com/jobs/detail/454084?pageSource=5015)。页面发布者标注“阿里巴巴集团·高级开发”；上海、本科、2027 届，投递期 2026-07-17 至 2026-10-17。
- **关注点**：规划、上下文、记忆和工具底层模块；RAG 与工作流；异步和缓存；权限、沙箱及成功率、延迟、Token 等观测指标。
- **读法**：上下文工程在招聘要求中有直接对应。岗位还包含 Java 服务端和分布式工程内容，需要结合完整技术栈判断。
- **bot 对应**：C01—C14、R01—R06、S01—S04、E03—E04。

### J04｜阿里巴巴：AI agent 平台研发工程师（校招）

- **来源 C**：[职先机转载](https://jobs.ultraai.site/jobs/alibaba_campus/campus:199907780019)；[原始校招链接](https://campus-talent.alibaba.com/campus/position/199907780019)仅返回页面外壳。转载收录于 2026-08-06，北京／杭州／上海。
- **关注点**：Agent 的运行、通信、存储、调度和反馈基础设施；Prompt、Skill、记忆的生命周期以及状态持久化；看重异步 IO、并发、存储和底层源码理解。
- **读法**：偏平台与系统工程。会话、任务、状态和数据抽象的设计，可能比前端功能数量更相关。
- **bot 对应**：C13—C14、S03、M01、E04；进程内调度不能写成分布式平台经验。

### J05｜字节跳动：Agent 后端开发工程师－Aime（校招）

- **来源 C**：[JDWatch 转载](https://www.jdwatch.work/jobs/jed9eyjyx)；[转载所附官网链接](https://jobs.bytedance.com/campus/position/7668351902195009845/detail)本次未能读取。页面标注 2026-07-30，2027 届，北京／上海／杭州。

- **读法**：这是与 bot 的模块结构接近的工程类样本。可以同时展示执行链路和产品交付，但不要省略计算机基础。

### J06｜腾讯：AI Agent 后台开发工程师

### J07｜腾讯：智能运维 AI Agent 平台－资深软件开发工程师

### 几个容易混淆的概念

这些区分用于组织自身项目材料，不是给所有招聘团队强行统一术语：

- **上下文工程**：选择、组织、压缩和恢复模型每次实际看到的信息。长期记忆是其中一部分。
- **Agent 运行时／Harness**：范围通常更广，涉及执行循环、工具、状态、控制与评测。招聘文案中用法并不完全一致，面试时应先说明自己实现的范围。
- **RAG**：需要具体的数据与检索链路证据。bot 现有 Markdown 记忆和关键词 Router 不足以证明向量库、混合检索或重排序经验。
- **Agentic RL**：围绕轨迹、奖励和参数更新训练策略。调用模型完成任务、保存轨迹或运行基准，不自动构成 RL 训练经验。
- **运行时基础设施与训练基础设施**：会话／任务调度与 GPU／分布式训练是不同系统层次；不能因为都叫 Infra 就互换项目描述。

## 4. bot 素材的建议排序

### 第一组：上下文工程的主线

按“预算 → 信息选择 → 压缩恢复 → 验证”的顺序讲述，比平铺功能更容易让面试官理解设计原因。

1. **C01＋C02＋C12**：统一上下文建模，区分持久历史和请求视图；预算覆盖消息与工具定义，使用官方 Tokenizer 校准。
2. **C03＋C04**：将大工具结果外置，按需恢复证据，并在消费后收回长正文。
3. **C06＋C07＋C09＋C14**：维护压缩发布一致性、工具协议完整性与执行依赖，处理失败后的恢复。
4. **E03＋E04**：通过真实请求回放、质量门禁、Token 与延迟观测证明取舍。

对应的候选描述，可按实际个人贡献选择：

> 负责代码与终端 Agent 的上下文管理模块，统一建模会话历史、工具结果、项目指令和运行状态，分离持久事实源与模型请求视图，实现消息与工具定义的预算分配及按需加载。

> 设计大工具结果外置与可恢复引用机制，支持按范围或关键词读取证据，并在有效消费后将正文回收为短回执，控制长任务中的重复上下文输入。

> 实现事务化摘要发布与版本回退，维护工具调用和结果的原子性，补齐压缩后的执行依赖恢复及发送前校验；通过故障注入和请求回放验证异常路径。

这些句子是候选稿；详细实现、验证范围和提交归属以 [C01—C14 素材](resume-materials.md)为准。

### 第二组：运行时与系统工程的支撑

适用于 Agent 后端或平台岗位，避免整份项目经历只围绕 Token。

> 构建支持流式模型响应和异步工具调用的 Agent 执行链路，完善长命令托管、增量输出、进程组取消及中断恢复，并持久化会话事件与任务状态。

> 建设隔离执行与独立产物验收流程，结合文件、JSON 和容器验证器检查任务结果，记录调用轨迹、用量、耗时与失败类型，为 Agent 迭代提供可复现证据。

选择 R01—R04、S03、E01—E04。具体测试和性能指标仍应引用原素材，不将设计目标写成已达成的生产 SLA。

### 第三组：按目标岗位增补

| 目标方向 | 可增补素材 | 为什么有帮助 |
|---|---|---|
| AI Coding／研发效能 | M02—M03、E01—E02、W03 | 能展示子任务边界、worktree 隔离、补丁交付与独立验收 |
| Agent 应用后端 | R01—R06、S03、W01—W02 | 能展示会话、任务、流式交互、断线恢复等完整路径 |
| Agent 平台／运行时 | C13—C14、M01、S03、E04 | 能展示生命周期、调度、持久化和观测设计 |
| 业务工具型 Agent | D01、S01—S02、W03 | 能展示领域工具、执行边界和实际产物 |
| Agent 算法／训练 | E01—E04、H01—H03 作为辅助 | 可证明实验能力，核心仍需算法或训练经历 |

## 5. 指标怎么使用

当前最容易清楚解释的上下文量化素材是 **C12 的输入计数校准**：在 517 条 DeepSeek V4 Flash 非思考模式历史请求中，最大绝对误差从 41,806 降至 3 tokens。这是离线历史请求核对，并非 517 个独立任务，也不是未来所有请求的误差保证。详见 [输入 Token 校准](../architecture/input-token-calibration.md)。

另外两类数字可以用，但必须保留测量对象：

- **C03 的表示缩短**：说明大工具结果或普通工具结果的内联字符变化；不改写成同等比例的 API Token 或账单节省。
- **C05 的缓存收益**：明确是历史布局的受控离线缓存模拟及折算成本；不将其作为当前布局的线上费用。

优先采用“优化对象＋对照条件＋结果＋质量检查”的表达。任务成功率、端到端延迟、每成功任务成本等更完整指标，可以基于已有 E01—E04 评测继续取得，未取得前不填写推测数字。

09-13 可补充两组更适合被追问的材料，均保留各自实验版本：

| 材料 | 可以讲的结果 | 面试时必须一起说明 |
|---|---|---|
| [Flash 四策略三轮复测](../evaluations/context-strategy-flash-repeats.md) | 双路径在同一题三场有效运行中均正常结束并通过完整官方验收；其他三组各为 0/3 | 实际运行 13 场、有效比较 12 场；不是三个不同任务，也没有证明单独由兜底造成提升。运行包为 `99d70d8`，早于当前重复控制与正文门限调整 |
| [重复工具执行修复](../evaluations/repeat-guard-validation.md) | 新 PID 不再被误认作新证据；小任务续跑 4/4 完成，强制模式每场少执行一次重复读取 | 前四个模型响应由脚本固定；费用略增，未证明公开基准通过率改善。历史 230 次重复对应第 14 步限制是离线反事实，不能写成实测省掉 216 次 |

这些材料适合证明“能定位问题、设计验证、限制结论”，不能只取最亮眼的数字。进一步的问答见 [F04](#followup-failure)、[F06](#followup-evaluation)和手册 [Q23—Q24](context-management-interview-guide.md#q23-dual-path)。

## 6. 值得补充的证据，以及当前不能直接声称的能力

按申请工程类岗位的匹配价值，建议依次考虑：

1. **扩大完整任务的对照评测**：已有单题四策略三轮比较；下一步固定多种任务、模型、预算和验收规则，补足跨任务泛化与因果消融，联合展示结果、恢复情况、延迟与实际用量。
2. **一个可演示的长任务案例**：保留原始轨迹，展示工具产生长输出、预算变化、压缩与继续执行、最终产物验收，让上下文工程的作用具体可见。
3. **按目标 JD 补工具生态或知识检索**：需要 MCP 的岗位补真实客户端／服务端接入和错误处理；需要 RAG 的岗位补文档处理、检索评测、更新策略。二者应独立验收。
4. **按岗位补框架实践**：自研框架能说明原理，但不能把源码调研写成熟练使用 LangGraph／LangChain。若岗位明确要求，补一个包含状态恢复、工具错误和评测的实际案例。
5. **平台方向再补服务规模证据**：并发负载、持久队列、资源隔离、幂等和恢复；有了实际实现和测试后再描述相应能力。

当前仓库不能单独证明：分布式多 Agent 平台、生产级 Kubernetes 部署、通用 MCP 接入、向量检索与 GraphRAG、大模型 SFT／RL 训练、线上客户规模及业务增长指标。

“尚无证据”用于限制简历表述，不要求为投递所有岗位把全部能力做一遍。先按岗位类型选取已有强项，再决定是否补充。

<a id="followup-ownership"></a>

### F01：项目这么大，哪些是你做的？用了 AI 写代码吗？

**考查点：** 所有工程岗位都可能核对个人贡献；这里是面试准备判断，不归属于某条 JD 的原话。

**可口述回答：**

> 我主要负责【实际模块】，其中独立完成的是【具体设计、实现或实验】，与其他模块协作的是【接口或联调范围】。以【本人参与的一项修复】为例，我可以展开它的输入输出、关键约束、被否决的方案和验证过程。AI 辅助了【实际使用环节】，最终取舍、代码审查和验收由【实际责任人】完成。我会据此说明自己的贡献，不用生成代码量或提交作者代替职责证据。

填写时可从上下文预算、摘要发布或重复执行检测中选一项；不要在面试时原样念占位符，也不要把没有参与的案例填成主导经历。

**继续追问：**

- **“拿一个提交证明你理解。”** 选一个实际参与的修复，先解释旧版本为何失败，再画出新数据流，最后展示一个旧版失败、新版通过的回归，以及一个防止误拦的反例。不要仅展示提交作者或测试总数。
- **“没有 AI 你能维护吗？”** 现场追踪一个函数调用链、解释失败状态并修改一个边界条件，比声称完全独立更有说服力；若没有相关独立实践，就明确欠缺这一证据。

**证据入口：** [贡献筛选模板](resume-materials.md#14-从素材继续补全个人经历)、[重复控制验证中的回归与反例](../evaluations/repeat-guard-validation.md)。

<a id="followup-framework"></a>

### F02：为什么自研 Agent？什么时候用固定工作流？

**岗位关联：** J03—J05、J08、J11 的运行编排、工作流与框架实践。

**可口述回答：**

> 这个项目把会话位置、工具原子组、运行中补充要求、摘要事务和引用权限放在同一条可测试链路里，自研有利于明确这些约束。代价是协议适配和维护成本都由项目承担。面对新需求，我会先看现成框架是否能表达这些约束。步骤稳定、验收明确的流程适合固定工作流；下一步依赖未知环境和工具反馈的部分，再交给模型决策。

**继续追问：**

- **“你真的熟悉 LangGraph／LangChain 吗？”** 分别说清实际开发、读源码和只看资料的范围。bot 自研经历不能替代框架项目经验；可把同一最小任务在框架中实现，比较中断恢复、工具错误与观测能力。
- **“用了 ReAct 就有规划能力吗？”** 工具反馈循环不保证计划正确。bot 的 TODO 是持久任务状态，既不是正确规划的证明，也不是完成验收；关键步骤仍需执行结果和独立检查。

**证据入口：** [手册 Q21](context-management-interview-guide.md#q21为什么自己实现没有直接套现成框架)、[任务计划工具](../../src/bot/tools/plan.py)。

<a id="followup-cost"></a>

### F03：你说做了成本优化，究竟省在哪？

**岗位关联：** J02—J03、J06、J10 的效率与资源成本。

**可口述回答：**

> 我先拆分输入、输出、摘要、失败重试和证据回读，再看优化影响了哪一项。大输出外置减少的是请求中的表示长度，稳定前缀影响可复用输入，二者不能直接相加成账单节省。历史 Fast 的 35.02% 是受控离线折算成本下降；真实任务要把失败请求和压缩开销算进去，并同时看独立验收和耗时。

**继续追问：**

- **“缓存率更高为什么还可能更贵？”** 分母和请求次数都可能增加。应报告加权缓存率 `Σ命中输入 / Σ总输入`、总用量及质量，不能只比较每次请求的百分比。
- **“每成功任务成本怎么算？”** 先声明口径：成功场平均费用只统计成功场；批次总费用除以成功数则把失败代价也算进来。相同任务分布和预算下才适合比较，成功数为零时该比值不可估，usage 缺失时只报已知下界。

**证据入口：** [历史布局实验](../evaluations/context-cache-benchmark.md)、[真实策略费用口径](../evaluations/context-strategy-flash-repeats.md#结果口径)。

<a id="followup-failure"></a>

### F04：讲一个最难的故障，你怎样证明修复有效？

**岗位关联：** J01、J05—J09 的运行稳定性、容错与失败迭代。

**可口述回答：**

> 一个适合展开的故障是 Agent 不断重复同一条命令，却没有被识别为停滞。追踪发现，同样的结果因为每次启动的新进程标识被当成新证据，重复的弱进展又抵消停滞计数。修复把执行身份和结果证据分开，使用终态、退出码及累计保留输出的稳定摘要判断新信息，再增加有状态的重复检测和执行前限制。它还要识别文件更新和存活进程，避免把合法重试、等待和回读一起挡住。

**继续追问：**

- **“为什么不数连续相同的工具名？”** 同名工具可以访问不同文件，同一命令也可能面对已变化的资源；PID、耗时又会造成虚假的差异。需要区分操作语义、结果证据和资源版本。
- **“现在已经不会循环了吗？”** 尚不能这样说。默认仍为 `observe`；`enforce` 只覆盖已适配工具。两项关键回归在旧版失败、新版通过；四场小任务续跑通过，但不能据此保证任意 shell、副作用操作或公开长任务都已解决。

**证据入口：** [完整验证与开销边界](../evaluations/repeat-guard-validation.md)、[手册 Q24](context-management-interview-guide.md#q24-repeat-guard)。仅在实际参与后使用“我定位／修复”。

<a id="followup-tradeoff"></a>

### F05：有没有实验推翻你原来的设计判断？

**岗位关联：** J02、J09、J11 的实验、迭代与工程判断。

**可口述回答：**

> 压缩设计里，一个重要教训是格式更严格不一定让任务更可靠。精简提示的早期实验中，七次标题格式回退使平均摘要费用增加 102.8%，但目标旧错误没有稳定消除。后来单独修复标题兼容，再验证历史候选。另一项调整是取消完整摘要正文的 4K 发布门限：完整的长摘要仍要检查恢复后的总输入预算，生成被截断的摘要仍然拒绝。这样分别处理格式、长度、语义和容量问题。

**继续追问：**

- **“取消限制后质量提高了吗？”** 本地回归证明完整长摘要可发布、截断或超预算仍拒绝；该变更没有新的整题模型对照，不能声称提升了通过率。
- **“怎样避免为每个失败都加规则？”** 先判断能否稳定复现，检查规则是否直接保护协议或状态不变量；涉及语义收益时保留对照与反例，达不到证据要求就不扩大结论。

**证据入口：** [精简提示实验](../evaluations/compaction-fidelity-evaluation.md)、[标题兼容](../evaluations/compaction-heading-compatibility.md)、[正文门限调整](../designs/compaction-summary-body-limit-removal.md)。

<a id="followup-evaluation"></a>

### F06：双路径 3/3 通过，能证明方案更好吗？你如何验收？

**岗位关联：** J01—J03、J08—J11 的效果评估与独立质量检查。

**可口述回答：**

> 它支持继续验证双路径，但证据只来自同一题三场有效运行。四组共 12 场有效比较，另有一场因宿主机休眠被按原规则排除并补跑。双路径三场正常结束且通过完整官方验收，成功图像还经过独立重放核对；其他组有产物部分通过，不能概括成完全没有进展。提示词、路径和输出额度并非单变量一致，3/3 不能证明兜底单独带来提升，更不能宣称跨任务成功率是 100%。

**继续追问：**

- **“如何进一步证明因果？”** 从相同中间状态分叉，固定模型、预算和工具，分别只改提示词、兜底或组装；短程观察之后仍做整题验收，并加入多种任务与重复样本。避免把三次同题当成三个独立任务。
- **“模型说完成、600 个测试通过，不够吗？”** `completed` 是运行状态；单元和集成测试检查运行时机制。任务结果还需要文件变化、JSON Schema 或独立容器测试；基础设施和验收器故障要单列，不能混入模型能力失败。

**证据入口：** [三轮复测](../evaluations/context-strategy-flash-repeats.md)、[因果边界](../evaluations/context-strategy-flash-causal-analysis.md)、[任务验收实现](../evaluations/evaluation.md)。

<a id="followup-platform"></a>

### F07：只有 SQLite 和 asyncio，怎么扩成多人使用的平台？

**岗位关联：** J03—J07、J09 的并发、存储与平台能力。

**可口述回答：**

> 当前是本地优先运行时，进程内 Worker Pool 和 SQLite 持久状态不等于分布式平台。我会先明确并发量、任务时长、隔离要求与恢复目标，再分离接入、任务调度和执行 Worker。需要增加持久队列、任务租约、结果版本校验、资源配额和租户授权；大产物可以独立存储。这里是扩展方案，项目还没有相关多机负载或 SLA 证据。

**继续追问：**

- **“Worker 执行完外部操作，写结果前崩了怎么办？”** 重投任务可能重复副作用。对支持的外部系统用幂等键或结果查询；否则标记结果未知，先核对或补偿。数据库事务不能跨任意外部命令提供 exactly-once。
- **“asyncio 能解决什么，不能解决什么？”** 它便于并发等待模型网络请求和子进程；CPU 密集操作、阻塞调用、队列无界增长和并发写冲突仍需分别治理。不能用异步语法推导出吞吐提升数字。

**证据入口：** [现有 Worker Pool](../../src/bot/subagents/pool.py)、[会话存储](../../src/bot/sessions/store.py)、[实现范围](../architecture/implementation-status.md)。

<a id="followup-subagents"></a>

### F08：为什么用多 Agent？子 Agent 写错或相互冲突怎么办？

**岗位关联：** J02、J08—J09、J11 的协同、子任务隔离与产物契约。

**可口述回答：**

> 我会把输入和产物契约清晰、可以独立验证的任务拆出去；共享状态密集的小任务继续串行。bot 子任务有独立会话、工具白名单和 Skill 状态，父历史不会完整复制。写任务可放在独立 worktree，返回补丁后由父任务核对基线、检查并验收。当前委托深度是一层，调度在主进程内，主进程退出后不承诺后台任务继续执行。

**继续追问：**

- **“worktree 就隔离了吗？”** 它隔离代码工作副本，不隔离宿主网络、进程和凭据。工具权限与必要的容器／操作系统隔离仍是另一层责任。
- **“一定更快吗？”** 不一定。模型调用、启动、重复读取和集成冲突都有成本。应比较同一任务下的完整交付时间、费用和验收结果；仓库没有普遍的多 Agent 加速结论。

**证据入口：** [自定义 Agent 协议](../guides/custom-agents.md)、[M01—M03 素材](resume-materials.md#7-多-agent-协作素材m01m03)。

<a id="followup-tools"></a>

### F09：工具调用怎么做到可靠？Prompt Injection 和重试怎么处理？

**岗位关联：** J01、J03、J06、J10 的工具、权限与异常恢复。

**可口述回答：**

> 工具 schema 只是接口描述。真正执行前要校验参数、路径和权限，需要时取得审批；执行后保留退出状态、输出及调用对应关系。文档中的恶意指令即使被模型接受，也不能因此获得更高工具权限。模型请求的瞬态重试和外部工具的副作用重试要分开：恢复一次模型请求，不意味着可以重新执行一次转账、部署或迁移。

**继续追问：**

- **“进程取消是不是发个 kill 就行？”** 还要处理子进程、进程组、取消与自然退出竞态以及结果收尾；需要真实进程测试。当前本地执行器的保证不能直接外推到跨机器取消。
- **“设为自动批准还安全吗？”** 自动批准改变的是审批交互，不应越过仍生效的拒绝规则；安全性也依赖实际配置。来源标记和路径策略不能被表述为完备的操作系统沙箱。

**证据入口：** [权限引擎](../../src/bot/policy/engine.py)、[执行实现](../../src/bot/execution/)、[执行与策略测试](../../tests/unit/test_execution_tools_policy.py)。

<a id="followup-rag"></a>

### F10：做了 Memory，是不是就有 RAG 项目经验？

**岗位关联：** J01、J03、J06、J08、J10—J11 的知识检索。

**可口述回答：**

> 我现有的证据主要是会话事实源、Markdown 记忆、规则路由和按需回读，能解释何时检索、来源如何授权、冲突如何核对。它不能证明我做过完整的向量检索或重排序系统。如果目标岗位需要企业知识库，我会单独建设文档接入、版本与权限、分块、召回、重排和引用链路，并分别验收检索和最终回答。

**继续追问：**

- **“怎样定位答错是检索还是生成的问题？”** 固定问题、所需证据和权限，先看正确证据是否进入候选及最终上下文，再看答案是否使用它；无答案和过期知识样本也要覆盖。检索命中不能替代回答正确率。
- **“为什么不把整本知识库放进长上下文？”** 小型、稳定资料可以先做这个基线。数据规模、更新、权限与成本变化后再比较检索方案，不能默认向量库必然优于全文输入。

**证据入口：** [Markdown 记忆](../architecture/markdown-memory.md)、[Memory Router](../architecture/memory-routing.md)。新增 RAG 链路为准备方案，不写成已实现。

<a id="followup-training"></a>

### F11：你做过 Agentic RL 或模型训练吗？运行轨迹有什么用？

**岗位关联：** J02、J11、J12；J12 的训练引擎与算法方向还需分别准备。

**可口述回答：**

> bot 这部分工作没有训练模型参数。已有轨迹和独立验收可以支持失败分析，也可能成为后续训练数据或奖励设计的基础，但还没有形成 rollout、奖励、策略更新和独立验证的训练闭环。若申请训练方向，我需要另行拿出实际训练框架、数据、优化目标、训练曲线和对照结果，不能把 API 调用或改提示词当成 RL。

**继续追问：**

- **“有 reward 为什么不算强化学习？”** 评测产生一个结果信号，与用该信号更新策略参数是两件事；还要解释训练目标、采样、参数更新和留出集表现。
- **“PPO 和 GRPO 有什么区别？”** 常见 PPO-Clip 使用新旧策略概率比与裁剪代理目标，抑制过大的有利更新；LLM 的 actor-critic 用法还要训练价值模型估计优势。DeepSeekMath 的 GRPO 对同一问题采样一组回答，用组内奖励估计相对优势，省去独立价值模型；代价包括组采样开销和奖励设计依赖。这里回答的是原理，不代表本人已经训练过。见 [DeepSeekMath 第 4.1 节](https://arxiv.org/html/2402.03300v3#S4.SS1)。
- **“长任务只有最终 reward，有什么问题？”** 很难知道哪一步真正贡献了成功或失败。可以研究过程奖励或层次化子目标，但错误的中间指标也可能被策略利用；需要用留出的最终任务验收检查是否只是提高代理奖励。这是后续实验设想，当前 bot 没有完成对应训练验证。

**证据入口：** [J12 团队原始要求](https://github.com/redai-studio/Relax/discussions/9)、[现有评测素材](resume-materials.md#9-评测与可观测性素材e01e04)。

<a id="followup-value"></a>

### F12：项目有什么实际价值？入职后你能承担什么？

**岗位关联：** J01—J03、J05、J08、J10—J11 的场景落地与工程交付。

**可口述回答：**

> 项目已经能围绕真实文件和命令完成代码、终端任务，并保留可恢复会话和独立验收证据。我可以用一个完整案例展示用户目标、工具过程、异常恢复和最终产物。现有证据更支持承担上下文、执行恢复、状态持久化或评测模块；线上用户量、客户收益和大规模服务经验需要另外证明。入职后我会先理解团队的质量指标与失败样本，再选一个可量化的模块问题落地。

**继续追问：**

- **“没有线上规模，项目价值怎么证明？”** 展示可复现案例、失败前后差异和合理的验收，比编造用户数更有用；同时承认真实用户反馈、生产运维和成本规模是尚缺的证据。
- **“如果只有两周，你先做什么？”** 先与团队确认高频故障和验收契约，做一条端到端基线，再只改一个关键变量并回归。具体排期取决于权限、依赖和已有系统；这里是工作方法，不承诺未知业务的收益。

**证据入口：** [公开基准部分结果](../evaluations/public-benchmark-40-results.md)、[Web 工作台](../guides/web-workbench.md)、[个人经历待补字段](resume-materials.md#14-从素材继续补全个人经历)。

## 9. 面试前的练习顺序

1. 用 F01 和 F12 准备一分钟开场，填写真实职责、使用对象和交付范围。
2. 从 F04 或 F05 选一件实际参与的事，按“故障 → 证据 → 修复 → 反例 → 局限”讲三分钟。
3. 用 F03 和 F06 校对每个数字的分母、版本、费用口径和失败样本。
4. 按 JD 选择 F07—F11，再进入技术手册的对应问题；没有经历的方向明确作为方案题回答。
5. 请对方连续追问两层：为什么这样做、反例是什么、如何验证。答不出时回到源码或实验补证据，避免只背开场稿。

可向招聘方反问：岗位主要负责 Agent 应用、运行时还是训练系统？当前如何独立验收任务？最主要的失败与成本来自哪里？这些答案有助于判断实际职责和准备重点。
