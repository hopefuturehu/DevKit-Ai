## 1. 如何使用这份素材

每条素材包含历史问题、具体实现、可以直接改写的简历表述，以及证据和边界。先选择自己确实做过、能够解释实现与取舍的条目，再根据岗位组合；同一机制拆出的多个角度最终可以合并。

| 个人参与程度 | 建议动词 | 需要能够回答的内容 |
|---|---|---|
| 负责方案和主要实现 | 设计、实现、重构、优化 | 原问题、核心代码、取舍、验证与失败处理 |
| 参与某个环节 | 参与……，负责其中的…… | 自己交付的具体范围及与其他模块的接口 |
| 主要负责实验 | 构建评测、设计对照、分析轨迹、定位 | 控制变量、评分方法、指标来源和结论边界 |
| 完成研究或原型 | 调研、提出、实现实验原型、验证 | 哪些已落地、哪些仍为假设、实验未覆盖什么 |

以下“简历描述”按负责该项工作的口吻起草，供筛选时改写，不默认将所有项目成果归于同一人。项目时间请使用实际参与时间，Git 首末提交时间不等于任职时间。

状态口径：**已实现**指当前源码中存在；**历史演进**指曾实施但后来替换；**实验原型**指有代码与受控验证但未成为默认入口；**研究提案**指分析或建议尚无对应生产闭环。“已实现”不自动等于已上线、经过客户验收或取得业务收益。

## 4. 上下文与记忆素材（C01—C16）

### C01：将上下文组装建模为独立模块

**状态与历史：** 已实现；主要起点 `9df98c0`，后续经 `2035795`、`ef60740`、`875750c` 演进。

**问题与实现：** 项目规则、用户输入、历史结果、记忆和运行状态具有不同来源、有效期与保留要求。以 `ContextItem` 描述来源、信任、保留策略、优先级、位置和原子组，区分持久 Transcript、压缩派生状态和最终 `ModelRequest`；先按预算选择，再按语义及稳定性排序。

**简历描述：**

> 设计独立的 Agent 上下文规划模块，以统一数据模型管理项目指令、会话历史、记忆、工具结果和运行状态，将持久事实源与模型请求视图分离，实现按来源、优先级和原子组进行预算选择及确定性组装。

**证据与边界：** [组装说明](../architecture/context-assembly.md)、[ContextPlanner](../../src/bot/core/context.py)、[上下文单测](../../tests/unit/test_context_management.py)。可以讲模块抽象与可测试性；没有维护成本下降比例或线上规模数据。

### C02：多层预算与 Tool schema 渐进披露

**状态与历史：** 已实现；`9df98c0` 引入主要机制，`d1656d7` 稳定排序，`b2ee251` 接入模型输入预算。

**问题与实现：** messages 与顶层 tools 共同占用输入，仅限制历史条数无法保护总窗口。区分输入硬上限、压缩触发目标以及输出/协议余量；工具定义超预算时保留内部恢复工具和已激活业务工具，其余降为目录，允许按名称重新激活。

**简历描述：**

> 实现覆盖消息与工具定义的分层 Token 预算，将软触发阈值、硬输入上限及输出预留分开管理；设计 Tool schema 目录化与按需激活机制，在预算压力下整组保留必要上下文并卸载低优先级内容。

**证据与边界：** [预算和 schema 规则](../architecture/context-assembly.md)、[AgentRunner](../../src/bot/core/agent.py)。默认 120K 输入、16K schema 等是配置值，不是吞吐成绩或最优参数；内部工具仍受最终总预算检查。

### C03：大工具结果外置、内容寻址与可恢复引用

**状态与历史：** 已实现；`9df98c0` 建立主要链路，`02020ff` 扩展读取方式，`47734c7` 记录公开任务中的表示削减。

**问题与实现：** 编译日志、源码和命令输出容易占满后续请求。将已接收完整正文保存为按 SHA-256 寻址的 blob，请求中保留有界头尾和引用；读取时校验 session 权限，支持范围读取和 query 定位，并处理 fork/child 的引用授权。

**简历描述：**

> 设计内容寻址的工具结果存储与引用回读机制，将大输出转换为有界预览和可校验引用，支持按范围或关键词恢复证据，并通过会话授权隔离父子任务及无关会话的数据访问。

**可附量化句：**

> 在 18 题历史公开任务快照中，23 条大工具结果的内联字符量减少 79.62%；计入小结果引用开销后，718 条普通工具结果的总内联字符量净减少 45.93%。

**证据与边界：** [效率指标](../evaluations/context-efficiency-benchmark-metrics.md)、[结构化观测](../data/public-benchmark-context-metrics.json)、[Store](../../src/bot/sessions/store.py)、[规模测试](../../tests/integration/test_context_blob_scale_benchmark.py)。这是每条结果一次计数的表示缩短，不是累计 API Token/费用节省；上游未保存的截断部分不能恢复，query 当前会读取完整 BLOB 后在进程内搜索，未实现 GC。

### C04：引用检索与一次性交付，控制正文重复回放

**状态与历史：** 已实现；`02020ff`，后续由 `12d2df0`、`8c81d7e` 补齐评测。

**问题与实现：** 已经外置的长文本被读回后，如果永久留在历史中，会重新造成输入膨胀。为 `load_context_reference` 增加 query、匹配上下文和范围控制；读取片段供一次有效模型请求使用，持久历史与后续请求保留短回执，仍可通过原引用再次读取。

**简历描述：**

> 优化外置上下文的证据读取链路，增加关键词定位与一次性交付机制，使检索正文消费后回收为短回执，保留原始引用以支持再次检索，避免已外置内容在后续轮次重复进入模型输入。

**证据与边界：** [组装与综合验收](../architecture/context-assembly.md)、[效率指标口径](../evaluations/context-efficiency-benchmark-metrics.md)、[集成测试](../../tests/integration/test_agent_loop.py)。回收只在有效消费后发生；相对全量内联可能增加工具调用。query 相对盲分页的调用收益和一次性交付相对持续回放的 Token 收益是不同对照。

### C05：稳定请求前缀与缓存成本优化

**状态与历史：** 已实现的历史优化；`4b0741f` 调整旧动态记忆位置，`d1656d7` 实施稳定排序；`cb911b1`/`d16b203` 冻结旧/新对照，`f930a19` 记录结果。

**问题与实现：** 易变状态插在会话前部会使其后的大段历史失去公共前缀，稳定记忆放在历史后部也难以复用。按稳定性重新安排指令、显式记忆、摘要、历史和运行提示，按名称排序 Tool schema；用相同 workload hash 的 Fast/Soak 验证完整任务成本。

**简历描述：**

> 定位长任务请求布局中的缓存失效来源，重排稳定指令、显式记忆与动态运行状态，并对工具定义执行确定性排序；在历史受控离线实验中，将 Fast 全请求加权缓存命中率由 70.44% 提升至 84.81%，每逻辑轮折算成本降低 35.02%，Soak 降低 27.59%。

**补充素材：** Fast 压缩后恢复到 80% 命中由 6 次请求缩短为 2 次；Fast/Soak 分别经历 5/7 次压缩，质量门禁通过。

**证据与边界：** [历史布局实验](../evaluations/context-cache-benchmark.md)。这是离线 Provider 的前缀缓存模拟及成本模型结果；不是线上账单。2026-09-10 Skill history 布局已变化，不能将旧结果作为新布局实测。命中率变化为 14.37 个百分点，不能写成“提升 14.37%”。

### C06：事务化单活动摘要与恢复一致性

**状态与历史：** 已实现；`73c13d4` 引入，`f78d911`、`cff6338` 持续完善。

**问题与实现：** 长任务压缩存在输出不合格、发布中断和多版本覆盖问题。使用 `building/ready/superseded/failed` 状态、部分唯一索引及父版本检查；候选验证通过后原子替换活动摘要，保存范围、源哈希、用户锚点和父链；恢复时校验并退回最近有效版本。

**简历描述：**

> 设计可恢复的单活动摘要机制，以 SQLite 事务、唯一约束和父版本校验维护压缩发布一致性，保留不可变原始历史及来源哈希，支持失败保留旧游标、摘要回滚和原文重建。

**证据与边界：** [压缩状态机](../architecture/recoverable-context-compaction.md)、[压缩器](../../src/bot/compaction/service.py)、[压缩单测](../../tests/unit/test_context_compaction.py)。能保证发布与来源状态，不能保证摘要语义无损；压缩失败后 Planner 仍可能卸载可选历史，不能说“失败总会停止整个任务”。

### C07：工具协议原子性与运行中补充指令

**状态与历史：** 已实现；`6f615fc`，相关后续 `7e7b9da`、`2035795`。

**问题与实现：** 用户 steering 或历史裁剪可能把 Assistant Tool Call 与对应 Tool Result 拆开，造成无效请求。以调用及同批结果为完整原子组，在工具批次结束后接收 steering；最终请求视图归位结果、标记中断未知结果、剔除孤儿结果，保留持久历史原貌。

**简历描述：**

> 修复运行中用户补充指令与历史裁剪引发的 Tool Call/Result 配对问题，实现工具消息整组保留、批次安全边界注入和发送前协议检查，使请求修复与不可变审计历史分离。

**证据与边界：** [上下文协议规则](../architecture/context-assembly.md)、[Agent Loop 测试](../../tests/integration/test_agent_loop.py)。中断结果只标注“执行结果未知”，不能伪装执行成功；该机制不等于解决所有 Provider 的 reasoning 协议问题。

### C08：中断历史闭合与积压压缩分块

**状态与历史：** 已实现；`7e7b9da`、`f78d911`。

**问题与实现：** 旧运行留下缺失工具结果时，压缩安全边界无法推进；边界恢复后又暴露一次性追赶数百条消息的问题。区分活动 Run 与已中断历史，只对后者构造可审计的逻辑闭合；按最旧完整工具组逐块摘要，对单个过大组生成有界输入视图。

**简历描述：**

> 定位中断工具调用导致的压缩游标阻塞，设计基于运行状态的历史逻辑闭合；进一步将积压历史按协议安全边界分块，分别约束摘要输入与近期尾部，支持显式多块追赶和自动逐步推进。

**历史例子：** 修复前两次请求实际输入为 159,646/167,229 tokens；修复后离线规划将位置 105—527 的一次追赶拆为首块 105—231，估算输入 47,619。

## 17. 上下文管理机制开发负责人：简历单项成稿

本节按“本人承担上下文模块的方案设计、主要实现和验证责任”这一前提起草。技术内容核对当前仓库 `ea495d6` 的相关实现与已有报告，未重新运行实验。项目时间填写实际参与时间；“开发负责人”表达模块技术责任，带人、排期和团队规模按实际经历另行填写。

一项项目经历建议组织为：**项目用途与角色 → 架构职责 → 关键难点 → 可核实结果**。正文围绕一条主线展开：在有限模型窗口内，管理长任务的输入预算、证据保留和失败恢复。

### 17.1 推荐版：作为一项完整项目经历

**bot AI Agent｜上下文管理机制开发负责人｜【实际参与时间】**

面向代码操作与工程分析的 AI Agent，负责上下文模块的架构设计、核心开发及评测验证，覆盖请求组装、历史压缩、证据回读和运行恢复。

- **架构与预算：** 设计持久会话与模型请求视图分离的上下文架构，按来源、优先级和工具原子组管理内容，统一消息与工具定义的 Token 预算、输出预留及发送前检查。
- **压缩与恢复：** 主导可恢复的单活动摘要机制，保留用户目标和近期原文，结合前缀复用、独立摘要兜底、来源校验及事务发布，实现摘要发布失败不推进游标，并支持回滚与原文重建。
- **证据按需读取：** 实现大工具结果外置、范围／关键词检索及一次性交付，消费后的回读正文收敛为短回执，保留原始引用，减少长日志和源码在后续请求中的重复传入。
- **评测与优化：** 构建跨多次压缩的对照评测，以事实保留、工具协议和原始记录不变作为质量门禁；优化请求前缀与工具定义排序，在历史离线缓存模拟中，Fast／Soak 每逻辑轮折算成本分别降低 **35.02%／27.59%**。

技术栈可写：Python、asyncio、Pydantic、SQLite、pytest、LLM API、Token 预算、上下文压缩。按本人实际使用范围筛选。

最后一条数字来自 **2026-08-23 固定旧／新布局对照**，包含主 Agent 和压缩请求的模拟用量；并非当前双路径与 Skill 历史布局的重新实测。若本人没有负责该实验，把“构建”改为实际承担的验证职责，或使用下方不带历史数字的版本。证据见[缓存实验](../evaluations/context-cache-benchmark.md)。

### 17.2 篇幅有限时如何压缩

**三条精简版：**

**bot AI Agent｜上下文管理机制开发负责人｜【实际参与时间】**

### 17.5 面试前为这一个项目准备五个回答

1. **你负责到哪一层？** 说明自己负责的方案、核心实现和验收；列出与主循环、Provider、存储及 Skill 的接口，明确相邻模块中自己实际参与的范围。
2. **最关键的设计决定是什么？** 从事实源与请求视图分离讲起：压缩只更新可替换的派生状态，原始记录用于审计、回读和重建。依据见 C01／C06。
3. **最难的一次故障怎么处理？** 选择本人处理过的发布失败、工具协议边界或输入计数偏差，按触发条件、定位证据、修复和反例验证展开。依据见 C07／C09／C12。
4. **结果怎么测出来的？** 能说明基线版本、相同负载、计费范围和质量门禁；区分离线缓存模拟、历史请求核对、真实压缩回放及整题验收。口径见第 12 节。
5. **还有什么限制，下一步怎么做？** 解释摘要遗漏和回读成本，说明更大任务集、跨模型计数校准或 blob 生命周期中的一个后续方向，并给出验收办法。参考[手册第 8 节](context-management-interview-guide.md#8-仍待补足的验收与评测)。

准备材料优先选择本人最熟悉的一处架构代码、一次故障修复和一份实验报告。简历中的每条职责，都应能落实到这类具体证据与个人行动。
