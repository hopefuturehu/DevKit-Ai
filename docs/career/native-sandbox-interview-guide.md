## 3. 架构、选型与成本

### Q01：怎样设计沙箱工作区？

**来源：** 电信面经主题。对应方案 §4–5、§7。

**参考回答：**

我会把项目文件、任务临时数据和系统控制数据分开。项目沿用用户指定的 workspace；每个 Run 有独立的 home/tmp/cache。命令可以修改授权项目，但不能读取凭证、修改审批和会话数据库，worker 与策略文件也放在任务不可写的位置。只读任务不允许写项目，worktree 子任务只允许写自己的工作树。

目录分开只是布局，真正的约束还要编译为 OS 读写策略。尤其父工作区可能包含 `.bot/agent-worktrees`，不能因为父目录可写就把所有子任务目录一起授权。

**追问：文件都放在同一个项目目录，为什么不能全放开？**

同一目录下既可能有普通代码，也可能有 `.env`、`.bot/config.toml`、`.git/hooks` 和数据库。它们的角色不同；允许编辑代码不等于允许改写控制策略或读取模型凭证。需要按实际路径保护，而且不能仅枚举当前已存在的兄弟任务目录。

**避免说：** “每个任务建个目录就隔离了。”

### Q02：为什么选原生沙箱，而不是 Docker 或 microVM？

**来源：** 电信面经选型主题。对应方案 §1、§3。

**参考回答：**

我们的首要场景是本地开发助手，需要使用宿主上的 Python、Git 等工具，目标是约束本机文件和网络访问。因此先评估原生沙箱，降低额外镜像和环境管理工作。选择 SRT 是为了复用跨平台文件规则与网络代理，同时在自己的适配接口后面锁定版本。

这不意味着原生方案总比容器好。需要一致的依赖环境时，容器更容易统一；需要面对互不信任的租户时，要重新评估 gVisor、microVM、宿主权限和控制面。Linux 上普通容器与原生机制都可能共享宿主内核，不能仅凭“容器”名称判断隔离强度。

**追问：为什么不直接写 Seatbelt/bwrap 参数？**

策略编译、网络转发、异常识别和平台兼容都有维护成本。先复用 SRT，同时检查依赖版本与能力；如果 CLI 不满足 argv、流式输出或清理要求，再评估固定版本 helper，不把兼容问题转成无沙箱回退。[SRT](https://github.com/anthropics/sandbox-runtime)、[bubblewrap](https://github.com/containers/bubblewrap)

### Q03：macOS 与 Linux 的沙箱底层分别是什么？

**来源：** 从实现与选型主题延伸的技术题。对应方案 §3、§8。

**参考回答：**

macOS 计划通过 SRT 使用 `sandbox-exec` 加载 Seatbelt 策略。Linux 的 bwrap 主要组合 namespaces 和文件挂载规则；seccomp 可以进一步限制系统调用，Landlock 用于访问权限收紧，cgroups 用于资源与进程组织。这些机制分工不同，不是几个可以直接互换的“沙箱产品”。首版实际依赖哪些机制，以锁定版本和平台探测为准。

**追问：seccomp 能直接实现“只允许访问这个目录”吗？**

普通 seccomp-BPF 主要检查系统调用号和参数值，不能直接解引用路径字符串指针来完成文件系统路径授权；它本身不是完整沙箱。路径访问需要结合挂载视图或文件访问控制机制。[内核文档](https://docs.kernel.org/userspace-api/seccomp_filter.html)

**追问：Landlock 能无条件替换 bwrap 吗？**

不能。Landlock 的支持项依赖内核 ABI，文件访问约束也不等于完整进程和网络环境隔离。方案中不自动回退。macOS 还要面对 `sandbox-exec` 的弃用状态，不能承诺接口永久稳定。[Landlock 文档](https://docs.kernel.org/userspace-api/landlock.html)

### Q04：Agent 状态放沙箱里，用户状态放外面，怎么设计？

**来源：** 顺丰面经主题。对应方案 §1、§4、§8。

**参考回答：**

我会先区分对话/审批状态和执行状态。对话、授权、任务记录和模型凭证由主进程持久化；项目产物和临时文件属于执行环境。沙箱进程销毁以后，会话与产物仍按各自策略保留，不能把“进程还活着”作为状态唯一来源。

我们的方案只把工具执行下沉，Agent 主循环仍在外面，因此不需要每次启动 worker 都重新加载完整对话。代价是主进程和结果接收端成为可信边界，必须限制可以触发的宿主操作。

**追问：沙箱返回 `approved=true`，主进程能相信吗？**

不能。工具返回值只能是数据，不能产生新权限。授权和执行事实由主进程的状态机及可信启动器决定；格式正确的 JSON 不代表授权成立。

### Q05：沙箱应该常驻，还是每次用完销毁？

**来源：** 顺丰面经主题。对应方案 §3、§8、§11。

**参考回答：**

首版选择每次调用启动受限进程，因为每个调用的权限和清理范围容易固定。常驻可以摊薄启动器、代理和 Python 导入成本，但会引入状态污染、权限变更、并发请求关联和崩溃恢复问题。我们先测额外延迟和资源使用，再决定是否为同一任务保留 worker，不直接跨任务复用有写状态的执行进程。

**追问：每次销毁会不会丢文件？**

进程生命周期与文件持久化分开。授权工作区中的产物保留；home/tmp/cache 按 Run 管理，在确认相关进程结束后回收。连接池、解释器内存状态不保证保留，应用确有依赖时再增加显式会话执行能力。

### Q06：怎样把任务发进沙箱，拿回结果？

**来源：** 电信面经任务通信主题。对应方案 §4。

**参考回答：**

主进程完成 Tool 授权后，生成不可变的调用 scope 和权限快照，再由 target 启动受限进程。命令保留 argv 与原始 stdout/stderr；文件和 HTTP 工具通过 stdin 传入有界 JSON 请求，worker 只支持固定操作枚举，返回经过 schema 校验的结果。诊断走 stderr，不执行结果里的宿主指令。

**追问：普通命令打印一行伪造的 JSON 怎么办？**

普通命令输出不走 worker 协议解析。worker 响应还要验证 request_id、大小、消息数量和终态；即便全部通过，也不能用它证明沙箱能力、审批或清理成功。控制信号与不可信输出的权威性必须分开。

**避免说：** “用了 JSON-RPC/JSON 就安全。”

### Q07：启动有多慢、占多少资源，怎么优化？

**来源：** 电信、顺丰面经主题。对应方案 §11。

**参考回答：**

目前没有本项目的原生沙箱实测数字，所以我会讲测量方法。固定机器、依赖版本、任务和缓存状态，分别比较 off/required。拆开启动器与代理初始化、worker 导入、任务运行、输出传输和清理，报告冷启动、预热后的 p50/p95、进程树峰值内存、CPU 和残留资源。

方案中的“短调用额外 p95 不超过 500 ms”和“长计算任务中位增幅不超过 10%”是待验证的工程目标，不是测得结果。短命令慢就优先看重复初始化；长任务慢就看 I/O、代理和权限失败重试。原生沙箱本身不直接增加模型 token，但额外重试可能增加费用。

**追问：为什么不先做池化？**

还不知道瓶颈时做池化，会提前引入状态复用风险。先量化，再选择预热、启动缓存或同任务常驻；每项优化都重跑权限与清理验证。

### Q08：只有一个用户，或者任务很零散，还需要沙箱吗？

**来源：** 电信面经主题。对应方案 §1、§5、§7。

**参考回答：**

需要看任务是否运行不可信代码、读取外部内容以及能接触哪些资产。单用户也可能安装恶意依赖、遇到提示注入或误删其他项目。多个任务同时运行还可能覆盖文件、争用缓存和占满资源，所以授权范围应绑定任务。

但沙箱不解决所有并发问题。两个合法任务同时修改同一个文件，仍需要文件所有权、锁、worktree 或冲突合并；原生沙箱也不自动提供 CPU/内存配额。使用互不信任租户时，需要比本方案更强的威胁模型。

## 4. 凭证、绕过与异常

### Q09：CLI 能鉴权，又不让模型看到密钥吗？

**来源：** 小满科技面经主题。对应方案 §5、§7。

**参考回答：**

可以由可信主进程或受控服务代理完成鉴权，模型只提交业务参数，不直接获得密钥。对当前设计，模型 API Key 留在主进程；工具使用最小环境，不能继承整个宿主环境、SSH agent 或 Docker socket。worker 安装路径和解释器也必须可信，否则启动时就可能加载工作区里的伪造模块。

**追问：不写进 prompt，只放工具的环境变量里，可以吗？**

不够。工具如果能执行任意代码，就能读取自己的环境变量，再写入输出。需要第三方服务凭证时，应按能力、目标和期限发放，或由主进程代理注入；这类凭证代理尚未在本项目实现，不能当作现成能力。

**追问：给一个只读数据库账号就安全了吗？**

只读限制修改，不限制能读到哪些数据。还需要用户/租户范围、表和字段权限、查询限制等业务授权，不能用 OS 沙箱替代。

### Q10：Tool 层已经检查命令和路径，为什么还需要沙箱？

**来源：** 结合当前实现补充的设计题。对应方案 §2、§4–5。

**参考回答：**

Tool 层检查的是调用入口，沙箱约束的是执行中的资源访问。例如允许 `python scripts/build.py` 后，脚本可能在内部写项目外文件，还可以启动子进程，这些操作不再调用 bot 的文件工具。沙箱在策略覆盖范围内继续限制这些操作。

但不能说所有 Tool 设计都不安全。固定业务接口如果没有任意执行能力，并且每个资源访问都经过可信校验，可以形成有效授权边界。我们的 bot 提供通用 Shell，所以保留业务授权，再加系统隔离。

**追问：只给 Shell 加沙箱够吗？**

不够。现有 read/search/patch 和 fetch 在主进程执行，文件版本检查也有直接读取路径。方案将这些操作迁入受限 worker，其他 host broker 逐项审计，防止同一资源通过另一工具被访问。

### Q11：禁止项目外写入，加域名白名单，就不会泄漏了吗？

**来源：** 技术延伸题。对应方案 §5–6、验收 S03/S05/S06。

**参考回答：**

不会自动得到这个保证。禁止写入不限制读取；域名白名单也不检查业务意图。任务若能读秘密，再向一个允许上传内容的服务发送数据，仍可能泄漏。模型 API、工具结果、日志等通道也需要考虑。

网络上必须阻断直接连接，再经过代理；仅设置代理环境变量可以被忽略。还要处理 IPv4/IPv6、重定向、DNS 解析后的本机/私网地址和重新解析，不能只检查初始域名。首版 allowlist 只有通过这些验证才开放；SRT 默认的广泛读取也必须收紧。[SRT 行为说明](https://github.com/anthropics/sandbox-runtime)

**追问：这些加上后能保证没有数据外传吗？**

仍不能这样说。允许的工具输出和服务请求本身就是信息通道；要做更强防泄漏，需要业务级授权、数据分级和内容/目的地控制。我们当前不承诺 DLP。[Anthropic 对多层隔离边界的讨论](https://www.anthropic.com/engineering/how-we-contain-claude)

### Q12：超时以后 kill 一下进程，不就结束了吗？

**来源：** 从生命周期、崩溃恢复主题延伸。对应方案 §8、验收 S11/S15。

**参考回答：**

不一定。最外层可能是 SRT 包装器，后面还有代理、Shell 和子孙进程。根进程退出时，后代仍可能运行；子进程也可能改变 session。沙箱限制访问和进程清理是两件事，不能用其中一个代替另一个。

当前 bot 已有身份校验、后代观察和有界清理，但需要针对真实 SRT 进程树重新验证。无法确认全部退出时应保留 incomplete/unknown、残留信息和配额，不假装清理成功。Linux cgroup 级回收是后续增强，不能声称已经实现。

**追问：重启后根据 PID 继续清理可以吗？**

PID 会复用，需要启动时间、宿主启动标识、后端/作用域记录等证据。恢复会话不代表恢复旧进程权限；新的 Run 若控制旧进程，应经过显式的归属/续跑授权检查，不能放开任意 process_id。

### Q13：项目配置、MCP 描述或审批结果能把沙箱关掉吗？

**来源：** 小满面经投毒主题的设计延伸。对应方案 §5.3、§7。

**参考回答：**

项目文件、模型输出和外部工具描述都不能成为安全策略的信任根。沙箱上限由可信主进程和用户配置决定，项目和子 Agent 只能收紧。批准一次命令只是允许在既定边界内执行，不能等价为关闭沙箱；已有 auto_approve 也不能放宽这个上限。

MCP 的 schema 或工具自报的 read-only 只能作为元数据，不能直接决定信任级别。远程 MCP 的服务端行为也不因本地进程进入沙箱就被隔离；需要远端鉴权、范围和审计。本仓库尚未交付完整 MCP 治理能力。

**追问：网络被拦，能否自动关闭限制重试一次？**

不能。这样让错误或恶意输入成为扩大权限的触发器。首版返回所需资源，用户修改可信配置后新建 Run；已经部分执行的任务不自动重放。

### Q14：怎样防止模型扫库、跨用户查询？

**来源：** 深信服面经主题。对应方案 §1、§7 的业务授权边界。

**参考回答：**

这首先是应用和数据层授权。用户身份由可信会话决定，不能取模型传来的 tenant_id；数据库访问使用受限账号和带租户约束的业务接口，必要时增加数据库行级策略、字段限制、查询预算和审计。只读账号仍可能越权读取。

OS 沙箱可以限制进程能否连接数据库、能接触哪些凭证，但一旦授权连接建立，通常无法判断某一行数据属于哪个用户。当前 bot 没有通用数据库授权层，这部分应该以未来设计回答，不能把 workspace 校验当作数据库 ACL。

**追问：如果工具参数已经通过 JSON Schema 呢？**

Schema 证明形状和类型，不能证明调用者拥有对应资源，也不能证明请求符合业务意图。授权必须基于可信身份和实际资源关系。

## 5. 深挖、验证与扩展

### Q15：你怎么证明沙箱真的生效，而不是只加了一个参数？

**来源：** 设计验收延伸题。对应方案 §9–11。

**参考回答：**

用独立于模型的外部观察验证实际效果。预先创建临时哨兵文件和假凭证，分别通过文件工具、Python、Shell、孙进程尝试访问，检查外部文件是否变化、输出是否含假秘密；再验证允许操作仍能成功。联网使用受控服务验证请求是否真正到达，不能只看工具是否打印 denied。

还要测缺依赖、配置损坏、跨任务调用、符号链接/硬链接、重定向、取消竞态和残留进程。macOS、Linux 分开跑，记录实际版本。发布验收缺少平台能力应失败，不能用 skip 或 mock 当通过。

**追问：项目里有多少项已经通过？**

当前只有设计中的 15 项验收场景，还没有原生沙箱通过数。已有工具策略和清理测试不能替代这些验证；需要 P0 到 P5 的新证据。

### Q16：路径 resolve 后再检查，能防住所有路径绕过吗？

**来源：** 技术延伸题。对应方案 §5、验收 S04/S10。

**参考回答：**

不能。检查与实际打开之间可能被换成符号链接，路径字符串还可能有系统别名；硬链接使不同名字指向同一文件对象，继承的已打开描述符也需要单独控制。一次 `resolve()` 不是完整的访问隔离证明。

方案保留参数层规范化，在受限 worker 再检查，并用 OS 策略约束实际访问。涉及 TOCTOU 的实现应考虑基于目录描述符的安全文件操作或平台等价方式，具体按后端能力验证。已有硬链接、特殊文件和继承 FD 的行为不能仅凭“内核会检查”就声称解决。

**追问：实测发现某个别名仍可访问怎么办？**

先明确资产与策略承诺，再修正文件布局/后端规则，必要时拒绝该工作区或该模式。达不到必需限制就不能发布 required 支持，不能悄悄改成应用层提示。

### Q17：这套设计最容易被追问的不足是什么？

**来源：** 对当前方案的审视。对应方案 §1、§3、§5、§8、§11。

**参考回答：**

我会主动说明五个代价：SRT 与平台接口有版本依赖；每次启动 worker 有额外开销；Git 元数据保护可能阻止普通 add/commit；缺少硬资源配额；同用户下的原生沙箱不能当成多租户内核隔离。同时，读白名单、网络出口和后代清理目前都还需要真实平台验证。

不以扩大整个 HOME、开放所有网络、放行 Docker socket 或自动关闭沙箱来解决兼容问题。先判断缺少的是业务能力还是后端能力，再做窄范围授权或选择更适合的执行环境。

**追问：沙箱里生成的文件拿出来执行是否安全？**

沙箱不会给产物背书。代码、构建脚本和二进制仍是不可信输入，在宿主执行前需要独立审查/验证或继续受限执行。它也不保证任务业务结果正确。

### Q18：以后要承载一千个并发任务，怎么扩展？

**来源：** 从顺丰并发与成本主题延伸的系统设计题；一千不是该帖子原题数字。超出当前首版范围。

**参考回答：**

我会先区分排队任务数、正在调用模型的任务数和实际占用执行资源的任务数。控制面管理租户身份、队列、配额、持久化、取消与租约，执行节点管理沙箱生命周期和资源。按 CPU、内存、进程、磁盘与网络预算做准入和背压；隔离后端根据租户威胁模型选择，不直接把本地共享用户的实现复制一千份。

冷启动可通过预热基础环境、缓存依赖和快照优化，但不能跨租户复用含凭证或写状态的实例。持久化任务状态和产物索引，不依赖存活进程作为唯一事实；节点故障后判断操作是否已产生副作用，不能将重试等同于 exactly-once。

**追问：你做过这些了吗？**

没有。这是从当前调用级策略与执行接口继续演进的方案，需要额外实现调度、租户认证、资源管理和故障恢复。不能用本地 `max_managed_processes` 代表分布式调度能力。

## 6. 用面试问题反查设计是否站得住

| 面试追问 | 当前方案的决定 | 还缺什么证据或能力 |
|---|---|---|
| 真的隔离了吗？ | 必需能力缺失时拒绝执行 | P0 两平台真实探针 |
| 谁控制权限？ | 主进程生成不可变策略，项目只收紧 | 配置来源和父子交集测试 |
| 文件工具会绕过吗？ | worker 迁移 + host broker 审计 | P3/P4 完整入口验证 |
| 网络与读取是否都管住？ | 收紧读范围 + 受控出口 | 私网、重定向、直连及平台版本验证 |
| 子任务互相影响吗？ | 每调用 scope + 独立临时目录/worktree | 并发、权限变化及归属测试 |
| 取消是否真的结束？ | 不明清理保留失败状态和配额 | 包装器、代理、脱离 session 后代实测 |
| 哪些正常功能会受损？ | 明确 Git/硬件工具边界 | 日常任务兼容对照 |
| 性能到底怎样？ | 分解成本，off/required 对照 | 冷热启动、p95、RSS 与总耗时数据 |
| 多租户能直接上吗？ | 首版不承诺 | 租户身份、资源与更强隔离后端 |

最适合面试展示的进展是：明确当前缺口，解释为何这样划边界，给出可失败的验收方式。实现完成后，再用平台版本、测试记录和性能结果替换“计划/目标”，不提前补造数字。

- [Anthropic 的隔离边界讨论](https://www.anthropic.com/engineering/how-we-contain-claude)：执行隔离、凭证与出口控制之间的区别。
